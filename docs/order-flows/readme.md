# オーダーの業務フロー

オーダー種別ごとと、入院から退院までのようにオーダーをまたぐ業務の運用フロー(アクティビティ図)と開発者向けシーケンス図です。医療機関の運用を検討する人は各文書の「運用フロー」、院内の開発者は「開発者向け」を読みます。

各文書の冒頭の段落と「運用フロー」節は、利用者向けのサイト(`../fhir-client-docs`)にそのまま取り込みます(取り込みは向こうの `scripts/sync-flows.mjs`)。

- 冒頭は、全員向けの概要の段落と、「医療機関の運用を検討する人は」で始まる開発者向けの案内の段落に分ける。取り込むのは概要だけ。
- 「運用フロー」節には、`docs/` のほかの文書へのリンク、画面の URL のパス、テンプレートやタスク分類のコード、seed・設定キーなどの開発者向けの内容を書かない。画面は「メニュー > 画面名」、テンプレートは画面に出る名前で書く。
- 「運用フロー」節から「開発者向け」の節を指さない。リンクは業務フローの文書どうしだけにする。
- 「開発者向け」節と開発者向けの案内の段落は、利用者向けのサイトの「シーケンス図」の部に載る。開発者向けの案内の段落と、本文の「([設計文書](../x.md) §1)」の形の出典は載せない。本文で設計文書を出典として指すときは、この括弧書きの形にする。

## 書き方の決まり

読み手が止まらないための決まりです。図の大きさ、開発者向けの語、リンクの後ろの節の名前は、取り込みのときに機械で確かめ、外れていると取り込みが止まります(`../fhir-client-docs` で `npm run sync-flows`)。

### 「運用フロー」節(読み手は医療機関の利用者と運用を検討する人)

- **節の順**: 全体の流れ → 状態 → 場面ごとの流れ(登録・予約・実施・結果…)→ 変更・中止・削除 → ほかの画面とのつながり → 帳票。ほかのオーダーとの比較(「〜との違い」)は、そのオーダーの流れを書いた後ろに置く。同じオーダーの中の区分の違い(入院と外来、検査区分など)は前に置いてよい。
- **そのページだけで流れが分かるようにする**: 「〜と同じ」で済ませるときも、利用者が必ず通る所(予約、結果の確認、取消・中止)は要点を 2〜3 行書いてからリンクする。先に読むページがあるなら冒頭に書く。
- **1 つの語は 1 つのものに使う**: 状態の名前・操作の名前・ふつうの語が重なるときは書き分ける(「回の終了」と「オーダーの終了」、「一覧の「取消」」と「到着の取消」)。同じものを 2 つの語で呼ばない(依頼医と指示医師、状態と進捗)。そのページで決めた呼び名は、最初に出る所で 1 度説明する。
- **画面の言葉**: 画面の文言は「」で囲む(メニューの場所も「部門業務 > 放射線検査一覧」)。画面に出ない呼び名は言い換えるか、最初に説明する。行の「︙」のメニューは「行のメニュー」、「DO」は最初に「DO(前回と同じ内容で出し直す)」、カルテの右側のオーダー入力は最初に「カルテの右ペイン(右側のオーダー入力)」と書く。
- **利用者に見える結果で書く**: データの持ち方・保存の仕方(「版」「焼き付ける」「展開して持つ」「同じ保存を通る」「紐付いていない」)ではなく、画面で何が起き、利用者が何をすればよいかを書く。まだ無い機能は「まだ出せません」のように書き、課題の一覧(バックログ)や連携の規格・電文・フィールドの名前(SS-MIX2、HL7 など)は書かない。
- **誰がするかを書く**: 設定する人(マスタ・施設設定)への指示と、日々操作する人への説明を同じ項目に混ぜない。
- **箇条書き**: 1 項目に 1 つの話題、3 文まで。図の下の箇条書きは、話題が 3 つを超えたら見出し語(「**予約**: …」)か小見出しで分ける。現場に効く注意を括弧や項目の末尾に入れない。
- **表**: セルは 1 文か数語。5 つを超える列挙や条件つきの説明は、箇条書きか別の表に出す。「同じ」は何と同じかを書く。
- **図(流れ図)**: 1 枚は 14 ノードまで、ノードのラベルは 2 行まで。入力チェックの並びや入力項目の一覧は図にせず、図の下の表(項目 / 条件)に出す。分岐は肯定形の問い 1 つにし、出口のラベルを問いに合わせる。任意の段は点線か「(任意)」。ノードからほかの節を指すときは「→「登録の判定」」と書く。図と本文を食い違わせない。

### 「開発者向け」節(読み手は院内の開発者)

- **最初の節は「シーケンス図の前提」**: 書き込みの経路(transaction、backend の中継、楽観ロック)と、そのページで使う呼び名(上流・ヘッダ・明細・ハブ・子、全ページを読み切る検索など)を先に説明する。図で応答の中継を省くなら、ここに書く。
- **「リソースの構成」**: 表は 1 行に 1 つの要素(リソース / 要素 / 中身)。親子の形(ハブと子、ヘッダと明細)は入れ子の箇条書きか図で先に見せる。
- **部品**: 節の頭に識別子を並べず、「操作 / 画面 / 組み立て / hook」の表にする。名前と置き場所が合わないもの(全種別共通の hook など)は一言添える。
- **シーケンス図**: 1 枚に 1 つの操作(登録・編集・削除は分ける)。メッセージは 20 本まで、登場者は 5 つまで、メッセージの文は全角 24 字まで、`Note` は 3 行まで(1 行は全角 30 字まで)。検索の条件と transaction の中身は図に書かず、図の下の表(書くもの / 条件)に出す。登場者の名前は「運用フロー」節の部署に合わせる。
- **ほかの文書の節を指すとき**: 「[rad.md](rad.md)「読影レポート」」のように、リンクの直後に見出しをそのまま「」で書く(取り込みのときに、その節へのリンクになる)。1 つのリンクに「運用フロー」節と「開発者向け」節の見出しを混ぜない。
- **「医事会計と SS-MIX2」**: どの行も「なし」の列は作らず、1 文で書く。
