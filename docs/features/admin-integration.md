# 管理画面・外部連携・サーバー起動

## 管理画面（接続設定 / OAuth クライアント / SMART アプリ）

`/settings`（接続設定）、`/oauth-clients`（OAuth クライアント）、`/smart-apps`（SMART アプリ）は管理用の画面です。

接続設定の「ブラウザから見た FHIR サーバー URL」は、backend が上流を呼ぶ URL とは別に、ブラウザが上流を
直接叩くときの URL です（SMART アプリに渡す `iss`、ヘッダーの「起こす」ボタンの宛先）。開発環境では backend は
`host.docker.internal:3000` で繋ぎ、ブラウザは `localhost:3000` で繋ぐので値が違います。空欄なら
環境変数 `FHIR_SERVER_PUBLIC_BASE_URL`、それも無ければ FHIR サーバー URL と同じ値を使います。

### アクセス制限

環境変数 `ADMIN_TOKEN` を設定すると、両画面はログインを要求します。入力したパスフレーズは
backend が照合し、成功すると **HttpOnly のセッション Cookie**（`path=/admin`、SameSite=Lax、12時間）を
張ります。トークンをブラウザ側（sessionStorage 等）に保持しないため、XSS でパスフレーズ自体を
持ち去られることがありません。非 GET リクエストには `X-CSRF-Token`（ログイン応答で渡される値）が必要です。

`ADMIN_TOKEN` 未設定なら従来どおり認証なしで通ります（`docker compose up` だけで触れる）。
ただし本番環境では、`ADMIN_TOKEN` 未設定のとき OAuth クライアント管理の API は 503 で閉じます。
`Authorization: Bearer` / `X-Admin-Token` ヘッダーによる直叩き（curl・CI）も従来どおり使えます
（Cookie を使わないので CSRF トークンは不要）。

`ADMIN_TOKEN` をローテーションすると既存のセッションはすべて失効します。

### OAuth クライアント管理

fhir-server 側の OAuth クライアント（SMART Backend Services / 対話型 launch）を一覧・登録・削除できます。
これまで fhir-server の rake タスクでしか登録できず、削除の手段がありませんでした。

**fhir-server 側に管理 API `/admin/oauth_clients` を追加してあります**（`FHIR_ADMIN_TOKEN` による共有トークン認証）。
fhir-server は CORS を意図的に無効にしているため、ブラウザから直接は叩けません。この backend が
`FhirAdminGateway` でサーバー間中継します（`FHIR_SERVER_HOST_HEADER` は引き続き HostAuthorization 対策として必要）。

使うには両側の設定が必要です:

1. fhir-server に `FHIR_ADMIN_TOKEN` を設定する（`openssl rand -hex 32`。未設定なら管理 API は 503）
2. fhir-client の `/settings` で「FHIR 管理トークン」に同じ値を入れて保存する
   （DB に暗号化して保存。`FHIR_ADMIN_TOKEN` 環境変数でも渡せますが、接続先を変えるたびに
   再デプロイが必要になるので画面からの設定を推奨）

`client_secret` は登録直後の一度だけ表示され、以後どのレスポンスにも現れません。削除は物理削除で、
発行済みのアクセストークン・リフレッシュトークン・認可コードも同時に失効します（件数が返ります）。

> 上流の管理トークンが誤っている場合、画面は 502「管理トークンを拒否されました」を表示します
> （401 をそのまま返すとログアウト扱いになってしまうため、意図的に読み替えています）。
> 上流がスリープ中の場合、初回の表示は最大 90 秒ほどかかることがあります。

アプリ連携（SMART App Launch）のクライアントは「利用者」で患者本人（`patient/`、standalone launch）と
医療従事者（`user/`、カルテから起動する EHR launch）を選びます。両方を混ぜた登録は上流が 422 で拒みます。
カルテから起動するアプリには、スコープに加えて「電子カルテからの起動」（`launch`）を付けてください。
これが無いクライアントには起動文脈を発行しません（SMART アプリ画面の選択肢に「launch 未登録」と出ます）。

### SMART アプリ

カルテの「アプリ」タブから起動する外部アプリの台帳です（`docs/smart-app-launch-design.md`）。名称、
OAuth クライアント（アプリ連携のもの）、起動 URL、表示（埋め込み / 別ウィンドウ）、有効、表示順を持ちます。
認可（スコープ・リダイレクト URI）は OAuth クライアント側の登録が正で、ここでは変えられません。

起動の流れ: カルテがこの backend に起動を求める → backend が上流の管理 API `POST /admin/launch_contexts` に
開いている患者・受診とログイン中の医療者を名乗って launch トークン（5 分・単回）を発行してもらう →
起動 URL に `iss`（ブラウザから見た FHIR サーバー URL）と `launch` を添えて iframe に出す → アプリが上流の
`/oauth/authorize` に `launch` を持って行くと、上流はログイン・同意画面を出さずに認可コードを返す。
医療者の身元は「この backend が管理トークンを持って名乗った」ことで保証されるので、管理トークンの扱いは
OAuth クライアントの発行と同じ重さです。

埋め込み表示のアプリは、自身の応答に `Content-Security-Policy: frame-ancestors <このアプリのオリジン>` を
出す必要があります（`X-Frame-Options: DENY / SAMEORIGIN` を出すと枠内に表示されません）。起動 URL は
本番では `https` だけ受け付けます。

検証用の最小アプリを `frontend/public/smart-demo/index.html` に同梱しています。OAuth クライアントに
アプリ連携・医療従事者・public・リダイレクト URI `http://localhost:5173/smart-demo/index.html`・
スコープ `user/Patient.read user/Encounter.read user/Observation.read launch launch/patient launch/encounter openid fhirUser`
で登録し、SMART アプリに起動 URL `http://localhost:5173/smart-demo/index.html?client_id=<client_id>` で登録すると、
カルテの「アプリ」タブで氏名・受診・直近の検査結果と `fhirUser` が出ます。

## 外部システム連携

レセコンをはじめとする外部システムの設定は、管理 > 外部システム連携の一覧に並びます。
システムを選ぶと**そのシステムに応じた設定ページ**が開き、**有効/無効はシステム単位**です。

どんなシステムがあり、設定ページに何を出すかは backend の定義
(`Integrations::ExternalSystems`)が持ちます。画面はその宣言を見て描くだけなので、
特定の製品やシステムの語彙を持ちません。

| 定義が宣言するもの | 意味 |
|---|---|
| `sections: :connection` | 接続先 URL・ユーザー・パスワードと接続テスト(API で繋ぐシステム) |
| `sections: :inbound_token` | 外部から通知を受ける Bearer(院内エージェントに配る) |
| `sections: :code_mappings` | カルテ ↔ 外部システムのコード対応表 |
| `adapters` | 製品(`system_type`)の選択肢。製品固有の設定項目はアダプタが宣言する |
| `fields` | 定義自身が宣言する設定項目。**API で繋がないシステム**はこれだけを持つ |

設定は `external_system_connections` にシステム(`system_key`)ごとの 1 行として入ります。
接続先・ユーザー・パスワード・受信トークンは決まった列に、それ以外の項目は `options`
(jsonb)に入るので、システムを足すときにテーブルは変わりません。パスワードと受信トークンは
暗号化して保持し、パスワードはブラウザへ返しません(受信トークンは配る必要があるので
再発行時にだけ平文で返ります)。

コード対応表(`external_code_mappings`)は**製品(`system_type`)のコード体系に対する表**
なので、同じ製品と繋ぐシステムは同じ表を見ます。

システムを足すときは定義に 1 要素加えます。API で繋ぐなら、あわせてアダプタを 1 つ書いて
`adapters` に登録します。

## レセコン連携

レセコンは「外部システム連携」のひとつとして繋ぎます。カルテ側のコードに製品名は
出てこず、製品ごとの電文や語彙は backend のアダプタ(`Integrations::Orca` など)に
閉じています。他社レセコンを足すときはアダプタを 1 つ書き、定義の `adapters` に
登録します。詳細は `docs/receipt-computer-integration.md`。

向きは次のとおりです。

| | 向き | 中身 |
|---|---|---|
| 患者基本情報 | レセコン → カルテ | 氏名・生年月日・性別・住所・連絡先 |
| 保険・公費 | レセコン → カルテ | FHIR の `Coverage`(JP_Coverage)として保持 |
| 受付 | レセコン → カルテ | 当日受付と同じ形の `Appointment` |
| 病名・診療行為(会計) | カルテ → レセコン | レセプト電算コードで送る |

- **患者・保険・受付はレセコンが正本**です。カルテから登録しません。
  保険は取り込んだ `Coverage` を読むだけで、レセコンを画面から直接見に行くことはありません。
- 「同時に使う保険の組」はレセコンが採番した**不透明なキー**として `Coverage.class` に
  持ちます。カルテは中身を解釈せず、会計送信のときにそのまま返します。
- CLAIM は 2026 年 3 月末で廃止済みのため、連携は API(HTTP/XML)と PUSH 通知で行います。
- 受付取消の「診察が始まっているか」は上流の `Encounter?appointment=` で確かめます。**fhir-server を
  先にデプロイ**してください(旧版だと検索条件が黙殺されて全件が返り、取り消せなくなります)。

### 通知の受け取り

レセコンの変更は PUSH 通知(WebSocket)で届きますが、**backend は WebSocket も
製品ごとのイベント形式も知りません**。院内に常駐するエージェント
(別リポジトリ `fhir-client-agent`、Go 製の単一バイナリ)が通知を中立なイベントに直し、
`POST /integrations/receipt/events` へ HTTP で渡します。

通知は「患者番号が変わった」としか言わない(保険の中身は入らない)ので、
カルテは必ずレセコンの API で取り直します。**未接続中の通知は再配達されない**ため、
取りこぼしは次のどちらかで回復します。

- カルテ > 患者情報 > 保険・公費 の「医事会計から再取込」(患者 1 人)
- `bin/rails integrations:receipt:resync`(取り込み済みの患者を洗い直す)

### 画面

連携が無効な環境では連携 UI は出ません。

| 画面 | できること |
|---|---|
| 管理 > 外部システム連携 > 医事会計 | 接続先・資格情報・受信トークン。接続テストで医療機関名と保険医療機関番号を確認できる |
| 管理 > 外部システム連携 > 医事会計 > コード変換設定 | 診療科・医師のコード対応付け(種別はアダプタが宣言する) |
| カルテ > 患者情報 > 保険・公費 | 取り込んだ保険・公費の参照と再取込 |
| 外来一覧 > 行メニュー > 医事会計へ会計送信 | 送る内容を確認してから病名と診療行為を送る。送り直し・取消も同じ場所 |

送る診療行為は、実施入力を持つ種別(放射線・生理・内視鏡・処置・手術)では実施記録
(Procedure とその配下の薬剤・材料・コメント)から組み、実施記録の無い当日のオーダーは
「未実施」として送りません。実施入力を持たない種別(検体検査・細菌検査)と処方はオーダーの
実施(予定)日で集めます。剤の区分は診療行為マスタの章から決めるので、実施入力で足した
加算・薬剤・材料はそのまま同じ剤に載ります(設計は `docs/receipt-billing-design.md`)。
送信は同期で行い(ジョブ基盤は使いません)、記録は
`log/integrations/receipt_computer.log` に JSON Lines で残ります。送信済みかどうかは
レセコンに訊くので、カルテ側に控えは持ちません。

**レセプト電算コードが設定されていない項目は送りません。** 黙って落とさず、
送信前のプレビューに「送れない項目」として理由つきで出します。

検証環境は別リポジトリ `weborca-dev` にあります(WebORCA オンプレ版を Docker で起動)。
無償ソース利用では改定パッチもマスタ更新も取得できないため、**点数計算の正確性は検証対象外**で、
電文の形と往復の確認に使います。エージェントごと通しで動かす手順は
[任意の profile(院内エージェント / 日レセ)](../development.md#任意の-profile院内エージェント--日レセ)を参照。

## サーバーの休眠と「起こす」ボタン

Render 無料枠は約 15 分アクセスがないとスピンダウンし、次のリクエストで起動に 1 分前後
（backend + 上流 fhir-server で合わせて 1〜2 分）かかります。画面操作で待たされないよう、
ヘッダー右端に地味な「サーバー起動」ボタンを置いています。

- 押すと backend の `GET /wakeup` をポーリングします（最大 4 分、5 秒間隔）。
  リクエストが backend に届くこと自体が backend の起動トリガーです。
- 上流 fhir-server を起こすのは **ブラウザ** です。`/wakeup` が返す `upstream_probe_url`
  （`FHIR_SERVER_BASE_URL` + `/up`）を、フロントが `mode: "no-cors"` で直接叩きます
  （同時 1 本、最大 60 秒）。backend から叩いても上流は起きません（後述）。
- `/wakeup` 自体は上流の `/up` を 5 秒だけ叩き、その瞬間の可否
  （`{"backend":"ready","upstream":"ready"|"waking","upstream_probe_url":"…"}`）を返す
  判定専用です。待ち切らないのは、長時間ぶら下がるとゲートウェイのタイムアウトに
  当たるためです。
- ボタンの表示は「backend 起動中…」→（backend から応答が返ったら）「FHIR サーバー起動中…」
  と進み、両方起きると「起動しました」になって数秒後に元へ戻ります。

`/wakeup` は静的サイト側の rewrite（`render.yaml`）と dev サーバーの proxy（`vite.config.ts`）
で backend に転送しています。

### なぜ上流はブラウザから起こすのか

Render 上のサービスから `*.onrender.com` を叩くと内部経路に落ちるらしく、スピンダウン中の
インスタンスの起動トリガーになりません。本番で実測したところ、上流がコールドの間 backend
からのプローブは `open_timeout`（2 秒）にも達せず即失敗し（`/wakeup` 全体が 0〜1 秒で応答）、
2 分叩き続けても上流は寝たままでした。一方、外部クライアント（ブラウザや手元の curl）から
同じ URL を叩くとゲートウェイがリクエストを保留して起動が走り、~45 秒で 200 を返すように
なります。この非対称性が「起こすのはブラウザ、判定は backend」という分担の理由です。

なお `/wakeup` は上流を起こさずに状態だけ観測できるので、切り分けにも使えます。
