# オーダー共通・オーダーセット・レジメン・パス

## オーダーの日付(登録日時と開始日)

全 17 種別のオーダーで `ServiceRequest` の日付の意味を揃えてあります(2026-09-01。`fhir/shared.ts` 冒頭、
検討の経緯は `docs/order-common-backlog.md` §1)。

- **`authoredOn` = オーダー登録日時**。初回保存時にクライアントがシステム時刻を秒+オフセット付きで入れ
  (`nowFhirDateTime` / `registrationAuthoredOn`)、編集では元の値を引き継いで動かしません。DO(流用)は新規
  扱いです。フォームに入力欄はなく、詳細モーダルの「登録日時」行(`RegisteredAtRow`)で見ます。
- **`occurrenceDateTime` = オーダー開始日(実施予定日)**。種別ごとの「検査日」「撮影日」「実施日時」「注射日」
  「投与開始日」「開始日」「採取予定日時」「投与予定日時」「予定手術日」「希望日」はすべてここに入ります。
  全種別で必須で、未定(値を出さない)を許すのは手術だけです。カルテのカードの位置・診療日ペイン・
  部門一覧の日付軸はすべてこの値です(`orderDay`)。
- **例外は処方一覧の日付軸だけ**で、交付日(登録日の日付、`authoredon`)で引きます。薬剤部は当日交付された
  処方を受け取って開始日前日までに調剤するので、投与開始日で引くと入院の定期処方が開始日まで見えません。
  投与開始日は一覧の列で見せます。注射は 1 日 1 オーダーなので注射日(`occurrence`)で引きます。
- 既存データは上流 `fhir-server` の migration(`20260901000001`)がヘッダの `occurrenceDateTime` に
  `authoredOn` を写して補完しました(手術は対象外、`authoredOn` は書き換えません)。

## 代行入力の記録と承認

医師以外がログインしてオーダーを入力する場合(カルテ画面ヘッダーで依頼科と**指示医師**を選ぶ、
`OrderContextPicker`)、オーダー本体に入るのは指示医師(`requester`)だけなので、**実際に入力した本人**と
**指示医師の承認**を `Provenance` に残します(記録 2026-09-01、編集時の記録と承認 2026-09-02。
検討の経緯は `docs/order-common-backlog.md` §2)。厚労省の安全管理ガイドラインが代行入力に求める
「誰が入力し・誰の指示で・指示した医師が確認したか」の 3 点をこれで揃えます。

- **1 回の操作 = Provenance 1 件**。登録(`activity = CREATE`)と編集(`UPDATE`)のたびに 1 件書きます。
  登録は `useCreatePrescription`(名前は処方由来ですが 17 種別すべての登録がここを通ります)、編集は
  各種別の更新フック(`useUpdatePrescription` ほか 10 本)が、組み立て済みの transaction Bundle を
  `useWithOrderProvenance` に通して entry を足します(`fhir/provenanceHelpers.ts` の
  `buildOrderProvenanceEntry`)。中止・削除には書きません(削除は対象そのものが消えます)。
- `target` はオーダーのヘッダ(`basedOn` を持たない `ServiceRequest`。新規は `urn:uuid:` なので transaction
  内で解決、編集は PUT 先。注射の連日オーダーは日ごとのヘッダを全部)と、同じ Bundle の
  `MedicationRequest`(処方・注射の明細)。検体検査などの明細 `ServiceRequest` は入れません。
- `agent` は `author`(= オーダーの `requester`)と `enterer`(= ログイン中の医療従事者、`onBehalfOf` に
  指示医師)の 2 件で、氏名は `who.display` に焼き付けます。**入力者 = 指示医師でも常に残します**
  (後から「代行だったか」を判定でき、付け忘れも起きません)。
- **承認は活動ごと**。`enterer ≠ author` の活動だけが承認待ちで、指示医師本人が入力・編集した活動は
  承認不要です。承認すると同じ Provenance に `agent(type = verifier)` と `signature[]`(ASTM E1762 の
  Verification Signature。`when` / `who` だけで暗号署名 `data` は持たない、操作の記録)を足して PUT します
  (`buildApprovedProvenance`)。承認済みのオーダーを代行者が編集すると、その編集ぶんだけがまた承認待ちに
  なります。承認できるのは `author` 本人のみ(`useCanApproveOrder`)。
- **承認待ちは通知(Task)で拾います**。`enterer ≠ author` の来歴を書くとき、同じ transaction に
  指示医師あての `order-approval` の通知を積みます(`fhir/orderApprovalTaskHelpers.ts` の
  `buildOrderApprovalTaskEntries`)。`focus` は来歴の `urn:uuid` で、上流の transaction が
  `Provenance/{id}` に解決します。真正性の正本は引き続き Provenance で、通知は宛先と未対応・対応済みだけを
  持ちます([notifications.md](notifications.md))。
- **承認**すると、来歴への署名の PUT と通知を対応済みにする PUT を 1 つの transaction で送ります
  (`api/notificationActions.ts` の `approvalTransactionEntries`)。来歴は id で渡して中で最新を読み直すので、
  一覧を開いたままでも古い内容で上書きしません。通知を持たない承認待ち(通知の導入前のもの)でも
  承認は通ります。
- **画面**は 2 か所。詳細モーダルの来歴の行(`components/OrderDetailRows.tsx` の `EnteredByRow`。
  登録が代行なら「代行入力」、編集があれば「最終更新」、代行の活動があれば「承認」の行で、未承認かつ
  指示医師本人には「承認」ボタン)と、診療業務メニューの「通知」(`pages/NotificationPage.tsx` の
  種別「オーダー承認」。自分あての承認待ちを活動単位で並べ、カルテの詳細モーダルで内容を確認してから
  承認するか、一覧から直接・一括で承認する)。
- **承認前でもオーダーは部門に流れます**(`ServiceRequest.status = draft` は部門一覧から消えるので使えず、
  緊急オーダーが止まると危ないため)。部門一覧・カルテのタイムラインに未承認の印は出していません
  (`_revinclude` を足すと編集回数ぶん膨らむため)。出すことにした場合は、通知の `basedOn` にヘッダを
  入れてあるので `_revinclude=Task:based-on` で引けます(`_revinclude=Task:focus` は上流が
  ServiceRequest しか返さないので使えません)。
- 通知の導入前に溜まっていた承認待ちには、`bin/rails notifications:backfill_order_approval`
  (`backend/lib/tasks/notifications.rake`)で後から通知を作りました。既に通知を持つ来歴は飛ばすので
  何度流しても増えません。
- **読むのは詳細を開いたときだけ**(`useOrderProvenance`)。カルテのタイムラインは 1 ページ 20 件・
  先読みは 100 件 × 2 本をカルテを開くたびに叩くので、そこに `_revinclude` は足していません。
- 上流の `AuditEvent` は依然 OAuth クライアントしか記録せず、エンドユーザーは Provenance でしか追えません
  (認証回りの変更になるので別課題)。

## 警告(判断支援)の共通の器

処方・注射・放射線・放射線治療・生理・内視鏡・食事・指導・管理料のフォームとレジメン適用で出す警告は、1 つの型(`Advisory`)と 1 つの表示部品に
乗っています(`docs/advisory-design.md`)。重さは 3 段階です。

- **表示のみ**(橙): 重複投与、併用注意、妊娠・授乳、感染症、同一部位の照射歴、食物アレルギーの反映、開始日の注意、算定回数の上限など
- **確認を要する**(赤): アレルギーの一致、併用禁忌、用量の上限超過、許可制の抗菌薬、造影剤アレルギー・造影の注意区分・eGFR 30 未満、
  MRI の体内金属、レジメンの適応基準外・体重の大きな変化・同じレジメンの二重適用、判断支援の重要カード
- **止める**: 第 1 段では該当する警告はありません(型と流れだけ用意)

確認を要する警告が残ったまま「登録」すると「警告の確認」のモーダルが出て、1 件ずつ理由(マスタメンテ > 警告 > 警告の確認理由マスタ)を
選ぶまで登録できません(補足は自由記述)。選んだ理由は来歴 `Provenance`(activity `override`、オーダー詳細の「警告の確認」行)と
backend の台帳に残り、管理 > 警告の集計と設定で種別 × 月の発火数・無視率を見られます。施設は種別ごとに重さを「表示のみ」「出さない」に
下げられます(上げることはできません)。

## オーダーの削除

全種別の削除(カルテのカード・部門一覧・パスの取り消し・レジメンのクール取消)は、各種別が組んだ削除の
transaction を `api/queries/orderDelete.ts` の `postOrderDeleteBundle` に通して送ります。Bundle が消す
`ServiceRequest`(ヘッダ・明細)を指すものをその場で引き直し、次のように扱います。

- **一緒に消す**: 進捗・通知の `Task`(`focus` か `basedOn` がオーダー。承認待ち・疑義照会・食物アレルギーの
  通知を含む)と、薬剤明細を指す調剤・払出の記録(`MedicationDispense`)。
- **削除させない**: 実施記録(`Procedure` / `MedicationAdministration`)か結果(`DiagnosticReport` /
  `Observation`)が付いたオーダー。「実施記録があるため削除できません」と出すので、実施を取り消すか
  結果を削除してから消します。中止で残す運用はそのまま使えます。ただし削除の Bundle 自身が同じ
  transaction で消す実施記録は数えません(登録と同時に実施済にする指導・管理料は、実施記録ごと消します)。
- 残すもの: ラベル発行済みの `Specimen`(発行・到着の記録)と来歴の `Provenance`。

## 指導・管理料

医学管理料(点数表 B 章)と在宅(C 章)を、カルテ右ペインの「指導・管理料」で算定します(設計は
`docs/medical-management-order-design.md`)。部門が受ける種別ではないので、**登録と同時に実施済**になります。

- **項目**はマスタメンテ > 医学管理 > 指導・管理料項目で、施設が算定するものだけを診療行為マスタの B 章・C 章から
  選んで登録します(加算の候補・入院 / 外来・月の上限回数も)。`db:seed` で主な管理料・文書料・在宅の 27 件が入ります
  (特定疾患療養管理料は 100 床以上 200 床未満の病院のコードなので、施設に合わせて直します)。フォームは入外区分に合う有効な項目を並べ、
  チェックした項目の下に加算の候補が出ます。
- 登録はヘッダの `ServiceRequest`(`status = completed`、算定日 = `occurrenceDateTime`)と、項目ごとの実施記録
  (`Procedure`、加算はその子)を 1 つの transaction で書きます。医事会計はこの実施記録を 1 項目 1 剤で送ります
  (B 章は 130、C 章は 140)。備考はヘッダに置き、日レセへのコメントにはしません。
- 各項目に**前回算定日と算定日の月の回数 / 上限**を出し、上限に達している項目を選ぶと警告(表示のみ)が出ます。
  算定できるかの判断は日レセに任せます。
- 編集は同じ項目の実施記録を書き換え、外した項目・加算の記録は消します。削除は実施記録ごと消します。

## 研修医のカウンターサイン

研修医・学生が書いた診療記録とオーダーを、指導医が後から承認(カウンターサイン)・差戻し・コメントします
(設計は `docs/countersign-design.md`)。承認前でも記録は読め、オーダーは部門へ流れます(代行入力と同じ方針)。

- **研修医・学生の印**は医療従事者の「研修区分」(`Practitioner` のローカル拡張 `trainee-level`、
  `resident` / `student`)です。職種は医師のままにします(研修医を職種にすると医師扱いでなくなり、オーダーが
  代行入力の経路になるため)。学生は職種を医師にしないので、オーダーは今の代行入力の経路です。
- **指導医グループ**(マスタメンテ > 共通 > 指導医グループ、backend の `supervisor_groups` /
  `supervisor_group_members`)に指導医と研修医を入れます。研修医が属するグループの指導医なら**誰でも**
  承認できるので、担当の指導医が不在でも止まりません。`GET /master/supervisor_groups/mine` が、ログイン中の
  人から見た「仰ぐ指導医」と「受け持つ研修医」をグループをまたいで返し、画面はこれで承認の可否を決めます
  (`useCountersignContext`)。
- **診療記録**は看護サマリーの承認と同じ器です(`fhir/countersignHelpers.ts`)。研修医が書いた記録には
  `Composition.category` に印(`countersign`)を付け、確定(`final`)すると研修医の `attester(legal)` だけの
  **承認待ち**、指導医が承認すると `attester(professional)` を足して**承認済**、差戻しは `preliminary` に戻して
  署名を外します(理由は通知に持つ)。研修医が確定し直すと `professional` が落ちてまた承認待ちになり、
  指導医が直して保存すると(修正承認)その内容で承認済みになります。カルテのカードには「承認待ち」「承認済」の
  バッジが出ます(Composition だけで決めるので、通知は引き直しません)。
- **オーダー**は代行入力の承認と同じ `Provenance` です。研修医が自分を指示医師として入力した活動は、来歴の
  `author` に研修区分の `role` が付き、承認待ちになります(`needsApproval` は「代行か研修医」)。承認できるのは
  本人ではなく、受け持つ指導医です(`useCanApproveOrder`)。
- **通知**は指導医ごとに 1 件ずつ作ります(`note-countersign` カルテ承認・`order-approval` オーダー承認)。
  誰かが承認・差戻しすると、その人の通知を対応済みに、残りの指導医の通知を取り下げます
  (`api/notificationActions.ts`)。差戻しは研修医あての `note-returned` で、確定し直すと自動で閉じます。
  指導医が 1 人も登録されていなければ通知は作りません(承認は詳細からできます)。
- **コメント**は承認待ちの通知(`Task.note`。対応の記録と見分ける印の拡張付き)に積みます。承認・差戻しに
  添えても、単独でも書け、自分のものは直せます・消せます。閉じた通知のぶんも含めて記録の詳細に歴として並びます。
- **画面**は 3 か所。記録の詳細(カルテの詳細モーダル)の「カウンターサイン」欄(状態・承認者・差戻し理由・
  コメント歴と、指導医には承認・差戻し・コメントの操作)、診療業務 > **カルテ承認**(`/countersigns`。自分あての
  記録・オーダーの承認待ちと承認済みを、種別・研修医で絞って並べ、記録はその場のモーダルで確かめて操作)、
  通知(種別「カルテ承認」「カルテ差戻し」)。オーダーの承認は従来どおりカルテの詳細の「承認」行です。

## 日付未定オーダー

「依頼だけ立てて実施日は後で決める」オーダーを、種別に依存しない形で扱えるようにしてあります
(`fhir/karteTimeline.ts`)。フォームで未定を許しているのは手術・放射線検査・生理検査・内視鏡です。
他の種別で開きたくなったらフォームの必須検証を外して `UNSCHEDULABLE_ORDER_TYPES` に足すだけです。

- **未定は値を入れないことで表します**(`occurrenceDateTime` を出さない)。予約値(`9999-12-31` など)は
  「この値は未定」という約束を全種別・全部門一覧・帳票が守り続ける必要があり、閉じ込め先が無くなるため
  採りません。上流は `:missing`・`$distinct-dates` の `undated` に対応済みです。
- **カードを置く診療日**は「開始日(`occurrence`)。無ければ、未定を許す種別なら『日付未定』、それ以外は
  登録日(`authoredOn` の日付)」です(`orderCardDay`)。後者は `occurrence` を書く前に登録された旧データの
  ためのフォールバックで、上流の補完後は起きません。
- **「日付未定」は時系列の最上部**に出します(`KARTE_UNSCHEDULED_DAY` / `compareKarteDaysDesc`)。
  既にある「日付なし」(`day` が空文字、最下部)とは別概念で、あちらは日付を持たないリソース(データ不備)、
  こちらは予定がまだ決まっていない正常な状態です。表示名はどちらも `karteDayLabel` が返します。
- **本流と先読み**: タイムラインのオーダーは**開始日(`occurrence`)が今日以前のものを新しい順**に
  ページングします(`_sort=-occurrence` + `occurrence=le{today}`、`useKartePrescriptionsInfinite`)。
  カードを置く軸と読む軸が同じなので「この日より新しい日は読み切った」というカットオフ判定が厳密に
  成り立ちます。日付未定のものと開始日が今日より後のものは、種別ではなく**状態で切った別クエリ**
  (`occurrence:missing=true` と `occurrence=gt{today}`、`useKartePendingOrders`)で全件先読みし、
  ページングの結果と `ServiceRequest.id` で寄せます。どちらも未処理の仕事なので件数は溜まりません。
- **診療日ペイン**の日付も同じ出どころで、`$distinct-dates` を `date-param=occurrence` の 1 本で当てます。
  看護指示はカードにしないので、本流・先読み・診療日のいずれも `category:not` で外します。

**放射線・生理・内視鏡**は、オーダー枠(登録される 1 オーダー)ごとに日付欄の横の「日付未定」で出せます。

- 通常のオーダーだけです。至急は当日、事後は実施済みの日が決まっているためです。
- 予約必須の項目は「予約」か「日付未定」のどちらかを選びます。日付未定のオーダーは即実施にできません。
- 日付は依頼側の**編集**か、部門一覧の日付未定タブの「**予約**」で決めます。どちらも予約(`Appointment`)と枠の
  busy 化をオーダーの日付の更新と同じ transaction で書き、撮影日時(実施日時)が枠の開始になります。部門一覧からは
  ヘッダと明細の `occurrenceDateTime` を書き換えて PUT するので(`buildExamScheduleBundle`)、読んだ後に依頼側が
  編集していれば版違い(412)で止まります。枠表と所要時間は項目マスタの値を初期値にします。
- 部門一覧(放射線検査一覧・生理検査一覧・内視鏡一覧)は手術一覧と同じく「撮影日別(実施日別)」と
  「日付未定」のタブに分け、日付未定タブに `occurrence:missing=true` のオーダーを並べます
  (`UNSCHEDULED_WORKLIST_DATE`)。件数はタブ名に添えます。受付・中止・予約はできますが、実施はできません(実施日が無いため)。

## オーダーセット（よく出すオーダーのひとまとめ）

処方・検体検査・放射線検査などをまとめて保存し、カルテから一括で出す仕組みです。詳細は `docs/order-set-design.md`。

- **入口**: 「診療業務 > セット登録」(`/order-sets`)で登録・整理、カルテ右ペインの「セット」で適用。
- **持ち主は 3 段階**: 院内共通 / 診療科 / 医師。編集できるのは順に「医師なら誰でも / その科を担当する医師 / 本人」。
  医師かどうかは画面側(PractitionerRole)で判定し、backend が厳密に守るのは医師スコープの持ち主 = ログイン本人だけです。
  医師以外は閲覧のみ。フォルダで任意の深さに整理でき、複製で別の持ち主へ写せます(自分 → 診療科 → 院内共通への昇格)。
- **登録は通常のオーダー登録と同じ画面**。患者と日付に関わる入力(対象プロブレム・投与開始日・依頼病名・予約・即実施など)は
  出ません。保存する中身はフォームの入力値そのもの(backend の `order_set_entries.values`、jsonb)で、患者への参照は保存前に落とします。
- **適用は「全部のフォームを出して、直してから一括登録」**。各オーダーは既定で閉じていて(「すべて開く / すべて閉じる」で一括開閉)、
  除外するものはチェックを外します。入外区分は患者の在院状況に合わせて開きます(セットと食い違うと注意が出ます)。
- **適用日**を上で選ぶと、各オーダーの開始日(投与開始日・検査日・撮影日など)にまとめて入ります。既定は当日で、
  予約が必要な検査だけは予約した枠の日時が優先されるため動きません。個別に直したいオーダーは開いて日付を変えられます。
- 1 つの transaction なので途中まで登録されることはなく、来歴(Provenance)も 1 回の適用につき 1 件です。
  1 件でも入力検証に落ちると何も登録されません。
- **登録されたオーダーには出どころのセットが焼き付きます**(ヘッダ ServiceRequest の identifier `order-set-instance` と拡張 `order-set`)。
- 代行入力(医師以外のログイン)でカルテを開くと、「医師のセット」はログインユーザーではなくヘッダーで選んだ**指示医師**のものになります。
- 対応種別は病名と 17 種のオーダー(処方・注射・検体検査・細菌検査・病理検査・放射線検査・生理検査・内視鏡・処置・手術・食事・
  輸血・リハビリ・栄養指導・服薬指導・指導・管理料・他科依頼・看護指示)。看護指示と食事は入院向けなので外来の患者に適用すると注意が出ます。
  食事はセットから出しても前の食事を終わらせません(食事タブで終えます)。セット・パスから出す食事にも、
  適用時点の有効な食物アレルギーを写します(`docs/meal-order-design.md` §2.12)。手術はセットから出すと手術室の重なり確認を
  通らないので、登録後に手術カレンダーで確かめてください。
- **サンプル**: `db:seed` で院内共通に「外来」(高血圧症(初診)・2型糖尿病(定期)・脂質異常症・急性胃腸炎・急性上気道炎)と
  「入院」(入院時検査・術前検査・市中肺炎(入院))の 8 セットが入ります(`db/seed_data/order_sets.json`)。
  values は薬剤・用法・病名などのマスタ行の写しを含むフォーム値そのもので、同じ code のセットは上書きしません。

## 化学療法レジメンマスタ

化学療法の治療計画の雛形(レジメン)を施設共通のマスタとして登録し、患者に適用して注射・処方オーダーに展開します。
詳細は `docs/chemo-regimen-design.md`。

- **入口**: 「マスタメンテ > 化学療法 > レジメン」(`/regimens`)。一覧から行を選ぶと 1 レジメン 1 ページの編集画面(`/regimens/:id`)。
- **編集画面の目次**: 左に目次(区画と、投与内容の下にステップ)を出し、押すとその位置へ移動します。スクロールに合わせていま見ている区画・ステップを強調します。
- **持ち方**: backend の `master_regimens` と子テーブル(適応疾患・投与ステップ・薬剤・検査基準・副作用)。オーダーセットのような
  持ち主の階層は持たず、診療科と適応疾患(病名マスタ)を分類属性に、承認状態(下書き / 承認済 / 廃止)・承認日・承認者を持ちます。
- **投与ステップ**: 注射オーダーの RP(混注)に相当する単位で、順序・相対日(Day 1, 8, 15 …)・点滴 / ワンショット / 内服・経路・手技・
  ライン・点滴時間・器材を持ち、その中に薬剤(種類・算出基準(体表面積 / 体重 / AUC / 固定量 / 製剤単位)・基準値・上限値)を並べます。
  1 クール = 投与期間 + 休薬期間で、編集画面の Day 表でどの日に何が入るかを確認できます。
- **API**: `GET/POST /master/regimens`、`GET/PATCH/DELETE /master/regimens/:id`(id でもレジメンコードでも可)、`POST /master/regimens/:id/copy`。
  本体と子を 1 リクエストで読み書きし、子は送った種別だけ配列で丸ごと置換します。詳細は薬剤名・用法をマスタから解決して返します。
- **レジメンオーダー(患者への適用)**: カルテ右ペインの「化学療法」で承認済のレジメンを選び、開始日(Day 1)と体格(身長・体重 →
  体表面積)から投与量を出して、クール単位で登録します。適用 1 件はヘッダの `ServiceRequest`(`order-type|chemo-regimen`、
  `intent = plan`)で、日ごとの投与は**通常の注射・処方オーダー**(`requisition` と `regimen-order` 拡張でどのクールの何日目かを持つ)
  として登録されるので、注射一覧・払出・実施入力・経過表はそのまま使えます。カルテ左ペインの「化学療法」タブが月の暦で
  投与スケジュールを出し、適用が複数あればタブで切り替えます。移動・中止・次クールの登録・レジメンの中止は右ペインで行います。

## クリニカルパス定義マスタ

疾患・術式ごとの入院診療の標準計画(クリニカルパス)を施設共通のマスタとして登録します。基本仕様は JAMI・JSCP の
ePath(ePath R4 実装ガイド)の概念に準じます。患者への適用と日次評価(カルテの「パス」タブ)まで実装済みで、
ePath 形式の入出力が次の段階です。詳細は `docs/clinical-pathway-design.md`。

- **入口**: 「マスタメンテ > クリニカルパス > パス定義」(`/pathways`)。一覧から行を選ぶと 1 パス 1 ページの編集画面(`/pathways/:id`)。
- **編集画面の目次**: テンプレート編集と同じく左に目次(基本情報・対象病名・病日・概要表・運用、病日の下にフェーズと病日)を出し、
  押すとその位置へ移動します。スクロールに合わせていま見ている区画・病日を強調します。
- **持ち方**: backend の `master_pathways` と子テーブル(対象病名・病日・OAT ユニット・観察項目・タスク)。レジメンと同じ承認制
  (下書き / 承認済 / 廃止、承認日・承認者、承認済は凍結して複製で改訂)で、診療科と対象病名(病名マスタ)を分類属性に持ちます。
- **病日と OAT ユニット**: 入院日を 1、入院前日を -1 とする病日ごとに、OAT ユニット(1 つのアウトカム + それを判定する観察項目 +
  実施するタスク)を並べます。アウトカム・観察項目は BOM(Basic Outcome Master®)または施設ローカルのコードを任意で持ち、
  タスクは ePath のタスク分類(治療 / 検査 / 食事 / 観察項目 / ケア項目 / 教育・指導・説明 / 活動・安静度 / 医療文書と中分類)を持ちます。
  OAT ユニット・観察項目・タスクの識別子(uuid)は適用後まで持ち越すもので、編集で行を作り直しても変わりません。
- **続きと分割**: 同じ識別子のアウトカム・観察項目・タスクを複数の病日に置くと「続き」になり、パスシートでは 1 行に並びます。
  概要表のセルを押して続きを足す・外すことができ、名前や雛形は続き全体で揃います(適正値は日ごと)。続く病日の看護指示は
  1 件のオーダーにまとまり、食事・安静度は次の食事・安静度の直前で終わります。手術当日などは「分割」でステップ(術前 / 術後)に分けられます。
- **パスタブ**: 適用したパスは「日めくり」(1 病日ずつ達成状態・実績・タスクの実施をまとめて記録)と「オーバービュー」(紙のパスシートと同じ格子。既定)で見ます。
  オーバービューの見出し帯に未評価・バリアンス・未実施の件数を出し、押すとその行に絞ります。看護観察に結んだ観察項目には、その日の経過表の値を候補として出します。
  予定外の追加・日程の変更・終了・適用の取り消しは見出し帯のケバブから行います。
- **指示簿のパスのタスク**: 病棟の指示簿の看護指示の表の下に、その病棟の患者の、その日の病日に置かれたオーダーを持たないタスク
  (観察・説明・文書など)を患者ごとに出し、チェックで実施にできます(未指示受けのビューでは出しません)。
- **入院患者一覧・患者ヘッダのパス**: 入院患者一覧の「パス」列と患者ヘッダに、進行中のパス名を出します。パス名からパスタブを開きます。
- **バリアンスの通知**: 重要アウトカム(★)を「未達成」と記録すると、入院の主治医あてに「パスのバリアンス」の通知(強度は注意)が
  届きます。通知の「カルテ」からパスタブのその病日の日めくりを開きます。達成・未評価に直すと未対応の通知は取り下げます。
- **カルテのパス評価**: 記載(S/O/A/P・自由記載・コメント)のあるアウトカムの評価は、カルテのタイムラインに「パス評価」のカードとして
  記録日時の日に出ます。本文にパス名と病日、メニューの「パス表示」でパスタブのその病日の日めくりを開きます。
- **オーダー雛形**: タスクにはオーダーセットのエントリと同じ形(種別 + フォーム値)の雛形を任意で付けられます。既存のオーダー登録
  フォーム(オーダーセットと同じ 17 種。看護指示・食事・手術・輸血なども含む)をモーダルで開いて内容を決め、適用時に入院日 + (病日 − 1) の
  日付で展開する材料になります。種別の既定はタスク分類から決まります(ケア項目 → 看護指示、食事 → 食事オーダー など)。
  雛形の無いタスクはチェックリスト項目です。
- **概要表**: 編集画面の末尾に、列 = 病日、行 = アウトカムと大分類ごとのタスクの読み取り専用の表を出します。
- **プレビュー**: 編集画面の見出しの「プレビュー」で、患者に適用したときのパスシート(パスタブのオーバービューと同じ並び)を
  モーダルで見られます。保存前の内容もそのまま映り、入院日を選ぶと実日付が入ります。フェーズを分けたパスは分岐の先を選んで
  経路を切り替えられます(既定は標準の経路)。オーダー雛形を持つタスクのセルには種別が出て、押すと雛形の中身を
  読み取り専用のモーダルで開きます。読むだけで、評価や実施の記録はできません。
  カルテ右ペインの適用フォームにも「プレビュー」があり、フォームの入院日(次のフェーズでは開始日)から始まるシートを
  適用前に確かめられます。次のフェーズでは、そのフェーズから先の経路を出します。
- **フェーズと分岐**: 病日をフェーズ(連続する病日のまとまり)に分け、フェーズごとに「次に進めるフェーズ」の候補と選ぶ目安を登録できます
  (「＋ フェーズ」、フェーズ見出しのメニュー「分岐編集」)。患者への適用はフェーズ単位で、最初は開始フェーズだけを登録し、
  パスタブの見出しのアイコン「次のフェーズを適用」で候補から選んで進めます(開始日は前のフェーズの翌日が既定)。選び間違えたらケバブの「フェーズの取り消し」。
  フェーズが 1 つのパスは今まで通り一括で適用されます。サンプルは 900005(市中肺炎・3 日目に効果判定で分岐)。
- **API**: `GET/POST /master/pathways`、`GET/PATCH/DELETE /master/pathways/:id`(id でもパスコードでも可)、`POST /master/pathways/:id/copy`。
  本体と子を 1 リクエストで読み書きし、子は送った種別だけ配列で丸ごと置換します。
- **サンプル**: `db/seed_data/pathways/*.json` の 4 件(900001 腹腔鏡下胆嚢摘出術 4 泊 5 日、900002 内視鏡的大腸ポリープ切除術 1 泊 2 日、
  900003 鼠径ヘルニア根治術 2 泊 3 日、900004 市中肺炎 7 日間)を `db:seed` で下書きとして投入します。900001 は
  タスク 53 件のうち 32 件に 13 種別のオーダー雛形(処方・注射・検体検査・放射線検査・生理検査・病理検査・処置・手術・輸血・
  食事・看護指示・他科依頼・栄養指導・服薬指導)が入っているので、承認して患者に適用すると病日ごとの日付でオーダーがまとめて立ちます。
