# 病棟・入院

## 病棟・病室・ベッド（Location）

入院患者を「どこに寝かせているか」で扱うための場所マスタです。マスタメンテ > 共通 > **病棟・病室**
（`/wards`）から登録します。診察室・撮影室（`/locations`）と同じ `Location` ですが、階層を持ち使う場面も
違うので画面を分けています。

### 3 階層の持ち方

`Location` を `partOf` で 3 段に積みます。

| 階層 | `physicalType` | `type` | `partOf` | `name` |
| --- | --- | --- | --- | --- |
| 病棟 | `wa`（Ward） | v3-RoleCode `HU`（病棟） | なし | 東3階病棟 |
| 病室 | `ro`（Room） | 区分（下記） | 病棟 | 301号室 |
| ベッド | `bd`（Bed） | なし | 病室 | `1`（番号のみ） |

病室の**区分**は該当する標準コードが無いのでローカル CodeSystem を建てています。

```
system : http://fhir-client.local/CodeSystem/room-class
code   : general（一般室） / private（個室） / special（特別室）
         icu（集中治療室） / hcu（高度治療室） / ccu（循環器疾患集中治療室） / scu（脳卒中集中治療室）
```

区分は `ROOM_CLASS_OPTIONS`（`frontend/src/fhir/wardHelpers.ts`）の定数配列なので、増やすときはここに
1 行足すだけです。

区分を `type[0]` に入れているのは、上流が `type` の索引に**最初の coding の code だけ**を採るためです。
これで病棟一覧の `type=HU` 検索に病室が混ざりません。

### ベッドの扱い

**ベッドは病室ごとに 1 件ずつ `Location` として作ります。** 病室の登録・編集画面で「ベッド数」を入れると、
その数に合うよう配下のベッドを自動で増減します（1 つの transaction Bundle で病室と一緒に書くので、
病室だけ保存されてベッドが中途半端に残ることはありません）。数を減らすと**番号の大きいベッドから**消えます。

- ベッドの `name` は病室内の**番号だけ**（`1`, `2`, …）です。「301号室 ベッド1」のような表示名は病室名と
  合成して作ります。名前に病室名を含めると、病室名を変えるたびに配下のベッドを全部書き換えることに
  なるためです。
- ベッド数は病室リソースには持たせず、**配下のベッドの件数から数えます**。数と実体を二重に持つと必ず
  どこかでずれるので、実体だけを正とします。
- 一覧の「病室数」「ベッド数」は `_revinclude=Location:partof` で子ごと取って数えています。`_revinclude`
  の結果は `_count` の対象外なので、子が何件あっても取りこぼしません。

ベッドに患者を割り当てる（入院）のは入院患者一覧です。下の「入院患者一覧（Encounter）」を参照してください。

### オーダーに焼き付ける入院病棟（`order-ward` 拡張）

部門業務の各種一覧（検体検査・放射線検査・生理検査・内視鏡・処置・処方）は「入院病棟」の列とフィルタを持ちます。値は
オーダーを登録した時点の病棟で、`ServiceRequest` のローカル拡張
`http://fhir-client.local/StructureDefinition/order-ward` に
`valueReference { reference: "Location/<病棟>", display: "東3階病棟" }` として持たせます
（依頼科の `order-department` と同じ持ち方。入外区分を `category` に焼き付けているのと同じ考え方です）。

- **一覧から入院を引き直さないため**です。入院は `Encounter` にあり、`Encounter.location[0]` が
  指すのはベッドなので、病棟名を出すには 1 患者あたり Encounter 検索 1 回 + `partOf` を辿る
  Location 検索 1 回が要ります。1 ページ 100 行の一覧でこれをやると 100〜200 リクエストになります。
  オーダー側に焼き付けておけば、一覧は**追加のリクエスト 0** で病棟名を出せます。
- 書き込み口はオーダー 8 種別（処方・注射・検体検査・放射線検査・生理検査・内視鏡・処置・細菌検査）が共通で通る
  `applyOrderContext` 1 箇所です。病棟は `useDefaultOrderSetting`（入外区分の初期値を決めるために
  すでに入院を引いている）の戻り値から取るので、**オーダー登録側の追加リクエストも 0** です。
- **入外区分が「入院」のときだけ**付けます。入院中の患者に手で「外来」を選んで出したオーダーには
  付きません（一覧の区分列と病棟列が食い違わないように）。
- **スナップショットなので転棟しても書き換わりません**。オーダーを編集して保存し直しても、
  `orderRequester`(`fhir/orderHeader.ts`)が読み戻してそのまま渡すため登録時点の病棟が残ります
  （依頼科・依頼医師を引き継ぐのと同じ扱い）。
- この拡張が入る前に登録したオーダーは病棟を持たないので、一覧では `-` になります。
  一覧の病棟セレクトの選択肢は、読み込んだ 1 日ぶんのオーダーに実際に出てくる病棟だけです
  （拡張が `display` を持つので、病棟マスタを引く必要がありません）。
- 絞り込みは他のフィルタと同じくクライアント側です。上流で絞りたくなったら、`Observation` の
  `problem`（`element_match` 付きの reference 検索パラメータ）と同じ形で `ServiceRequest` に
  `ward` を足せます（マイグレーション不要）。

### 削除

- **病棟**は配下に病室があると削除できません（上流に参照整合性が無いので、削除前に
  `partof` で子の有無を確かめています）。先に病室をすべて削除してください。
- **病室**は配下のベッドごと削除します（確認ダイアログにベッド数を出します）。

### 診察室・撮影室（`/locations`）との分け方

同じ `Location` なので、放っておくと診察室の一覧やセレクトに病棟・病室・ベッドが混ざります。
上流の token 検索に `:not` が無いため「除く」ではなく、**診察室の種別（`LOCATION_TYPE_OPTIONS` の
コード）だけを挙げて OR で引く**ことで分けています。取得後にクライアント側で落とすやり方だと
`total` とページ内件数がずれるためです。

この都合で、診察室・撮影室の**種別は必須**です（未設定だと一覧に出てきません）。

## 入院患者一覧（Encounter）

患者一覧メニュー > **入院患者一覧**（`/inpatients`）。病棟を選ぶと、その病棟の病室・ベッドを
1 行 1 床で並べます。埋まっている床には入院中の患者を、空いている床には「患者選択」を出します。

- **注意のピクトグラム**: どのタブでも患者氏名の後ろに、外来患者一覧と同じ注意のピクトグラム
  （注意区分・アレルギー・感染症）を並べます。表示中のタブの患者ぶんをまとめて引きます。

- **表示項目変更**: 「入院患者」タブの見出しのケバブメニューから開き、「パス」「DPC」「NEWS2」の列を表示・非表示に
  切り替えます。パス・DPC は既定で表示、NEWS2 は既定で非表示で、切り替えは端末ごとに覚えます（localStorage）。
  隠した列のデータは読み込みません。
- **NEWS2 列**: 直近 3 日の最新の NEWS2 の点数を区分の色で出します(中は赤字、高は赤地)。欠測のある暫定値は「*」を
  添え、点数にマウスを載せると区分と測定日時が出ます(`docs/early-warning-design.md`)。
- **DPC 列**: 入院の今の診断群分類（有効な決定のうち最新。無ければ「未決定」）と、その下に期間Ⅱの末日を出します
  （DPC患者一覧と同じく、超過は日数つき、末日まで 2 日以内は印）。押すとカルテの DPC（診断群分類）を開きます。

### 入院の持ち方

入院は `Encounter` 1 件で「その患者が今どのベッドに居るか」を表します。

| 画面の項目 | Encounter の要素 |
| --- | --- |
| （入院中であること） | `status` = `in-progress`、`class` = v3-ActCode の `IMP` |
| 退院 | `status` = `finished` + `period.end`（退院日）、`location[0].status` = `completed` |
| 入院取消（誤登録） | `status` = `entered-in-error`（退院ではないので `period.end` は付けない） |
| 患者氏名・生年月日・性別 | `subject`（表示は `_include` で引いた Patient から）。カナは列を分けず「氏名（カナ）」と併記する |
| 病室・ベッド | `location[0].location` = **ベッドの Location**（病室・病棟は `partOf` で辿れる） |
| 診療科 | `serviceProvider` = 診療科の Organization |
| 主治医 | `participant` の種別 `ATND`（v3-ParticipationType の attender） |
| 担当看護師（複数可） | `participant` の種別 `nurse`（ローカル CodeSystem `http://fhir-client.local/CodeSystem/encounter-participant-role`。看護師を表すコードが ParticipationType に無いため） |
| 入院日 | `period.start`（時刻を持たない日付のみ） |
| 入院日数 | 保存しない。`period.start` から表示している日までを、入院日を 1 日目として数える（病棟マップの「入院 N 日目」と同じ） |
| 特記事項 | ローカル拡張 `http://fhir-client.local/StructureDefinition/encounter-note`（`valueString`） |

- **`Encounter.class` は Coding 単体**です（R4 では CodeableConcept ではない）。
- 主治医・担当看護師・特記事項は未入力なら要素ごと付けません。主治医と担当看護師は同じ
  `participant[]` に種別違いで並びます。
- 退院・入院取消はリソースを消さず `status` で残します。いつ誰が登録した記録なのかを
  後から追えるようにするためです。どちらも `in-progress` ではなくなるので一覧からは外れます。
- 特記事項に R4 の `Encounter` に無い要素（`note` など）を使っていないのは、プロファイル検証を
  将来 enforce にしたときに弾かれるためです。拡張なら中身を見られません。

### 取得のしかた

病棟で絞らず**院内の入院をすべて取ってから**ベッド id で突き合わせます
（`Encounter?status=in-progress,finished&class=IMP&_include=Encounter:subject`）。病棟のベッド id を
並べた `location=...` でも引けますが、ベッドの数だけ URL が伸びます。入院中の件数はベッド総数が
上限で高が知れているうえ、全部持っていれば「この患者は既に別の病棟に入院している」の判定も
追加のリクエスト無しでできます。

病室・ベッドの側は病棟マスタをそのまま使います（`partof` + `_revinclude=Location:partof` で
1 往復）。同じベッドに入院中が複数あったら、入院日（同日なら更新時刻）が新しいものを表示します。

**日付の絞り込み**は「その日にベッドを使っていた人」（入院日 ≦ 選択日 ≦ 退院日）なので、退院済み
（`finished`）も対象に含めます。上流の `date` は `eq` が「期間を完全に含む」で重なりではないため、
重なりは `ge` と `le` の AND で表します。

```
date=ge<選択日>   退院していない、または選択日以降に退院した
date=le<選択日>   選択日までに入院している
```

取り消した入院（`entered-in-error`）は在院ではないので `status` で外しています。

### 画面のふるまい

- 選んだ病棟と日付は URL の `?ward=` / `?date=` に持ちます。カルテへ渡す戻り先は検索文字列を
  含むので、カルテから「← 戻る」で同じ病棟・同じ日が開きます。
- **日付を選ぶとその日の在院状況になります。** `<` `>` で 1 日ずつ送れ、「今日」で当日に戻ります。
  日付は「いつの状態を見るか」なので、診療科・主治医・担当看護師の絞り込みとは別扱いです
  （日付を変えても空床は出します）。過去の日を見ているときは、入院登録の入院日の既定も
  その日になります（今日で登録すると登録した本人がその画面に出てこないため）。
- 病棟が未指定なら先頭の病棟を自動で開きます（履歴は汚さず replace で書き換え）。
- 「患者選択」→ 患者を検索して選ぶ → 診療科（必須）・主治医・担当看護師（複数可）・入院日（既定は今日）・特記事項で登録。
- 担当看護師はセレクトで 1 人ずつ選んで「追加」し、選んだ人は下に × 付きで並びます。選択済みの人は
  セレクトから消えるので二重に足せません。`select multiple` を使わないのは、Ctrl 押しながらの
  クリックが要って選び方が見て分からないためです。
- 選んだ患者が既にどこかの床に居る場合は確認を出しますが、転床やデータ修正の途中ということも
  あるので登録自体は止めません。
- 入院中の行の操作メニュー（⋮）に **退院** と **入院取消** があります。退院は退院日を聞く
  （既定は今日。入院日より前の日付は弾きます）、入院取消は誤登録向けで確認だけです。
- 同じメニューの **担当者変更** で、入院の主治医と担当看護師を差し替えます（participant の ATND と
  担当看護師だけを入れ替え、ほかの participant は残します）。選択肢は所属ロールの職種で絞り、主治医は
  医師・歯科医師、担当看護師は看護師・保健師・助産師です。いま担当に入っているのに職種が合わない人は、
  開いただけで外れないよう入院に記録された氏名で選択肢に残します。
- **診療科・主治医・担当看護師で絞り込めます。** 選択肢は院内の入院中の Encounter から作るので、実際に
  在院している科・医師しか並びません（病棟を切り替えても選択が消えないよう、表示中の病棟では
  なく全病棟ぶんを見ています）。絞り込み中は空床を出しません（空床はどちらも持たないので、
  残すと「絞ったのに一覧が変わらない」ように見えるため）。病室セルの rowspan も残った行数で
  数え直します。
- 病室の区分（個室・ICU など）は一覧には出しません。マスタメンテ > 病棟・病室 で見てください。
- 列はどれも折り返しません。入り切らないときは表ごと横スクロールします（折り返すと行の高さが
  変わってベッドの並びが読みにくくなるため）。

### 経過表一括入力

入院患者タブのケバブメニューの「経過表一括入力」(`/inpatients/bulk-vitals?ward=`、`pages/BulkVitalEntryPage.tsx`)で、
病棟の入院中の患者を病室順に並べ、同じ測定日時でバイタル・体重・食事摂取量をまとめて入れます。
病棟の検温のように、何人ぶんも続けて入れるときのための画面です(1 人ずつはカルテの右ペインの
バイタルと、経過表の食事の枠)。

- 出す列は施設設定の「経過表一括入力の列」(`bulk_vital_entry.items`)で選び、並べた順に出します。
  候補は血圧・体温・脈拍・SpO2・酸素流量・呼吸数・意識(JCS)・体重・食事摂取量で、1 列は残します。
  既定は酸素流量と意識を除いた 7 列です。
- 早期警告スコアが有効なら、右ペインと同じく患者ごとに NEWS2 を同梱し、主治医あての通知を作り直します。
- 値を入れた行だけを登録します。片方だけの血圧は行にエラーを出し、1 件でもあれば登録できません。
  しきい値(施設設定の「バイタルの異常値」)を外れた値は、入力中から経過表と同じ H/L の色になります。
- 記録の形は 1 人ずつ入れたときと同じです(`fhir/bulkVitalHelpers.ts`)。バイタルは
  `buildVitalObservations` で患者ごとに 1 回の測定として束ね、入院(`encounter`)と測定者
  (`performer` = ログイン中の医療従事者)を付けます。**体重だけ入れたときは、その患者の最新の
  身長で BMI を作ります**(身長は病棟の患者ぶんを 1 回の検索で引きます)。
- 食事摂取量は測定日の、画面で選んだ時間帯(朝・昼・夕。既定は測定時刻に近い食事)の 1 食です。
  枠の判定は経過表と同じで(`buildMealIntakeRows`)、食事オーダーの無い食事・食止め・欠食は
  「-」になります。記録済みの値を初期値に出し、**変えた患者だけを書きます**(空にすれば消す)。
  食事オーダーと記録は欠けると上書きや二重登録になるので、読み切れないときは止めます(`complete`)。
- 全員ぶんを **1 つの transaction** で送ります(上流のレート制限 300 件/分のため、患者ごとには送りません)。

## 病棟マップ（master_ward_maps + Encounter）

入院患者一覧の別の見え方。病棟の間取り(設備・病室・ベッドの配置)の上に、その日の
入院患者をベッドごとに出す。設計は `docs/ward-map-design.md`。

### レイアウトの持ち方

- backend の `master_ward_maps` に 1 病棟 1 行。`ward_location_id`(FHIR Location の id、
  一意)・`ward_name`(表示用の写し)・`layout`(jsonb)・`note`。API は
  `/master/ward_maps`(index は `?ward_location_id=` で絞れる。show/create/update/destroy)。
- `layout` はキャンバスの大きさ(マス数)・1 マスの px・オブジェクト配列。オブジェクトは
  `fixture`(設備。種別・任意の表示名・回転・色)/ `room`(病室 Location の id)/
  `bed`(ベッド Location の id と所属病室)。座標・大きさはマス数の整数。形は backend
  (`Master::WardMap#layout_shape`)と frontend(`normalizeLayout`)の両方が守る。
- ベッドが何床あるかは Location だけが正。レイアウトは「どこに描くか」しか持たず、消えた
  Location は欠番、置いていない病室・ベッドは未配置として扱う。

### 画面

- **病棟マップ**(`/ward-map?ward=&date=`、患者一覧メニュー)。病棟と日付を選ぶと、
  レイアウトの上に入院患者のカード(番号・患者番号・氏名・性別・年齢・診療科 / 主治医・
  入院日数・注意区分 / アレルギー / 感染症のピクトグラム・退院予定 / 転棟予定 / 外出泊中の
  札)が出る。カードを押すとカルテ(戻り先を保つ)。ケバブから転室・転床 / 外出泊 /
  転科・転棟予定 / 退院予定 / 退院、空床からは入院登録。マップが未作成の病棟は病室と
  ベッドを機械的に並べて出す(保存はしない)。
- **転床(移動プラン)**。今日の表示では患者カードを掴んで空床や別の患者の床へ運べる。
  落としても書き込まず「保留中の移動」に積む(占有床へ落とせば入れ替え)。
  「一時退避」に置けば床を空けられるが、退避のままでは確定できない。「転床確定」で
  転床日を決め、直前に入院を引き直して他端末の変更が無いことを確かめてから、全件を
  1 つの transaction で書く。病棟・日付を変えるとプランは捨てる。
- **本日の入院予定**。この病棟宛て(または病棟未定)の当日予定を並べ、空床へ落とすと
  入院実施モーダルがその床を選んだ状態で開く。
- **病棟マップ編集**(`/wards/:wardId/map/edit`、病棟一覧の行メニュー「マップ編集」と
  マップの「マップ編集」)。左に設備と未配置の病室・ベッド、中央にキャンバス、右に
  キャンバスの大きさと選んだオブジェクトのプロパティ。掴んで移動・縁でリサイズ
  (設備と病室)・回転・複製(設備)・削除・矢印キーで 1 マス(Shift で 5)・
  Ctrl+Z / Ctrl+Y・Ctrl+D・R・空白を掴んでスクロール・Ctrl+ホイールで拡大縮小。
  「自動配置」は病室とベッドを機械的に並べ直す、「整列」は病室内のベッドを並べ直す。
  保存はレイアウト全体を PATCH。未保存の変更はリロード・タブを閉じる前に止める
  (画面内のリンクでは止まらない)。

## ベッドスケジュール・病床状況・入退院文書

病床の運用(ベッドコントロール)と入退院の文書の督促のための 3 画面です。どれも入院(`Encounter`)と病棟・病室・
ベッド(`Location`)だけから組み立て、専用のデータは持ちません(入退院文書の対象と期限だけ施設設定)。設計は
`docs/bed-management-design.md`。入口はヘッダーの「患者一覧」(ベッドスケジュール・病床状況)と「診療業務」
(入退院文書)、入院患者一覧の入院患者タブのケバブです。

- **ベッドスケジュール**(`/bed-schedule?ward=&from=&days=`): 病棟のベッド × 日付(2 週間・4 週間)の格子に入院の帯を置きます。
  - 帯は入院の床の履歴(`Encounter.location`)から起こすので、転床・転棟した入院は床ごとに帯が分かれます
    (移動した床は移動の前日まで、退院した床は退院日まで)。
  - 実績は塗り、続いている入院の明日から先は薄く(退院予定があればその日で止め、無ければ右端まで続ける。
    退院予定日を過ぎても在院していれば今日まで)、予定は点線の枠です。予定の帯は入院予定(ベッドまで決まっているもの。
    名前に「入予」)と転科・転棟予定の移動先(ベッドまで決まっているもの。「転予」)。ベッドの決まっていない
    入院予定は最下段の「ベッド未定」に予定日の列で並べます。
  - 同じベッドで帯が重なるとき(退院前の患者と入院予定など)は段を分けて積みます。今日は見出しの印と縦の点線。
  - 帯の吹き出しに入院日〜退院日(予定)・診療科・主治医、押すとその患者のカルテ。休止中(ベッドか病室が有効でない)の
    ベッドは薄く「休止」を添えます。
- **病床状況**(`/bed-status?date=&period=`): 病棟ごとに、病床数・休止・在院(その日の 24 時)・稼働率(在院 ÷ 使えるベッド)、
  空床(病室の区分別)、その日の入院・退院・転入・転出、翌日の入院予定・退院予定、期間(直近 30 日・90 日)の
  病床利用率と平均在院日数を並べ、病棟が 2 つ以上なら合計の行を出します。
  - 在院患者延日数は夜の数(入院日を数え退院日は数えない)、病床利用率 = 延日数 ÷ (使えるベッド × 日数)、
    平均在院日数 = 延日数 ÷ ((新入棟 + 新退棟) ÷ 2)。病棟の新入棟・新退棟は転入・転出を含み、合計の行は
    病院全体として入院と退院だけで数えます。届出の様式の計算(除外する患者など)とは別の簡易計算です。
  - 同じ病棟の中の転床は転出入に数えません。病棟名を押すとその病棟のベッドスケジュール。
- **入退院文書**(`/admission-documents?ward=&from=`): 入院中と、指定日以降に退院した入院を並べ、入院診療計画書・
  栄養スクリーニング・栄養管理計画書・褥瘡リスク評価・褥瘡対策計画書・退院時サマリー・看護サマリー(区分「退院」)の
  作成状況と期限を出します。
  病棟・診療科・主治医・状態(未作成あり / 期限超過あり)で絞れます。
  - 期限は入院診療計画書が入院日 + N 日(既定 7)、栄養スクリーニングが入院日 + N 日(既定 3)、栄養管理計画書が
    入院日 + N 日(既定 7)、褥瘡リスク評価が入院日 + N 日(既定 1)、褥瘡対策計画書が入院日 + N 日(既定 7)、
    退院時サマリーが退院日 + 「文書作成の督促」の日数、看護サマリーが退院日 + N 日(既定 7)。
    退院系の文書は退院するまで「退院後」と出します(書き始めていれば状態を出す)。
  - 状態は、テンプレートで書く文書(入院診療計画書・栄養スクリーニング・栄養管理計画書)が回答の状態(完了 → 作成済)、
    退院時サマリーが確定 / 作成中、看護サマリーが作成中・承認待ち・承認済(承認待ちも作成済に数える)。
    期限を過ぎて作成済でないものは赤。
  - 栄養管理計画書は、完了した栄養スクリーニングか入院診療計画書の「特別な栄養管理の必要性」が有の入院だけが対象です。
    どちらかが有なら未作成、無だけなら「不要」、まだ答えていなければ「判定前」。作成済でも、最新の計画書の
    「栄養状態の再評価の時期」を過ぎて在院していれば「再評価」と期限を赤で出し、押すと新しい計画書を書き始めます
    (設計は `docs/nutrition-care-plan-design.md`)。
  - 褥瘡対策計画書は、確定した最新の褥瘡リスク評価(既定の雛形は看護プロファイルの区画「褥瘡リスク」)で計画が要る入院
    だけが対象です。現在の褥瘡がありなら要、日常生活自立度が J・A なら不要、それ以外は危険因子(あり・できない)が 1 つでも
    あれば要。不要・判定前・再評価(「評価の予定日」を過ぎて在院)の出し方は栄養管理計画書と同じです。計画書を書き始めると、
    同じ入院の褥瘡リスクの回答が褥瘡の有無・日常生活自立度・危険因子の初期値に入ります(設計は `docs/pressure-ulcer-plan-design.md`)。
  - セルを押すとカルテを開き、未作成なら右ペインでその入院の登録を始めます(テンプレートで書く文書は施設設定の
    テンプレートを選んだ状態で、回答に入院を持たせる。退院時サマリー・看護サマリーは既存の `?open=` の入口)。
    テンプレートで書く文書の作成済・作成中のセルは、その回答を右ペインで開きます(入院に結び付いた回答はカルテの時系列に出ない)。
  - テンプレートの回答は入院を持てばそれで、持たなければ記入日が入院期間(入院日の 7 日前から)に入るもので当てます。
  - 対象と期限は施設設定「文書作成の督促」の「看護サマリーの期限」と、入院診療計画書・栄養スクリーニング・
    栄養管理計画書・褥瘡リスク評価・褥瘡対策計画書それぞれの「テンプレート」「期限」(backend の `admission_documents`)。テンプレートは既定で未設定で、
    未設定なら列を出しません(同梱の雛形は `docs/report-mappings/admission-plan-01.*`・`nutrition-screening-01.*`・
    `nutrition-plan-01.*`・`nursing-profile-pressure-ulcer-01.*`・`pressure-ulcer-plan-01.*`)。

## 食事一覧（給食部門）

- **入口**: 部門業務 > 栄養部門 > 食事一覧(`/meal-worklist`)。日付と病棟(既定はすべて)を選びます。
- **患者別**: その日に在院した患者ごとに、朝・昼・夕の食種と主食(欠食は「欠食」)、副食形態・塩分制限・
  食物アレルギー・欠食理由・コメントを並べます。その食事から食事が変わった欄には「変更」の印が付き、
  食事オーダーの無い食事は「—」です。「表示」で「変更あり」「オーダーなし」に絞れます。患者名からカルテの食事タブを開き、行を押すと他の部門一覧と同じく右に患者プロファイルのドロワーが出ます。
- **食数集計**: 食種ごと・主食ごとに朝・昼・夕の食数を数え、食種の表の下に計・欠食・オーダーなしを出します。
- 病棟は入院のいまのベッドで決めるので、転棟した患者はいまの病棟に出ます。退院済みの患者は出ません
  (`docs/meal-order-design.md` §5.2)。

## 栄養管理（栄養部門）

- **入口**: 部門業務 > 栄養部門 > 栄養管理(`/nutrition-management`)。病棟と対象(すべて・特別な栄養管理あり・低栄養(GLIM)・
  未対応あり)で絞れます。
- 今日の入院患者ごとに、栄養スクリーニングの状況、確定した最新のスクリーニングの MUST(点とリスク)・GLIM(判定と重症度)・SGA、
  特別な栄養管理の必要性、栄養管理計画書の状況、いまの食事(食種・主食・副食形態・塩分制限)を並べます。GLIM で低栄養なら赤字です。
- スクリーニングと計画書のセルは入退院文書と同じ判定・期限で、押すとカルテで登録を始めるか書いた文書を開きます。
  「未対応あり」は未作成・作成中・期限超過のどれかがある患者です。
- 一覧の上に、病棟で絞った在院数と、スクリーニング実施・低栄養・特別な栄養管理ありの人数と割合(在院数に対する)、
  計画書作成済の人数と割合(特別な栄養管理ありに対する)を出します。
- 対象のテンプレートは施設設定「文書作成の督促」の栄養スクリーニング・栄養管理計画書(`docs/nutrition-care-plan-design.md` §7)。
