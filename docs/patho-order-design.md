# JAHIS規約をベースとした病理検査（組織診・細胞診）オーダーとレポートの設計

設計日: 2026-08-29。JAHIS の 2 つの規約を主要な拠り所とする。

- **JAHIS 病理・臨床細胞データ交換規約 Ver.2.1C**（22-009）… オーダー（依頼）側
- **JAHIS 病理診断レポート構造化記述規約 Ver.2.0**（20-004）… レポート（報告）側
- **JAHIS 医療情報システムの患者安全ガイド（病理編）Ver.1.0**（22-103）… 診断医・重要度・追加/訂正の別・患者説明（§4.8）

**実装済み（2026-08-29）**。マスタは規約 22-009 付録-3 のサンプルマスタを seed で投入し、
実データで検証済み: 臓器・検査材料 533 件、採取法 23 件（いずれもスキップ 0）。

本文中の区別:
- **［事実］** = 公式規約・リポジトリ内の実装で確認した内容
- **［導出］** = 仕様・既存実装から論理的に導ける内容

- **［決定］** = 設計検討（2026-08-29）でユーザーと合意済みの内容

## 1. スコープ

- 病理検査オーダーのマスタ（`master_patho_*`）とメンテ UI

スコープ外（［決定］）:

- **免疫染色の追加依頼・遺伝子検査**。検査区分の定数に足せば乗る（§8-3）。

## 2. 決定事項と経緯

［決定］設計検討で確定した主要判断:

| 論点 | 決定 | 理由 |
|---|---|---|
| オーダー種別 | **`pathology` 1 つ**。組織診・細胞診・術中迅速はオーダー内の「検査区分」で分ける | 規約 22-009 が同じ枠組みで検査目的群コードにより区分している。部門一覧・カルテカードも 1 本で済む |
| オーダー構造 | **ヘッダ + 検体 ×N の 2 層**。検査項目の層は作らない | 病理の「検査項目」は検査目的群 1 個が実質そのもので、1 オーダーに 1 つしか選ばない（§4.1）。細菌検査の 3 層から 1 段減らす |
| 検体の数 | **1 オーダー = 複数検体**（UI でも展開する） | 多部位の生検（胃前庭部と胃体部を別容器で提出）が病理では普通で、それを 1 件の依頼として出すため。細菌検査が構造だけ残していた層を UI に開いた |
| 検体の採取日時 | v1 は**ヘッダに 1 つ**（採取予定日時）。検体ごとの実採取日はレポート側で持つ | 規約は SPM 単位で持つが、同じ機会に採る検体がほとんど。オーダーは予定、レポートは実績という分担にする（§8-5） |
| マスタ | **臓器・検査材料と採取法の 2 つだけ** DB に置く | 検査区分・検体タイプ・左右・細胞診判定は数個の固定値なのでフロントの定数にする |
| マスタの出所 | 規約 22-009 **付録-3 のサンプルマスタを seed で投入** | 規約 §5.1.1 が「JJ1017 に相当する標準マスタが無いため、このサンプルの採用で個別作成の手間を減らせる」と明記している。取込用の配布ファイルは存在しない |
| レポートの項目立て | 規約 20-004 の**セクション LOINC を Observation.code に直接使う** | 細菌検査のようなローカル result-item を挟むより、規約との対応が読んで分かる |
| 確定と修正 | status で表す。**確定後の編集保存は訂正（`amended`）か追加（`appended`）を毎回選ぶ**（2026-11-01、§4.8） | final のままだと「一度も直していない最終報告」と区別が付かなくなる。患者安全ガイド（病理編）が追加診断と訂正診断を見分けることを求める |
| 削除 | `entered-in-error` にせず **DELETE** | 他オーダー・実施記録と同じ（上流は論理削除なので `_history` で追える） |

## 3. JAHIS 規約の要点

### 3.1 オーダー側（22-009）

［事実］業務フローは「④検査依頼 → ⑥検体到着通知 → ⑦報告書情報通知」。オーダーメッセージ
（OML^O21）は**親子レコード**で、親（`ORC-1: PA`）が検査項目と患者プロファイル、
子（`ORC-1: CH`）が SPM セグメントで検体情報を持つ。

［導出］この親子は、本実装の「ヘッダ ServiceRequest ← basedOn ─ 検体明細」に対応する。

［事実］付録-3 のサンプルマスタ:

| テーブル | 内容 | 件数 | 本実装での扱い |
|---|---|---|---|
| LPATHO001 | 検査目的群 ID（組織診 N000 / 免疫染色 N002 / 術中迅速 N003 / 細胞診 N004 / 遺伝子検査 N005） | 5 群 | フロント定数（N000/N003/N004 のみ採用） |
| LPATHO002 | 検体タイプ（101 細胞診材料 / 201 生検 / 211 手術材料） | 3 | フロント定数 |
| LPATHO003 | 臓器・検査材料（8 桁コード + ICD-10） | 533 | `master_patho_organs`（seed） |
| LPATHO004 | 採取法（擦過・穿刺吸引・生検・EMR・ESD・部分切除 ほか） | 23 | `master_patho_collection_methods`（seed） |

［事実］付帯情報のコメント種別（JHSA 表 010）には、臨床病名（MS3-34）、病理検査目的
（AP-001）、手術室番号（AP-011）、報告希望日（AP-021）、シェーマ（AP-031）、
内視鏡検査報告書（AP-051/052）がある。本実装は臨床経過・報告希望日・手術室番号を採る。

### 3.2 レポート側（20-004）

［事実］一般病理診断レポートのドキュメントコードは LOINC **11526-1**。ボディ部の
セクションは以下（**診断だけが 1..1 必須**、他はすべて任意）:

| セクション | LOINC | 本実装 |
|---|---|---|
| 臨床情報 | — | オーダー側に持ち、レポートには重複させない |
| 検体情報 | 667469-9 | 独立 Specimen ×N（臓器・検体タイプ・実採取日） |
| 肉眼所見 | 22634-0 | Observation（valueString） |
| 顕微鏡所見 | 22635-7 | Observation（valueString） |
| **診断** | **22637-3** | Observation（組織診=valueString / 細胞診=判定+推定病変） |
| 採取法／検体処理法 | 10157-6 | Observation（valueString。追加染色） |

［事実］記述サンプルでは、組織診の診断は取扱い規約・UICC の病期を含む自由文、
細胞診の診断は「判定: 悪性 / 推定病変: Papillary carcinoma」の形。
［提案］これに合わせ、細胞診だけ `valueCodeableConcept`（判定）+ `component`（推定病変）にする。

## 4. FHIR 表現

### 4.1 オーダー（ServiceRequest 2 層）

```
ヘッダ ServiceRequest (category = order-type|pathology + 入外区分)
  ← basedOn ─ 検体明細 ServiceRequest ×N (contained Specimen #specimen)
```

**ヘッダ**（`frontend/src/fhir/pathoOrderHelpers.ts`）:

| 要素 | 内容 |
|---|---|
| `category` | `CodeSystem/order-type` に `pathology` + 入外区分 |
| `code` | 検査区分（`CodeSystem/jahis-patho-exam-category`、LPATHO001 のコード） |
| `occurrenceDateTime` | 採取（予定）日時。**必須**（§4.3） |
| `priority` | routine / urgent（術中迅速を選ぶと urgent を自動セット） |
| `reasonReference` | 対象プロブレム（POMR） |
| 拡張 `patho-clinical-info` | 臨床経過・所見（valueString） |
| 拡張 `patho-report-due` | 報告希望日（valueDate） |
| 拡張 `patho-operating-room` | 手術室番号（valueString。術中迅速のみ） |
| 拡張 `patho-clinical-info-questionnaire-response` | 臨床経過をテンプレートから書いたときの記入内容（valueReference → QuestionnaireResponse） |
| 拡張 `patho-schema-image` | シェーマ（valueAttachment → `Binary/<id>`）。0..* |
| `note[0]` | 依頼コメント |

**検体明細**: `identifier` に検体番号（連番）、`code.text` に臓器名、`contained` の
Specimen（JP_Specimen_Common）に `type`（LPATHO002）/ `collection.bodySite`（LPATHO003 +
左右）/ `collection.method`（LPATHO004）、`note[0]` に補足。
`contained` の Specimen には、検体個数（`collection.quantity`、UCUM `{piece}`）・容器数（拡張
`patho-container-count`、valueInteger、既定 1）・採取日時（`collection.collectedDateTime`、採取を記録したとき）も持つ（§4.9）。

### 4.2 レポート（DiagnosticReport + Observation）

```
DiagnosticReport (code = LOINC 11526-1, status = registered|preliminary|final|amended|appended)
  ├ basedOn  → 病理検査オーダー（ヘッダ）
  ├ specimen → Specimen ×N（臓器・検体タイプ・実採取日）
  └ result   → Observation 群（§3.2 のセクション LOINC）
```

`category` は v2-0074 の **SP**（組織診・術中迅速）/ **CP**（細胞診）+ 入外区分。
診断医は `resultsInterpreter`（最大 3 名、先頭が主たる診断医）、重要度は拡張 `patho-report-importance`（§4.8）。
診療科は他の結果と同じローカル拡張。診断をテンプレートから書いたときは拡張
`patho-diagnosis-response`（valueReference → QuestionnaireResponse）で回答を指す（§4.7）。

### 4.3 日付軸

［決定］ヘッダの `occurrenceDateTime`（採取予定日時）を必須にし、部門一覧はこれで引く
（`dateParam: "occurrence"`）。カルテカードもこの日に出す（`OCCURRENCE_ORDER_TYPES` に追加）。

理由: 検体を採る日が病理部門の作業の起点であること、上流が `occurrenceDateTime` しか
索引しない（Period は索引されない）こと。2026-09-01 に全種別で occurrence = 開始日、
authoredOn = 登録日時に統一したので、細菌検査も検査日を occurrence に書く。

### 4.4 臨床経過のテンプレートとシェーマ

**臨床経過・所見**は自由入力に加えてテンプレート（Questionnaire）から書ける。放射線の
検査目的・特別指示、手術の術前指示と同じ作りで、記入内容の正本は QuestionnaireResponse、
`patho-clinical-info` に入るのはそれを平文化した「人が読むための写し」。テンプレート紐付き
中は欄を直接編集させない（回答と本文が食い違うため）。「解除」で紐付けだけ外せる（文言は残る）。

［導出］回答はオーダー本体と**同じ transaction Bundle** に載せる。先に単独で保存すると
「オーダーを保存しなかったのに回答だけ残る」孤児が出るため。テンプレートを解除して
参照が外れた回答は、同じ transaction で DELETE する。

［決定］**既定テンプレートは持たない**。放射線・内視鏡・生理は検査項目マスタに
`*_template_canonical` を持つが、病理には検査項目マスタが無く（あるのは臓器と採取法）、
検査区分はフロントの定数なので置き場所が無い。依頼医が毎回テンプレートを選ぶ。
区分ごとに既定を持たせたくなったら、検査区分をマスタ化するのが素直（§8-9）。

**シェーマ**（JAHIS コメント種別 AP-031。規約上のデータ型は ED で、依頼メッセージには
JPEG 画像として載る）は、シェーママスタ（`master_schemas`）の臓器図を台紙に選んで
`SchemaPaintModal` で描き、描き込み済みの合成 PNG を `Binary` に保存して
`patho-schema-image` 拡張から参照する。

［決定］テンプレートの項目に台紙を固定する持ち方（手術記録などが採る形）ではなく、
**診療記録と同じ「マスタから台紙を選ぶ」方式**にする。病理はオーダーごとに対象臓器が
変わるため、台紙を固定するとテンプレートが臓器の数だけ要る。多部位の生検があるので
シェーマは複数枚添付できる。

［事実］Binary は本体と同じ transaction に積み、まだ id が無いのでプレースホルダ
（`urn:uuid:`）で指す（上流が実 ID に書き換える）。参照が外れた旧 Binary は**削除しない**
（旧バージョンが参照しており、消すと過去の記録が壊れる。`fhir/schemaImage.ts` を参照）。

［導出］DO（複写）では**テンプレートの紐付けとシェーマを引き継がない**。同じ回答・画像を
2 つのオーダーが指すと、片方を消したときにもう片方が壊れるため。平文の文言だけは残る。

［注意］タイムラインでは、オーダーが参照している回答を単独カードにしない
（`karteTimeline.ts` の `linkedResponseIds` に `pathoOrderResponseIds` を含める）。
入れ忘れると臨床経過がオーダーカードとテンプレートカードで二重に出る。

### 4.5 レポートの画像

［事実］規約 20-004 はレポートを本文セクションだけで定義しており、**画像を規定していない**
（「画像」「シェーマ」「写真」の語がいずれも出てこない）。持ち方は自由設計になる。

［決定］オーダーのシェーマと同じく **Binary + 拡張**（`patho-report-image`、0..*）で持つ。
`DiagnosticReport.media` は `Reference(Media)` を要求するが、Media は上流プロキシの
許可リストに無く（`FhirProxyController::ALLOWED_RESOURCE_TYPES`）、Binary は許可済みのため。

種別と説明を添えるので**複合拡張**にする（手術の輸血準備と同じ形）:

```
extension[patho-report-image]
  extension[kind]  valueCoding  … 肉眼写真 / 切り出し図 / 鏡検写真 / その他
  extension[image] valueAttachment  … contentType, url=Binary/<id>, title=説明
```

入口は 2 つ。**ファイルから添付**（カメラ・スキャナで撮った肉眼写真・鏡検写真。
`normalizeImageFile` で長辺 1600px に縮小）と、**シェーママスタの臓器図に描く**
（切り出し図。オーダーのシェーマと同じ `SchemaPickerModal` → `SchemaPaintModal`）。
詳細表示では種別ごとにまとめて並べる。

［事実］Binary の扱いはオーダーのシェーマと同じ。本体と同じ transaction に積み、
プレースホルダで指す。外した画像の Binary は削除しない（§4.4）。

### 4.6 進捗 Task

`CodeSystem/task-code|patho-exam`。`requested 依頼済 → accepted 受付済（検体受領）→
completed 検査済 / cancelled 中止`。受付は**病理受付の画面でラベルを照合して**進める（§4.11）。一覧の「受付」は
その画面を開くだけで、照合しない受付はケバブの「受付済にする」（検体検査のフォールバックと同じ扱い）。
検査済は一覧の主ボタンで進める。

### 4.7 診断のテンプレート記入（シノプティックレポート、2026-10-25）

組織診・術中迅速の「診断」は自由文に加えてテンプレート（Questionnaire）から書ける。取扱い規約・UICC TNM の
項目を選択肢で記録する**シノプティックレポート**で、同梱テンプレートは固形がん共通 TNM（`PATHO_TNM_01`）と
大腸癌（`PATHO_COLON_01`。`docs/report-mappings/patho-synoptic.md`）。

- 作りは所見レポート（`docs/exam-report-design.md`）の所見・診断と同じ。記入内容の正本は QuestionnaireResponse、
  診断 Observation（22637-3）の `valueString` にはその平文が入る。テンプレート紐付き中は診断欄を直接編集させず、
  「解除」で紐付けだけ外せる（文言は残る）。
- 回答はレポートと**同じ transaction** に積み、レポートの拡張 `patho-diagnosis-response` から指す。保存済みの回答を
  再編集していなければ参照だけ引き継ぐ。解除・細胞診への切替で参照が外れた回答と、レポートの削除では回答も同じ
  transaction で消す（`pathoReportResponseIds`）。
- タイムラインでは、レポートが参照する回答を単独カードにしない（`karteTimeline.ts` の `linkedResponseIds`）。
- **院内がん登録への写し**: 回答の項目コード（`pathology-synoptic` の `histologic-type` `grade` `pt` `pn` `pm`
  `pstage` `neoadjuvant`）を院内がん登録の初期値変数（`%pathologyMorphology` `%pathologyPT` など）が読む
  （`docs/cancer-registry-design.md` §3）。選択肢のコードが様式のコードへの対応の鍵なので、施設が複製して直すときも
  コードは変えない。
- 既定テンプレートは持たない（§4.4 と同じ理由）。細胞診の診断（判定 + 推定病変）には出さない。

### 4.8 患者安全ガイド（病理編）への対応（2026-11-01）

JAHIS 技術文書 22-103 の「病理診断」「診断結果確認」のシステム機能要件のうち、電子カルテ側で持つものを入れた。
依頼・採取・受付（検体ラベル・容器数・受付照合）と標本作製（カセット・スライド）は未対応（§8-11）。

**診断医（ガイド 7.4.3「最大 3 名程度まで保存・表示する機能が必須」）**

- `DiagnosticReport.resultsInterpreter` に入力欄の順で入れる（`display` に氏名を焼き付け）。フォームは「診断医1〜3」の
  セレクトで、選択肢は医師・歯科医師（`useDoctorOptions`）。一覧から外れた医師も保存済みの名前で残す。
- 新規のレポートはログイン中の利用者が医師なら 1 人目に入れる。確定する報告（最終・訂正・追加）では 1 人以上必須、重複は不可。

**重要度（ガイド 7.5.3「悪性または悪性疑い等を入力・電子カルテで確認できる」）**

- 拡張 `patho-report-importance`（valueCoding、`CodeSystem/patho-report-importance` の `suspicious` 悪性疑い /
  `malignant` 悪性）。指定なしは拡張ごと無い。
- 細胞診は判定を選ぶと重要度の初期値が入る（悪性 → 悪性、悪性疑い → 悪性疑い、それ以外 → なし）。後から直せる。
- 表示は内容表示の「診断」の頭、カルテのカード（病理検査オーダーのカード）、通知の内容欄。悪性は塗り、悪性疑いは枠。
- **検査結果確認の通知をアラートにする**（`Task.priority = stat`）。重要所見のような別の通知は作らない。宛先が同じ依頼医で、
  確認も同じ操作になるため（2 回確認させない）。印（重要度・訂正/追加）は `Task.input`（`印`）に持ち、一覧で内容の前に出す。

**訂正報告と追加報告（ガイド 7.5.3「病理診断報告書のステータス（追加診断、訂正診断等）が確認できる」）**

- 確定済み（最終・訂正・追加）のレポートを編集すると、報告区分の選択肢が「訂正報告（`amended`）/ 追加報告（`appended`）」に
  変わり、既定を置かず毎回選ばせる。免疫染色の結果を足すのは追加、診断を改めるのは訂正。
- `Observation.status` には `appended` が無いので、追加報告で書き直した所見の Observation は `amended` にする。
- 表示名は「修正報告」から「訂正報告」に改めた（ガイドの用語、読影・所見レポートと揃える）。
- 確定とみなす status に `appended` を加えた（院内がん登録の初期値の検索 `status=final,amended,appended` など）。

**一時保存（下書き。ガイド 7.4.3「割り込みに際して入力中の診断・所見を簡便に一時保存して入力中の画面をクリアする機能が必須」）**

- フォームの「一時保存」で `status = registered`（FHIR R4 の「存在は登録済みだが中身はまだ無い」）として保存し、フォームを閉じる。
  入力途中でも保存できるよう、検査するのは報告日だけ。中間報告で保存すると、途中経過として臨床側から見えてしまうため分けた。
- 一時保存できるのは**まだ公開していない**（新規・下書きの）レポートだけ。中間報告以降を下書きに戻すと、一度見せた内容が
  臨床側から消えるため。下書きを開き直すと報告区分は中間・最終から選べ（既定は最終報告）、保存すれば通常どおり公開される。
- 臨床側には見せない:
  - カルテのカード（病理検査オーダー）はレポートが無いものとして扱う（バッジ・「レポート表示」なし）。
  - 病理タブの日付ペインには破線の枠・斜体で残し（行のツールチップに「下書き」）、選ぶと内容の代わりに「作成中のレポート（下書き）です」と出す。
    「編集」から続きを書ける。既定の選択は公開済みのレポート。カードから開く詳細モーダルも同じ表示。
  - 「確認」「患者説明」は出さない。検査結果確認・患者説明の台帳も作らない（`isReviewableReportStatus` が `registered` を除く）。
- 病理部門一覧（病理医・技師が書く場所）だけは内容まで表示する（`PathoResultDetailPanel` の `showDraft`）。レポート列は「下書き」。
- 検査結果の日付ペインの要約に `status` を足した（`_elements` に `status`）。

**患者説明（ガイド 7.5.3「患者への説明の実施有無を入力」「チーム・医療安全で確認」「重要度が高く未説明の一覧」）**

- 台帳は `Task`（`task-code|result-explanation`、`fhir/resultExplanationHelpers.ts`）。検査結果確認（読んだか）とは別に、
  患者に伝えたかを追う。

  | 要素 | 値 |
  |---|---|
  | `status` | `requested`（未説明）/ `completed`（記録済）/ `cancelled`（レポートを削除した） |
  | `priority` | 重要度ありは `urgent`、なしは `routine`（ベルには載せないので一覧の並びには使わない） |
  | `focus` / `for` / `owner` / `basedOn` | レポート / 患者 / オーダーの依頼医 / オーダー |
  | `input` | 種別（`patho`）・対象日（報告日）・内容（検体）・重要度・報告区分（訂正・追加のときだけ） |
  | `output` | 対応（`result-explanation-resolution`: `explained` 説明済 / `referred` 紹介先で説明 / `not-needed` 説明不要）、説明日 |
  | `note` | 記録した人・日時・メモ |

- レポートが確定したとき（保存の transaction で）作る。**確定後に訂正・追加すると説明済みでも未説明に戻す**（診断が変われば
  説明も変わる。前の記録は Task の版の履歴に残る）。中間報告では作らない。レポートの削除で未説明のものは取り下げる。
- **説明を記録すると、検査結果確認が未確認なら既読（来歴）も同じ transaction で残す**（説明した人は結果を読んでいる）。
- **通知一覧（ベル）には載せない**。説明は次回受診まで数週間かかることが多く、ベルに残ると今すぐの通知が埋もれる
  （フォロー推奨と同じ判断）。追うのは次の 3 か所:
  - カルテの病理タブ（とカードから開く詳細モーダル）の見出し行、「確認」の隣の「患者説明」。記録後は対応区分の印になり、
    記録した人・日・メモはツールチップで読む。
  - 診療業務 > 検査結果フォローの「患者説明」タブ（`docs/result-followup-design.md` §3.2）。未説明は台帳に載った（載せ直した）
    古い順で、14 日以上は経過を赤にする。「重要度ありのみ」で絞れる。「自分あてのみ」を外せばチームや医療安全の担当が全体を見られる。
  - ホームのカード「検査結果フォロー」に未説明の件数（14 日以上・重要度ありの内訳）。
- 台帳を作るのはこの仕組みを入れた後に確定・訂正したレポートから（検査結果確認と同じ。過去分を一気に未説明にしない）。
- いまの対象は病理だけ。`ReviewReportKind` を持たせてあるので、読影の重要所見などにも同じ台帳を広げられる（§8-12）。

**フォロー推奨（再生検・追加検査・他科受診の推奨。2026-11-01）**

- 読影・所見レポートのフォロー推奨（`docs/result-followup-design.md`）を病理診断レポートに広げた。フォームの区画「フォロー推奨」
  （チェックすると内容・期限が必須）、拡張 `patho-follow-up`（子拡張 `recommendation` / `due`。`rad-follow-up` と同じ形）。
  内容表示では報告共通の上に枠で出す。
- 台帳（`task-code|followup-recommendation`）の作り方・取り下げ・対応の記録は読影・所見レポートと同じ。確定したときに載せ、
  推奨か期限を変えたら未対応に戻し、推奨を外すかレポートを削除したら未対応のものを取り下げる。`Task.input` の種別は `patho`、
  検査内容は検体名（検査結果確認の通知と同じ要約）。検査結果フォローの一覧では種別「病理検査」、「カルテ」で病理タブを開く。

### 4.9 検体個数・容器数と採取の記録（2026-11-01）

JAHIS 患者安全ガイド（病理編）7.1「病理依頼・検体採取」のシステム機能要件のうち、オーダーごとの検体数／容器数の管理と、
採取時の入力（修正）を入れた。検体ラベル（容器番号/総容器数）と受付の照合はこの数を使う（§8-1・§8-11）。

- **持ち方**: 検体明細の contained Specimen に、検体個数 `collection.quantity`（UCUM `{piece}`、表示「個」）と容器数
  拡張 `patho-container-count`（HL7 v2 SPM-26 Number of Specimen Containers に当たる）。`Specimen.container` は容器ごとの
  識別子を持つ要素で、数だけを持てないので拡張にした。容器数を持たない既存のオーダーは 1 容器とみなす。
  オーダーの容器の総数は検体ごとの容器数の和（ラベルの「容器番号/総容器数」の分母）。
- **依頼時**: オーダー入力の検体カードに「検体個数」（任意。採取するまで分からないことが多い）と「容器数」（1 以上、既定 1）。
  DO では個数・容器数を予定として引き継ぎ、採取の記録は引き継がない。
- **採取時**: カルテの病理検査オーダーのカードのメニュー「採取」（記録後は「採取修正」）。部門が受け付ける前（進捗が依頼済）
  だけ出す。モーダルで採取日時（既定はいま）と、検体ごとの臓器（検索で変更）・左右・検体個数・容器数を入れる。
  採取では個数も必須（仮の数のまま搬送しないため）。保存は**検体明細だけ**を `If-Match` 付きで PUT する
  （`buildPathoCollectionBundle`）。ヘッダを組み直すとオーダーの依頼医・診療科が採取した人のものに替わるため。
  オーダーの編集ではなく実施の記録なので、代行入力の来歴は付けない。採取日時は全検体に同じ値を書く。
- **オーダーの編集**は採取の記録を保ったまま行える（フォーム値に採取日時を持ち回る）。
- **表示**: カードの検体の行に「3個・容器2」、採取を記録したら「採取: 日時 容器 計n」。内容表示（カルテ・部門一覧）に
  採取日時・検体個数・容器数の列と容器の総数。部門一覧の検体の列に容器の総数と、依頼済で採取の記録が無ければ「未採取」。
- ［残り］1 つの容器に複数の検体を入れる運用（容器を共有する）は表せない（検体ごとに 1 容器以上）。ベッドサイドの
  ネームバンド照合、採取に連動したラベルの発行は §8-11。

### 4.10 病理検体ラベル（2026-11-01）

JAHIS 患者安全ガイド（病理編）7.1.3「患者ID・患者名・ユニークID付きの容器総数が明記された検体ラベルが印刷・管理される機能」。
1 ページ = 容器 1 つ（オーダーの容器の総数ぶん、§4.9 の容器数の和）。レイアウトは `docs/report-mappings/patho-label-01.md`。

- **刷る内容**: バーコードと番号（ユニーク ID）、患者番号・漢字氏名・カナ氏名・生年月日・性別、「検体1 右 胃前庭部」、
  「容器 2/3」（オーダー通しの容器番号 / 総数）、検査区分・検体タイプ・採取法・検体個数、採取日（未採取なら採取予定日）、至急。
- **台帳は上流の Specimen**（検体検査の採取管と同じ作り。`docs/lab-arrival-design.md` §6-1）。容器 1 つに 1 件で、
  - `identifier`（`IdSystem/patho-container`）= 「検体明細の id:明細内の容器の順番」。これで容器を見分け、conditional create の鍵にする。
  - `accessionIdentifier` = ラベル番号。**検体検査と同じ `IdSystem/lab-label-number` の採番**（上流 `Fhir::AccessionAssigner`）を使い、
    院内で 1 つの通し番号にした。上流の採番は 1 つの system にしか効かないので、病理用の体系を足すには上流の変更が要る。
    同じ番号の体系なので、検体到着確認（検体検査）で病理の容器を読んだときは弾く（「病理検査の検体です」）。
  - `request` = [オーダー（ヘッダ）, 検体明細]。オーダー側は部門一覧が `_revinclude=Specimen:request` で引くため、明細はどの検体の容器かを示すため。
- **発行の冪等性と容器数の変化**: backend `PathoLabelReport` が発行のたびに、いまの容器（明細 × 容器数）と台帳を突き合わせる。
  無い容器は作り（番号は送らず上流が採番）、ある容器はその番号を刷る（再発行で番号は変わらない）。採取で容器数を減らした・
  検体を外したときは、当たらない容器を `entered-in-error` にし、また数えるようになったら戻す（同じ番号）。
  受付の照合（§8-11）は `entered-in-error` の容器を「無効なラベル」として扱える。
- **発行の入口**:
  - 採取のモーダル（§4.9）の「ラベル発行」（既定でオン）。保存できたら新規タブで PDF を開く（保存前に刷ると直す前の容器数で
    刷られるので、クリック時に空のタブだけ開き、保存後に PDF へ差し替える。ポップアップブロック対策）。
  - カルテのカードのメニュー「ラベル発行」と、病理部門一覧のケバブの「ラベル発行」（刷り直し）。中止のオーダーには出さない。
- **エンドポイント**: `GET /reports/patho_labels/:order_id/pdf`（`Reports::PathoLabelPdfsController`）。病理以外のオーダーは 422、
  検体の無いオーダーは 422。

### 4.11 病理受付（ラベルの照合と病理受付番号、2026-11-01）

JAHIS 患者安全ガイド（病理編）7.2.3 のシステム機能要件:「全容器のバーコードを読んで容器数をチェック」「誤った検体ラベルを
読み取った時はアラート（必須）」「容器数に過不足があれば受付不可」「オーダ番号（検体ラベルのバーコード）で情報を呼び出す」。

- **画面**: 部門業務 > 病理部門 > **病理受付**（`/patho-reception`、`pages/PathoReceptionPage.tsx`）。病理検査一覧の行の「受付」は
  `?order=<id>` 付きでこの画面を開き、そのオーダーを照合の対象にしておく。
- **照合の流れ**: ラベルを読むと番号で容器の台帳（§4.10）を引き、最初に読んだラベルのオーダーが照合の対象になる。
  オーダーの容器（明細 × 容器数、ラベルと同じ並び）を表で出し、読んだ容器に「済」を付ける。**全容器を読み、ラベル未発行の容器が
  無く、進捗が依頼済のときだけ「受付」を押せる**（足りなければ押せない）。「やり直し」で照合を捨てる。
- **警告（照合には入れない）**: 番号の形式違い・発行記録なし・検体検査のラベル・取り下げたラベル（容器数の変更で刷り直し前のもの）・
  照合中と別のオーダー（別の患者なら「別の患者（氏名）のラベルです」、同じ患者なら別オーダー）・オーダーの容器に当たらないラベル・
  中止のオーダー。警告は読み取り欄の下に大きく出し、履歴にも赤で残す。受付済のオーダーのラベルは「受付済のオーダーです（病理受付番号 n）」。
- **受付の書き込み**（`buildPathoReceptionBundle`、1 transaction）: 進捗を受付済、オーダー（ヘッダ）の `identifier` に
  **病理受付番号**（`IdSystem/patho-accession-number`）、読んだ容器の Specimen に `receivedTime` と `status: available`。
  ヘッダは読んだ版を書き換えて送る（依頼医・診療科はそのまま、`If-Match` 付き）。
- **病理受付番号**: 上流の `ServiceRequest/$next-identifier?system=…` で連番を払い出す（番号に意味は持たせない。年で区切る書式などは未対応）。
  受付を取り消して受け付け直しても番号は変えない。照合しない受付（ケバブ）でも振る。オーダーの編集でヘッダを組み直すときも
  元の identifier を引き継ぐ。表示は病理検査一覧の区分の列（No.n）、オーダーの内容表示、カルテのカード。
- **番号で呼び出し**: 病理検査一覧の「ラベル番号・病理受付番号」欄。11 桁のラベル番号なら容器の台帳から、それ以外は
  `ServiceRequest?identifier=<受付番号の system>|<値>` でオーダーを引き、採取日をそのオーダーの日に合わせて内容を開く。
- ［採らなかった］病理受付ラベル（受付番号を刷って上貼りする）。ガイドも「上貼りしなければ貼り間違いは発生しない」とし、
  番号での呼び出しで上貼りを不要にする方を推すため、上貼りの運用は作らない。依頼書（紙）との照合も持たない（依頼書を刷らないため）。

   至急＋手術室番号欄が出ることを確認
4. 部門一覧: 採取日で拾えること、依頼済 → 受付済 → 検査済の遷移を確認
5. レポート: 中間報告で保存 → 最終報告に更新 → 再編集で `amended`（当時の表示名は修正報告）へ
   自動遷移することを確認。最終報告で診断が空なら弾かれることも確認
6. 細胞診レポート: 判定（valueCodeableConcept）+ 推定病変（component）で保存されることを確認
7. 編集: 検体を 1 件外して保存 → 外した明細が DELETE され 410 になることを確認
8. カルテ: 病理タブでの表示、カードの検体一覧・進捗・修正報告バッジ、
   ケバブメニューの「レポート表示」を確認

## 8. 未決事項・申し送り

1. **検体ラベル（バーコード）発行**。2026-11-01 に入れた（§4.10）。残りは、ラベルプリンタ・用紙が決まったときの `.tlf` の
   調整と、ベッドサイドでのネームバンド照合（§8-11）。
2. **手術・内視鏡からの導線**。手術オーダーには既に「検体提出予定」
   （`surgery-specimen-plan`: 術中迅速 / 永久標本）があり、手術記録テンプレート
   （`docs/report-mappings/sur-op-01.md`）にも「病理検査のオーダーは別に出す（ここは記録）」
   と書かれている。今回はその方針どおり導線を作らない。DO 起票を作るなら
   `specimenPlans` から検査区分を決める形になる。
3. **免疫染色の追加依頼（N002）・遺伝子検査（N005）**。`EXAM_CATEGORY_OPTIONS` に足せば
   オーダーは出せる。ただし「既存オーダーへの追加依頼」は親オーダーを指す構造
   （`basedOn` か `replaces`）を決める必要がある。
4. **剖検（病理解剖）**。規約 20-004 は剖検レポート（LOINC 18743-5）も定義している。
   区分を足せば同じ構造に乗るが、依頼元・承諾書など業務が別。
5. **検体ごとの採取日時**。規約は SPM 単位。v1 はヘッダ 1 欄で、実採取日はレポート側の
   Specimen に持つ。必要になれば検体明細の `occurrenceDateTime` に個別値を書ける
   （構造は既にある）。
6. **細胞診判定の領域別分類**。v1 は汎用 5 段階（陰性 / 鑑別困難 / 悪性疑い / 悪性 /
   検体不適正）+ 推定病変の自由文。ベセスダ分類などの領域別分類は持たない。
7. **WSI・DICOM 画像**。シェーマ（AP-031）は実装済み（§4.4）だが、規約が扱う
   WSI（バーチャルスライド）・DICOM 画像の連携は対象外。
8. **院内がん登録への連携**は、診断のシノプティックレポート（§4.7）の項目コードを登録の初期値が読む形で
   対応した（`docs/cancer-registry-design.md`）。臓器別のテンプレートは大腸癌だけで、胃・肺・乳腺などは
   固形がん共通 TNM で書くか、臓器別に足す。
9. **検査区分ごとの既定テンプレート**。検査区分をマスタ化して
   `clinical_info_template_canonical` を持たせれば、組織診と細胞診で既定を分けられる
   （臨床経過に書く内容は区分で変わる）。今は毎回選ぶ運用（§4.4）。
10. **シェーマの再編集**。`SchemaPaintModal` は fabric オブジェクトを保存せず合成画像だけを
   残すため、一度添付したシェーマの線を 1 本だけ消すことはできない（外して描き直す）。
11. **患者安全ガイド（病理編）の残り**（§4.8・§4.9 で入れた以外）。依頼・採取:
   ベッドサイドのネームバンド照合（注射の 3 点認証を流用できる）。
   受付: 受付完了の依頼医への連絡（全容器の照合・病理受付番号・番号での呼び出しは §4.11）。
   診断: 臨床診断と病理診断の相違の印 → 依頼医への通知（フォロー推奨は §4.8）。
   標本作製（カセット・スライドの印字と照合、スライド枚数のチェック）は病理部門システムの領域として対象外にしている。
12. **患者説明の対象の拡大**。台帳は種別を持つので、読影の重要所見や検体検査の緊急異常値にも同じ「説明済」を付けられる。
