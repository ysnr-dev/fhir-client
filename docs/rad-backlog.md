# 放射線検査(オーダー・部門業務・実施・読影)の不足機能

2026-09-16 に放射線検査の実装を棚卸しして洗い出した未実装の記録。オーダー入力・部門業務
(進捗 Task)・実施入力(造影剤・器材・被曝線量)・予約連携までは動いており、**不足は結果側
(読影レポート)と安全確認と帳票に集中している**。

放射線には設計書が 2 本あり(`docs/rad-order-master-design.md` = マスタとオーダー、
`docs/rad-result-design.md` = 実施入力)、それぞれの「申し送り」に断片が散っている。他種別が
各設計書の「§8 未実装・今後」に置いている内容を、検体検査の `docs/lab-backlog.md` と同じ形で
ここにまとめ直す。オーダー種別をまたぐ課題は `docs/order-common-backlog.md`、上流サーバー側の
課題は `docs/server-improvement-backlog.md`。

- **［事実］** = このリポジトリ・上流の実装で確認した内容
- **［導出］** = 事実から論理的に導ける内容
- **［提案］** = 本メモの提案

着手の推奨順は **A → B → D-1 / E-1 / E-3 → C**。A(読影レポート)が無いと放射線は「撮って
終わり」のままで、検体検査・細菌・病理が 2026-09 に揃えた報告区分・既読・通知の器がまるごと
乗っていない。B(安全確認)は器がすべて既存なので工数に対して効果が大きい。

## 0. 現状(実装済みの範囲)

洗い出しの前提として、動いているものを先に挙げる。

- **マスタ**(`docs/rad-order-master-design.md`): JJ1017 部品コード 11 要素・頻用コード表・
  撮影項目(`master_rad_items`)・セット構成・撮影伝票レイアウト・器材(`master_rad_materials`)・
  実施入力データセット(`master_rad_datasets`)。32 桁コードの組立/分解は `Master::Jj1017Code` の 1 か所。
- **オーダー入力**(`components/RadOrderForm.tsx`): 撮影伝票と項目検索の 2 方式、セットの自動展開、
  GP 単位(1 GP = 撮影項目 1 つ、セットは親で 1 GP)の依頼病名・検査目的・特別指示、テンプレート記入
  (`TemplateEntryModal`)、至急区分(通常 / 至急 / 事後)、撮影日時、予約枠の選択、即実施、
  単独オーダーの自動分割(`splitRadOrderValues`)、DO・編集・削除、オーダーセット、クリニカルパス連携。
- **部門業務**(`pages/RadWorklistPage.tsx`): 撮影日 1 日ぶんの一覧、モダリティ / 入外区分 / 病棟 /
  診療科 / ステータスでの絞り込み、Task の 依頼済 → 受付済 → 実施済 / 中止(`fhir/radTaskHelpers.ts`)、
  実施取消での実施記録の DELETE。
- **実施入力**(`components/RadPerformModal.tsx` / `fhir/radResultHelpers.ts`): Procedure をハブに、
  手技料(2 件目以降は `partOf` の子)・造影剤(`MedicationAdministration`、使用量と経路)・
  器材(`Procedure.usedCode` + 数量のローカル拡張)・被曝線量(`Observation`、モダリティで欄を出し分け)・
  コメント。データセットからの初期表示と候補選択(`DatasetPickList`)。
- **予約**: 撮影項目マスタの `requires_appointment` / `duration_minutes` / `appointment_schedule_id`。
  枠の確保・付け替え・解放をオーダーの transaction に同梱する(`buildExamAppointmentEntries`)。
- **横断機能**: 代行入力の記録と承認(Provenance)、妊娠・授乳の注意(`PregnancyNotice`)、
  カルテカードでの実施情報表示。

## A. 読影レポート(最大の欠落)

> **設計・実装(2026-09-16)**: `docs/rad-report-design.md`。A-1〜A-4 を実装した。A-5(読影ワークリスト)は未実装。
> 画像は元画像と描き込み画像を別の Binary で持つ形にした(以下の A-4 の「当面はファイルのアップロードだけ」から広げた)。
> 要素の割り当て(読影医は `resultsInterpreter`、画像は `media` ではなく拡張)は設計書が正で、以下の A-1 の図とは異なる。

［事実］放射線には結果に当たるリソースが無い。

- `frontend/src/fhir/resultReviewHelpers.ts` の `ReviewReportKind` は `"lab" | "micro" | "patho"` で、
  コメントに「放射線は読影レポート(DiagnosticReport)がまだ無く、実施記録(Procedure)だけなので
  対象にできない。読影レポートを入れるときにここへ足す」と書いてある。
- `frontend/src/fhir/karteTimeline.ts` の放射線カードは `reportId` を持たない
  (「検査結果(ImagingStudy)との紐付けは未実装」)。`components/KarteTimeline.tsx` の
  「検査結果表示」は検体検査・細菌検査・病理の 3 種別だけに出る。
- readme の「検査結果の確認(既読)」も「放射線は読影レポートがまだ無く、実施記録だけなので対象外」と断る。

［導出］**上流とプロキシの追加は要らない**。`DiagnosticReport` は
`FhirProxyController::ALLOWED_RESOURCE_TYPES` に既にあり、上流の `based-on` 検索も検体検査で
使用中。`Binary`(キー画像)・`Provenance`(既読)・`Task`(通知)も揃っている。足りないのは
クライアント側の器だけ。

### A-1. 読影レポートの登録・表示

［提案］**病理レポート(`fhir/pathoResultHelpers.ts`)を雛形にする**。検体検査は項目 × 値の表で
構造が合わず、病理は「所見(自由文)+ 診断 + 画像」で読影レポートとほぼ同じ形をしているため。

```text
DiagnosticReport                             ← 今回の中心
  basedOn      = ServiceRequest(オーダーヘッダ)
  category     = order-type|rad と v2-0074|RAD
  code         = 撮影内容(オーダー明細の写し。モダリティ + 部位)
  subject / encounter
  status       = preliminary | final | amended   ※ A-2
  effectiveDateTime = 撮影日時(オーダーの occurrence を写す)
  issued       = 報告日時(保存のたびに更新)
  performer    = 読影医 / 自院
  conclusion   = 診断(印象)
  result       ← Observation(所見。1 レポート 1 件)
  media        ← キー画像(Binary。§A-4)
  extension[rad-critical-finding]  = 重要所見の有無 ※ A-3
```

設計判断:

- **所見は `Observation` 1 件、診断は `conclusion`**。［事実］`DiagnosticReport.conclusion` は
  「所見の要約・解釈」そのもので診断に当たる。所見本文を `conclusion` に混ぜると、A-2 の訂正で
  どちらを直したかが読めなくなる。病理が所見と診断を分けているのと同じ形にする。
- **`presentedForm`(PDF 埋め込み)は使わない**。検索も差分も取れない塊になり、訂正の履歴が
  `_history` から読めなくなるため。外部 RIS のレポートを取り込む段階で改めて判断する。
- **`imagingStudy` は空で作る**。PACS 連携が入るまで DICOM の Study UID を持てない(§F-1)。
  参照要素は後から足せるので、レポート自体を待たせない。
- **profile** は JP Core の `JP_DiagnosticReport_Radiology`。上流のバリデータが要求する必須要素は
  登録前に開発サーバーで確認する(JASPEHR 検証で IG 要約に無い必須が出た前例がある)。

画面:

- **登録・編集**: 放射線検査一覧の実施済の行の「読影」と、カルテの放射線カードのメニュー。
  病理の `PathoResultForm` と同じ構成(所見・診断・読影医・報告区分)。
- **表示**: カルテの放射線カードに「検査結果表示」を出し、`KarteCardModals` に `rad-result` を足す。
  カルテのタブは当面作らない(検体検査のような累積表示の要求がまだ無い)。
- 所見・診断はテンプレート記入(`TemplateEntryModal`)に対応させる。撮影項目マスタに
  `report_template_canonical` を足し、CT・MRI の定型所見をモダリティごとに既定にできるようにする。

［提案］**読影の進捗は Task に足さず、レポートの `status` で表す**。進捗 Task
(`fhir/radTaskHelpers.ts`)は撮影という 1 つの事実の進み方(依頼済 → 受付済 → 実施済 / 中止)で、
読影は撮影とは別の担当者が別の時間に行う工程。Task に「読影待ち」を足すと、撮影の取消と読影の
取消が同じリソースの取り合いになる。一覧には「未読影 / 暫定 / 確定」の列をレポートから出す。

### A-2. 報告区分(暫定・最終・訂正)

［提案］病理と同じ規約にする(`fhir/pathoResultHelpers.ts` の `preliminary` / `final` / `amended`)。

- **暫定報告**(`preliminary`) … 当直帯の速報。**最終報告**(`final`) … 読影医の確定。
  **訂正報告**(`amended`) … 確定後の編集で自動遷移する。
- 検体検査が `corrected` を使うのは「値を直した」意味だからで、読影は**解釈の変更**なので病理と
  同じ `amended` にする。
- 旧版は上流の `_history` から読む(検体検査の「選択項目の変更履歴」と同じ形)。
- 印はカルテカードのバッジと、レポート内容表示の「報告区分」の 2 か所。

### A-3. 既読(結果確認)と重要所見の通知

［提案］既存の器に足すだけで済む。

- **既読**: `resultReviewHelpers.ts` の `ReviewReportKind` に `"rad"` を足す。最終報告になった
  タイミングで依頼医あての通知(`Task`、`code = result-review`、強度**お知らせ**)を作り、確認の記録は
  `Provenance`(`agent.type = verifier` + Verification Signature)。訂正すると未確認に戻る扱いも
  そのまま効く。
- **重要所見**: ［提案］新しい通知種別 `rad-critical-finding`(**強度アラート**)を足す。読影医が
  レポート登録時に「重要所見」をチェックし、所見の要点を 1 行添えると、依頼医あてに通知が立つ。
  ［事実］通知は `components/notifications/notificationRegistry.tsx` の `NOTIFICATION_KINDS` に
  1 要素足すだけで一覧・件数・種別フィルタ・一括対応に乗る(いまは 4 種別)。
  ［導出］パニック値(`lab-panic`)と同じ位置づけで、**暫定報告でも通知を出す**。気胸・大動脈解離を
  見つけたことは確定前でも変わらないため(検体検査のパニック値が中間報告でも出すのと同じ判断)。
- **宛先**はオーダーの依頼医。オーダーに紐付かないレポートは宛先が決まらない(既存 2 種別と同じ)。

### A-4. キー画像

［提案］病理の `patho-report-image` 拡張(`docs/patho-order-design.md` §4.5)と同じ器を使う。
読影所見の根拠になるスライスを数枚、`Binary` として添付し、レポートから参照する。

［提案］**当面はファイルのアップロードだけにする**。PACS が無い段階では、技師・読影医が
ビューアから書き出した PNG / JPEG を貼る運用しか成立しない。DICOM のまま扱うのは PACS 連携の
段階(§F-1)。シェーマ画像(`SchemaImageField`)の描き込みは、矢印で所見を指す用途に流用できる。

### A-5. 読影ワークリスト

［事実］放射線検査一覧は撮影日 1 日ぶんの表示で、「実施済だが未読影」を日付をまたいで見る画面が無い。
［提案］部門業務に「読影一覧」を足す。未読影 / 暫定のレポートをモダリティ・依頼科・撮影日で絞り、
行から読影入力へ飛ぶ。検体検査の B-4(検査室の未処理一覧)と同じ趣旨。

［提案］**読影医の担当割当は持たない**。割当を持つとレポートの前に Task がもう 1 段要り、
交代・応援読影のたびに付け替えが要る。まずは「空いた人が上から読む」で足りる。

## B. オーダー入力時の安全確認

［事実］オーダーフォームが出す安全情報は妊娠・授乳の注意(`PregnancyNotice`)だけで、これも
表示のみ(確認の記録もブロックも無い)。

［事実］CT の特別指示テンプレート `RAD_CT_01`(`docs/report-mappings/rad-ct-01.md`)は
「造影剤の安全確認」として副作用歴・喘息・eGFR・透析・ビグアナイド・妊娠の可能性・同意を
**医師が手で答える設問**として持ち、設計書自身が「暫定」と書いている。

［提案］**カルテにあるデータから自動で出す**。設問は残し(最終判断は医師のもの)、既定値として
流し込む形にする。処方・注射の薬剤安全チェック(`components/MedicineWarnings.tsx`)と同じく
**登録は止めず、印と文で出す**。判定の材料はすべて既存。

| 見るもの | 既存の器 |
|---|---|
| 造影剤アレルギー | `fhir/allergyHelpers.ts` の `matchMedicationAllergies`(銘柄 YCM・成分 GCM) |
| 腎機能(eGFR) | `fhir/bodyMeasureHelpers.ts`(血清クレアチニンと年齢・性別から算出) |
| 投与中の薬剤 | `useActiveMedications`(YJ コード上 7 桁で成分照合) |
| 注意区分 | `Flag` + 注意区分マスタ。`implant`(体内金属・ペースメーカー)と `contrast`(造影剤注意)は seed 済み |
| 妊娠・授乳 | `PregnancyNotice`(実装済み) |
| 過去の造影剤使用 | 実施記録の `MedicationAdministration` |

判定の起点は選んだ撮影項目の JJ1017 要素。［導出］種別(1 桁目)でモダリティが、手技小分類
(4–5 桁目 `01`)で造影の有無が判る。撮影項目マスタを引き直さずにオーダーの明細から読める。

### B-1. 造影検査の注意

対象は造影 CT・造影 MRI・血管撮影・透視造影。

- 注意区分 `contrast`(造影剤注意)の Flag。
- 造影剤アレルギー。`matchMedicationAllergies` を「造影剤区分(`master_medicines.contrast_medium_category`
  が 0 以外)の医薬品」に当てる。過去に使った造影剤と使用量も並べる(前回問題なく使えた事実は判断材料)。
- eGFR。閾値(既定 45 / 30)以下なら文で出す。［事実］クレアチニンを持たない患者では算出できないので、
  その旨を出して黙って空欄にしない(`bodyMeasureHelpers` が理由を返す作りになっている)。
- ビグアナイド系(メトホルミン)の内服中。ヨード造影剤の休薬判断に要る。
- ［提案］喘息・甲状腺機能亢進症の既往は病名からの照合になるが、病名の表記ゆれで取りこぼすので
  当面は Flag(`alert`)に任せる。ICD コードでの照合は病名マスタ側の整備と一緒に判断する。

### B-2. MRI の注意

対象は種別 `7`(MRI)。

- 注意区分 `implant`(体内金属・ペースメーカー)の Flag。
- ［提案］**MRI 安全性の問診テンプレート `RAD_MRI_01` を新設する**(体内金属・植込み機器・刺青・
  閉所恐怖・妊娠の可能性)。`rad-ct-01` と同じ形で `docs/report-mappings/` に置き、MRI の撮影項目の
  特別指示の既定テンプレートにする。［導出］JJ1017 の特殊指示(別表6B)は 2 桁 × 1 個しか持てず、
  患者ごとに変わる確認事項を項目コードで表せない。CT の特別指示テンプレートと同じ答えになる。

### B-3. 重複撮影の警告

［事実］登録時の検証は「撮影項目 1 件以上・撮影日・予約の取得」だけで、同じ部位を続けて撮っても
何も出ない。［提案］同じ患者・同じモダリティ・同じ部位のオーダーが直近 N 日(既定 30)にあれば
文で出す。`ServiceRequest?subject=&category=…|rad&occurrence=ge…` を 1 本引き、明細の JJ1017 の
種別 + 部位で照合する。被曝の積み重ねと算定制限の両方に効く。**止めずに警告に留める**
(経過観察で続けて撮る場面があるため)。

### B-4. 放射線検査一覧への注意情報

［事実］一覧の患者列は生年月日・性別だけ(`components/PatientRowCells.tsx` の `PatientProfileCells`)。
注意区分のピクトグラム(`components/PatientPictograms.tsx`)は患者帯と病棟マップでしか使っていない。

［提案］一覧の患者列にピクトグラムと妊娠を出す。［導出］撮影の直前に見るのは一覧であって
オーダーフォームではない。フォームだけに出しても、撮影室の技師には届かない。

## C. 帳票

［事実］`backend/app/controllers/reports/` に放射線用のコントローラは無い(lab_label / injection /
injection_label / prescription / questionnaire_response だけ)。同梱 `.tlf` + Thinreports の基盤は
あるので、器は流用できる。マッピングは `docs/report-mappings/` に既存帳票と同じ形で残す。

### C-1. 検査案内(患者控え)

［提案］予約日時・撮影室・前処置(絶食・水分制限・内服中止)・持ち物・所要時間。予約必須の項目で
登録した直後に印刷する。前処置の文言は撮影項目マスタに `patient_instruction`(任意、複数行)を足して
そこから刷る。［導出］いまは口頭か手書きのメモに頼るしかなく、絶食の指示が伝わらないと当日に
撮れない(検査が流れる)。放射線の帳票としては最も効く 1 枚。

### C-2. 造影剤検査の同意書

［提案］手術の同意書(`SUR_CONSENT_01`)と同じく、テンプレート(Questionnaire)+ 帳票の組。
記入済みの `QuestionnaireResponse` をオーダーから参照し、**同意の有無を放射線検査一覧に印で出す**。
［導出］同意が無いまま造影剤を入れることは避けたいが、オーダー時点で同意書が揃っているかは
いま画面のどこからも分からない。

### C-3. 検査依頼票・受付票

［提案］撮影内容・依頼病名・検査目的・特別指示・依頼医を刷る 1 枚。紙の運用が残る施設と、
外部の撮影施設に依頼する場合に要る。［事実］検体検査(ラベル発行)と処方(処方箋発行)は
「帳票の発行 = 受付」の導線を持つが、放射線には無い。受付票にバーコード(オーダー id)を刷れば、
撮影室での受付をスキャンで行える。優先度は C-1・C-2 より低い。

## D. 被曝線量の管理

［事実］実施入力で CTDIvol / DLP / DAP / 透視時間を `Observation` に記録している
(`docs/rad-result-design.md` §3)。［事実］読む画面はカルテの放射線カードに出る**その 1 回ぶん**だけで、
経時の集計・照会が無い。

［事実］2020 年の医療法施行規則改正で CT・血管撮影・IVR の被曝線量の**記録と管理**が義務化されている。
記録(入力)は済んでいるが、管理(集計・照会・線量の適正化)の側が無い。

### D-1. 患者ごとの線量履歴

［提案］カルテに「被曝線量」の表示を足す。撮影日 × モダリティ × 撮影項目 × CTDIvol / DLP / DAP /
透視時間の一覧と、期間の累積。取得は `Observation?subject=&code=…|rad-dose&date=…` の 1 本。
［提案］置き場は検体検査の累積表と同じカルテのタブが素直だが、件数が少ないうちは
放射線カードのメニューから開くモーダルでもよい。**まず一覧を読めるようにする**のが要点。

### D-2. 施設の線量集計と診断参考レベル

［提案］部門業務に集計画面を足す。期間 × 撮影項目ごとの線量の分布(中央値・75 パーセンタイル)を出し、
**診断参考レベル(DRLs)との比較**で超過に印を付ける。DRL 値は撮影項目マスタに任意列
(`drl_value` / `drl_unit`)を足して持つ。［導出］DRL は「この撮影ならこの線量まで」の目安で、
撮影項目の単位で決まる。別マスタにすると撮影項目との突き合わせが要るだけで、持ち物は変わらない。

［提案］取得は `Observation?code=…|rad-dose&date=ge…&date=lt…` を期間で引く。件数が増えるので
`_count` の上限(500)を意識したページングが要る。集計そのものはクライアント側で足りる
(上流に `$aggregate` のような操作は無い)。

### D-3. 照射録

［事実］診療放射線技師法は、照射のたびに照射録(照射を受けた者の氏名・照射の年月日・照射の方法・
指示をした医師名)を作り、指示医師の署名を受けることを求める。

［提案］オーダー(指示医・撮影項目)と実施記録(実施者・実施時刻・線量・造影剤)から帳票を組む。
署名は代行入力の承認と同じ `Provenance` の Verification Signature を流用する(電子記録であって
暗号署名ではない旨は readme の既存の記述と揃える)。

### D-4. 線量の自動取得(RDSR)

［事実］`docs/rad-result-design.md` §7-4 で申し送り済み。装置の線量レポート(DICOM RDSR)から
自動で入るべき値を手入力している。［提案］PACS 連携(§F-1)と同じ段階で扱う。手入力欄は残し、
取り込み時に上書きできる形にする。線量の測定項目コードに DICOM の標準コードを**追加**すれば、
既存データはローカルコード側で引き続き読める。

## E. 部門業務とオーダーの細部

### E-1. 一覧の行からオーダー内容と実施情報を開く

［事実］放射線検査一覧の行からできるのは進捗の変更だけで、患者名のリンクでカルテへ飛ぶほかに
依頼内容を読む手段が無い。実施済の行に実施時刻も出ない(`docs/rad-result-design.md` §7-7 の未了)。
［提案］病理一覧の「表示」(依頼とレポートを並べて出す)と同じ導線を足す。撮影室で「何を撮るのか」を
確かめるのに毎回カルテを開かせない。

### E-2. 日付をまたぐ未処理の一覧

［事実］一覧は撮影日 1 日ぶん。「受付済のまま実施されていない」「予約日を過ぎて受付されていない」を
横断して見る画面が無い。［提案］A-5 の読影一覧と同じ画面に、切替で置く。

### E-3. 状態に応じた編集・削除の制限

［事実］受付済・実施済のオーダーも編集・削除が止まらない。オーダーを削除しても進捗 Task が残る
(部門横断の既知の課題)。［提案］受付済以降は編集時に警告、実施済・読影済は明細の変更と削除を止める。
削除時に Task を片付ける。［提案］**放射線から始めてよい**。実施記録・線量・レポートが紐付く種別で
最も実害が出やすく、片付けの形が決まれば他種別に写せる。

### E-4. 中止・実施取消の来歴

［事実］中止・実施取消は上流のバージョン履歴(`_history`)を直接読むしかない
(`docs/rad-result-design.md` §7-6)。［事実］`buildActivityProvenanceEntry`(CANCEL / REACTIVATE /
COMPLETE / SUSPEND / RESUME)という器は既にあり、いま呼んでいるのは化学療法だけ。
［提案］放射線の中止・実施取消からも同じ器を呼ぶ。詳細モーダルの来歴の行にそのまま並ぶ。

### E-5. 撮影装置と再撮影の記録

［事実］実施入力に装置・撮影室・照射条件(kV / mAs)・撮影枚数・再撮影の欄が無い。予約枠は
撮影室(Location)に付くが、至急と単純撮影は枠を取らないので、どの装置で撮ったかが残らない。

［提案］実施入力に**撮影装置**(撮影室の `Location`。`Procedure.location`)と**再撮影**(有無 + 理由)を足す。
［導出］装置は D-2 の集計の軸になり(同じ CT でも装置ごとに線量が違う)、再撮影は被曝の無駄と
運用の質を測る唯一の手がかりになる。
［提案］照射条件(kV / mAs)の手入力欄は**作らない**。RDSR で自動取得すべき値で、手で入れると
必ず形骸化する(§D-4)。

### E-6. 進捗の粒度

［事実］進捗は 依頼済 / 受付済 / 実施済 / 中止 の 4 状態。手術には「入室中」がある
(`fhir/surgeryTaskHelpers.ts`)。［提案］待合表示や「いま撮影中」を出す要求が出た時点で
「撮影中」を足す。足すときは `executionPeriod` の開始・終了の分岐を確認する。
現時点では**足さない**(状態が増えるぶん一覧の操作が増え、撮影は数分で終わるため実益が薄い)。

## F. 先送りを維持するもの

### F-1. ImagingStudy と PACS 連携

［事実］`JP_ImagingStudy_Radiology` は `series` を持つなら `series.uid` と `series.modality` が 1..1 で、
DICOM の Study / Series UID が要る(`docs/rad-result-design.md` §7-1)。［事実］`ImagingStudy` は
`FhirProxyController::ALLOWED_RESOURCE_TYPES` にも無い。

［提案］モダリティ・PACS と繋がるまで作らない。UID を捏造すると、後で実機の UID と突き合わせられない
偽データが残る。読影レポート(A)は `imagingStudy` を空で作り、連携時に足す。
［導出］画像ビューアへのリンクには Accession Number が要るので、その段階で
`ServiceRequest.identifier` への採番(上流の `$next-identifier`)を併せて入れる。

### F-2. 会計連携

［事実］上流に `ChargeItem` / `Claim` / `Invoice` が未実装。種別をまたぐ課題
(`docs/order-common-backlog.md` / `docs/lab-backlog.md` C-7)。オーダー明細の `receipt_code` と
実施記録の `usedCode` ・造影剤の使用量という「会計が必要とする材料」までは揃っている。

### F-3. 放射線治療オーダー

［事実］頻用コード表 F3(治療系 4,576 件)は取り込んでいるが、照射指示の属性(総線量・分割回数・
照射野・治療計画)は JJ1017 の範囲外(`docs/rad-order-master-design.md` §10-4)。別設計になる。

### F-4. JJ1017 Ver3.4 の正式取込

［事実］手元の別表は Ver3.3 で、Ver3.4 は PDF のみ公開。差分 3 件は seed CSV に入れてある。
JSRT への Excel / CSV 配布の確認は残っている。
