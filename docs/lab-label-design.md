# 検体ラベル発行の設計メモ

検体検査一覧(部門ワークリスト)から、採取管に貼る検体ラベルを発行するための設計。
検体検査一覧そのものは `frontend/src/pages/LabWorklistPage.tsx` として実装済み。
帳票基盤は QuestionnaireResponse の PDF 化(`backend/app/services/reports/thinreports_renderer.rb`)を流用する。
到着確認(検体が検査室に着いたことの記録)は別の設計で扱い、本メモでは「ラベルに刷る番号が
到着確認でそのまま使えること」だけを担保する。

調査日: 2026-08-18。帳票基盤・マスタ・上流プロキシの実装状況は同日のソースで確認済み。
本メモの範囲(§2〜§6)は 2026-08-18 に実装済み。§7 の未決事項は残っている。
運用条件は次で確定: スキャナはハンディの 1 次元リーダー前提(CODE128 + 採番テーブル方式)、
ラベル用紙は仮サイズ(60×40mm)、キャップ色は文字で刷る。

- **［事実］** = FHIR R4 / JP Core の仕様、またはこのリポジトリ・上流の実装で確認した内容
- **［導出］** = 仕様・実装から論理的に導ける内容
- **［提案］** = 本ドキュメントの設計提案

---

## 1. スコープ

要件は次の 3 つ。

1. オーダー・検体・採取管を識別可能な番号をバーコードに出力する
2. ラベルの印字内容は、患者番号・カナ氏名・性別・生年月日・検体・採取管(色)
3. オーダーを受付した後に、ラベルが発行できるようになる

要件 3 のため、検体検査にも放射線検査と同じ Task による進捗(受付)を導入する。
受付操作そのものは本機能の一部として実装する(受付が無いと発行可否を判定できない)。

### 含めないもの

- **到着確認**。別タスク。ただし §3 の番号設計は到着確認でのスキャン逆引きを前提に決める。
- **発行履歴の画面**。発行記録テーブル(§3-3)は持つが、一覧・監査画面は必要になってから。
- **色帯のカラー印刷**。キャップ色は文字で刷る(§2)。色帯はプリンタ・用紙が決まってから(§7-4)。
- **同一検体の複数本採取**。今のオーダー構造は「1 検体 = 1 採取管 = 1 本」を前提にしており
  (`groupBySpecimen` が検体コードでまとめる)、本数の概念が無い。必要になったら
  オーダー側の設計から見直す(§7-3)。

## 2. ラベルの単位と印字内容

**［導出］** ラベル 1 枚 = 採取管 1 本 = 検体グループ 1 つ。オーダー明細を検体・採取管ごとに
まとめる単位(`labOrderHelpers.ts` の `LabSpecimenGroup` / `groupBySpecimen`)は実装済みで、
検体検査一覧の「検査内容」列もこの単位で表示している。オーダー 1 件の発行操作で、
そのオーダーの全グループぶんのラベルを 1 つの PDF(1 ページ = 1 枚)にして返す。

**［提案］** 印字内容。要件の 6 項目に、現場で判断に使う情報を足す。

| 項目 | 出どころ | 備考 |
|---|---|---|
| バーコード | §3 の検体ラベル番号 | CODE128。下に番号を目視用の文字でも刷る |
| 患者番号 | `Patient.identifier[0].value` | 既存レンダラの `pt_id` と同じ |
| カナ氏名 | name(iso21090-EN-representation=SYL) | 既存レンダラの `pt_kana` と同じ |
| 性別 | `Patient.gender` → 男性/女性 | 既存レンダラの `pt_gender` と同じ |
| 生年月日 | `Patient.birthDate` | 既存レンダラの `pt_birthdate` と同じ |
| 検体 | 明細 contained Specimen の JLAC11 材料名 | 「血清」など |
| 採取管(色) | 採取管マスタの `short_name` + `cap_color` | 「EDTA管（紫）」の形 |
| 検査日 | ヘッダ `ServiceRequest.authoredOn` | 貼り間違い・日またぎの確認用 |
| 至急 | `ServiceRequest.priority` | urgent のときだけ「至急」を出す |
| 検査項目の略称 | グループ内の項目の略称(WBC など) | 何を採る管かの目視確認用。入り切らない分は省略 |

**［事実］** 採取管のキャップ色(`cap_color`)はオーダー明細に写していない。明細が持つのは
採取管のコードと名称だけ(`labOrderHelpers.ts` の `buildItemSpecimen`)。一方 `cap_color` は
backend の採取管マスタ(`master_lab_containers`)にあり、PDF を作るのも backend なので、
**［提案］** レンダリング時に `Master::LabContainer` を `container_code` で引いて色と略称を
得る。オーダーに写しを増やさないのは、色はオーダー内容ではなく採取管の属性で、
マスタで色を直したら過去のオーダーのラベルも新しい色で刷られるべきだから。

## 3. バーコードと検体ラベル番号

### 3-1. 番号の設計

**［事実］** 上流のリソース id は UUID(36 文字)。オーダー id + 検体コードを 1 次元バーコードに
直接載せると 40 文字級になり、ラベル幅(採取管に貼れるのは実質 40〜60mm)では読めない
密度になる。

**［提案］** 短い**検体ラベル番号**を backend で採番し、番号 → オーダー・検体・採取管の
対応を backend のテーブルに持つ(§3-3)。番号そのものに意味を持たせず(日付や患者番号を
埋め込まない)、対応表で引く。到着確認は「番号をスキャン → backend で逆引き →
オーダーと検体を特定」になる。

- 形式: **11 桁の数字** = 発行記録の id(10 桁ゼロ埋め)+ チェックデジット 1 桁(M10W3)。
  誤読・手入力ミス対策にチェックデジットは載せておく(採番側・照合側とも数行で済む)。
- 同じオーダー・同じ検体の再発行は**同じ番号**を刷る(番号は管の同一性を表すもので、
  発行操作の回数を表すものではない)。
- 検体未設定の項目だけのグループ(マスタで検体を決めていない項目)にも番号は振る。
  検体・採取管の欄は「検体未設定」で刷る。

設計判断: 採らなかった代案。

- **QR コードにオーダー id + 検体コードを直接載せる** — 採番も対応表も不要で最小構成だが、
  読む側に 2 次元スキャナが要る。ハンディの 1 次元 CCD/レーザーでも読める形にしておく方が
  機器の制約が少ない。スキャナが 2 次元前提と決まったら再検討してよい(§7-1)。
- **FHIR の独立 Specimen を受付時に作り、accessionIdentifier に番号を持たせる** —
  FHIR 的には最も素直だが、(1) 番号の採番自体は結局どこかで必要、(2) 結果登録が既に
  独立 Specimen を別に作っており(`labResultHelpers.ts` の `buildSpecimen`)、二重になる。
  受付時 Specimen への一本化は到着確認・結果登録も巻き込む構造変更なので、
  到着確認の設計で改めて判断する(§7-5)。それまでは backend の対応表で運ぶ。

### 3-2. シンボル

**［提案］** **CODE128**(数字のみなのでコード C で圧縮が効き、11 桁なら 40mm 幅に収まる)。
生成は barby + chunky_png(いずれも純 Ruby)で PNG を作り、Thinreports の image-block に
`page.item(id).src(StringIO.new(png))` で流し込む。**［事実］** thinreports 0.15 に
バーコード shape は無く、画像の流し込みは既存レンダラがシェーマ画像で使っている手順と同じ。

**［注意］** Gemfile 変更なので backend イメージの再ビルドが必要。

### 3-3. 発行記録テーブル

**［提案］**

```ruby
create_table :lab_label_records do |t|
  t.string :order_fhir_id, null: false      # ヘッダ ServiceRequest の id
  t.string :specimen_code, null: false, default: ""  # JLAC11 材料コード。未設定グループは ""
  t.string :container_code, null: false, default: ""
  # 採番済みの 11 桁(チェックデジット込み)。行を作ってから id で組むため、
  # 作成直後だけ NULL になる(unique index は NULL を許す)。
  t.string :label_number
  t.timestamps
  t.index %i[order_fhir_id specimen_code], unique: true
  t.index :label_number, unique: true
end
```

- 採番は「行を作ってから id で番号を組んで label_number を埋める」の 2 段。
  unique 制約があるので並行発行でも二重採番にならない(片方が拾い直す)。
- PDF 生成のたびに (order, specimen) で引き、無ければ作る。**発行 = 行があること**なので、
  再発行の判定・到着確認の逆引きがこのテーブルだけで済む。
- オーダー訂正で検体が消えた場合、行は残るが実害はない(スキャンされなければ使われない。
  スキャンされたらオーダー側に該当検体が無いことが到着確認側で分かる)。

## 4. 進捗(Task)と発行可否

**［提案］** 放射線検査(`radTaskHelpers.ts`)と同じ流儀で `labTaskHelpers.ts` を新設する。

```
ServiceRequest(オーダー) ← focus ── Task(進捗)
```

- `Task.code` = `task-code|lab-exam`(放射線の `rad-exam` と同じ CodeSystem)。
- 状態: `requested`(依頼済)→ `accepted`(受付済)→ `completed`(到着済)、別枠で
  `cancelled`(中止)。**本機能で実装するのは 受付(accepted)と中止・取消まで**。
  到着済への遷移(と、それが管ごとか オーダーごとか)は到着確認の設計で確定する(§7-2)。
- Task が無いオーダー = 依頼済。書き込みは transaction Bundle(ETag を持たないため)。
  いずれも放射線と同じ理由・同じ実装(`useUpdateRadTaskStatus` を型)。

**［提案］** ラベル発行は**受付済(accepted)のときだけ**押せる。ゲートは frontend の
ボタン活性で行い、PDF エンドポイント側では縛らない。受付前に URL を直叩きしても
困るのは本人だけで、エンドポイントに上流の Task 検索を足すほどの価値がない
(必要になれば後から足せる)。中止(cancelled)では発行も再発行も出さない。

## 5. 帳票(PDF)生成

### 5-1. 既存基盤の流用

**［事実］** 既存の帳票は「.tlf を DB(`report_layouts`)に登録 → backend が上流から資源を
集めて Thinreports で PDF → frontend は `<a target="_blank">` で新規タブに開き、印刷は
ブラウザに任せる」構成。`window.print()` は使っていない。ラベルもこの型に乗せる。

**［提案］** 構成要素:

- **レイアウト登録**: `report_layouts` のキー(questionnaire_url)に予約 URL
  `http://fhir-client.local/report/lab-label` を使い、既存の管理画面からアップロードする。
  設計判断: `kind` 列を足して帳票種別を分ける案もあるが、引き当て・管理画面・検証が
  1 本のままで済む予約 URL の方が変更が小さい。ラベル以外の非 Questionnaire 帳票が
  もう 1 つ増えた時点で `kind` 列に改める(§7-6)。
- **エンドポイント**: `GET /reports/lab_labels/:order_id/pdf`(`Reports::BaseController` 配下、
  ログイン必須・inline 返却は既存と同じ)。
- **資源収集サービス**: `QuestionnaireResponseReport` と同じ役割の `LabLabelReport` を新設。
  上流からヘッダ ServiceRequest(id 指定)+ 明細(`based-on` 検索)+ Patient を集め、
  検体グループに畳む。グルーピングは frontend の `groupBySpecimen` と同じ規則を
  Ruby で持つことになる(明細の contained Specimen から検体・採取管コードを読む)。
  二重実装だが、規則は「トップレベル項目を specimen_code でまとめる」だけなので許容する。
- **レンダラ**: 既存 `ThinreportsRenderer` の患者メタ抽出(氏名・カナ・性別・生年月日・年齢)を
  ラベルでも使うため、この部分を共通モジュールに切り出す。
- **ページ構成**: 1 ページ = ラベル 1 枚。用紙サイズは .tlf のユーザー定義サイズで
  ラベル用紙に合わせる(プリンタ・用紙が決まるまでは 60×40mm 程度で仮作成)。

### 5-2. プレースホルダー

**［提案］** ラベル .tlf の ID 規約(既存の `pt_*` 予約 ID と揃える)。

| ID | 内容 |
|---|---|
| `pt_id` / `pt_kana` / `pt_gender` / `pt_birthdate` | 既存レンダラと同じ患者メタ |
| `order_date` | 検査日 |
| `urgent` | 「至急」(text-block。通常時は hide) |
| `specimen_name` | 検体名 |
| `container_name` | 採取管(色)。「EDTA管（紫）」 |
| `items` | 検査項目の略称の並び |
| `barcode_img` | バーコード画像(image-block) |
| `label_number` | 番号の目視文字列 |

レイアウトのサンプルとマッピング表は `docs/report-mappings/lab-label-01.md` として、
実装時に既存帳票と同じ形で残す。

## 6. 画面

**［提案］** すべて検体検査一覧(`LabWorklistPage`)に足す。放射線検査一覧の
ステータス・操作列と同じ部品構成(`RowMenu` への畳み込み方も同じ)。

- **ステータス列**: 依頼済/受付済/(到着済)/中止。バッジの見た目は放射線と共通の
  スタイル(`.rad-worklist__status` 系のセレクタ共有)。
- **操作列**:
  - 依頼済 → 「受付」ボタン。
  - 受付済 → 「ラベル発行」。`<a href={/reports/lab_labels/{id}/pdf} target="_blank">` で
    新規タブに PDF。レイアウト未登録なら無効化してツールチップ(既存の `useReportLayoutStatus`
    と同じ照会を予約 canonical に対して行う)。発行済みかどうかで文言は変えない
    (再発行も同じボタン。同じ番号が刷られるだけなので区別する必要がない)。
  - 取消・中止は放射線と同じくケバブメニューに畳む。

## 7. 未決事項・申し送り

1. **スキャナ・プリンタの実機想定**。CODE128 で決め打ちしているが、運用機材が 2 次元
   スキャナ前提なら QR 直載せ(採番・対応表なし)の方が軽い。ラベル用紙のサイズも未確定。
   いずれもレイアウトは .tlf 側で吸収できるので、実装は進められる。
2. **到着確認の粒度**。Task はオーダー単位だが、到着は管単位で起きる。管ごとの到着を
   表すなら発行記録テーブルに到着列を足すか、独立 Specimen の status を使うか。
   到着確認の設計で決める。
3. **同一検体の複数本採取**。オーダー構造に本数が無いため対象外にした(§1)。
4. **色帯のカラー印刷**。`cap_color` は日本語の自由入力(「紫」など)なので、色見本を
   刷るならマスタに色コード(HEX)列を足す必要がある。モノクロのラベルプリンタなら不要。
5. **独立 Specimen への一本化**。受付時に Specimen を作り accessionIdentifier に
   ラベル番号を持たせれば、結果登録の Specimen とも到着確認とも一本の線になる。
   上流の Specimen identifier 検索の対応状況の確認も含め、到着確認の設計で判断する。
6. **report_layouts の帳票種別**。予約 URL 方式は 2 種類目の非 Questionnaire 帳票が
   出た時点で `kind` 列に改める。
7. **発行済みの見える化**。発行記録はテーブルに残るが、一覧に「発行済」を出すには
   backend への照会が要る(行ごとに引くか、日付でまとめて引くか)。到着確認と合わせて
   検討する。
