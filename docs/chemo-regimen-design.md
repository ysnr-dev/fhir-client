## 1. レジメンとは何か = マスタであってオーダーではない

| | オーダーセット | レジメンマスタ | レジメンオーダー(§7) |
|---|---|---|---|
| 何を表すか | 医師が育てる「いつも出す組み合わせ」 | 審査委員会で承認した施設共通の治療計画の雛形 | 患者に対する化学療法の指示 |
| 保存先 | backend DB(jsonb のフォーム値) | backend DB(正規化テーブル) | 上流 FHIR(ServiceRequest / MedicationRequest ほか) |
| 持ち主 | 院内共通 / 診療科 / 医師 の 3 段階 | 院内共通のみ(診療科は分類属性) | 患者と依頼医師 |
| 中身の解釈 | backend は解釈しない | backend が解釈する(薬剤名の解決・薬剤での検索) | — |

- ［事実］レジメンは審査委員会の承認を経て運用する施設共通の参照表で、医師個人が勝手に作るものではない。
  オーダーセットの 3 段階の持ち主は要らない。診療科・がん種(適応疾患)は分類属性として持ち、承認状態と承認日・承認者を持つ。
- ［決定］オーダーセットのように既存フォームの値を jsonb で持つ方式は採らない。mg/m² のような算出基準・上限値・薬剤の種類・
  相対日はどの既存フォームにも無く、backend 側で「この薬剤を含むレジメン」を引けることにも価値があるため、化学療法専用の
  正規化テーブルを持つ(§2)。
- ［決定］薬剤は「投与ステップ → 薬剤」の 2 階層。ステップは注射オーダーの RP(同じルートから同時に投与する薬剤のまとまり = 混注)に
  相当し、順序・相対日・手技・経路・点滴時間・器材はステップが持つ。将来オーダー化するとき `InjectionRpValues`
  (`frontend/src/fhir/injectionHelpers.ts`)に 1 対 1 で写せる(§3)。

### 1.1 命名

- **レジメン**(`regimen`)… 本ドキュメントの主題。抗がん剤・補液・制吐剤などの薬剤と、スケジュール・適応基準・副作用の束。
- **投与ステップ**(`step`)… レジメンの中の 1 回の投与単位(1 ボトル・1 ワンショット・1 処方)。注射の RP と同じ概念。
- **1 クール**… 投与期間 + 休薬期間。`cycle_days` は保存せず和として導出する。
- **相対日(Day)**… 1 クールの中の何日目か(1 始まり)。ステップが配列で持つ。

## 2. 保存の構造

```text
master_regimens                  … 本体
  regimen_code   unique(空なら 6 桁数字で自動採番。他マスタと同じ)
  name / short_name / name_kana
  department_code / department_name   診療科(非正規化。surgery_room_blocks と同じ持ち方)
  purpose        neoadjuvant | adjuvant | curative | palliative | other   治療目的
  setting        outpatient | inpatient | both                            実施区分
  treatment_days / rest_days     投与期間・休薬期間(日)。1 クール = 和
  planned_cycles                 予定クール数(NULL = 継続)
  emetic_risk    high | moderate | low | minimal                          制吐リスク分類(JSCO の区分)
  status         draft | approved | retired、approved_on、approved_by
  indication_note / discontinuation_criteria / dose_reduction_criteria / references_note   自由記述
  valid_from / valid_to / display_order / note / search_*
master_regimen_indications       … 適応疾患。病名マスタの管理番号 + 表示用の名称・ICD10
master_regimen_steps             … 投与ステップ(注射 RP 相当)
  display_order(投与順序) / name(見出し)
  days           jsonb [1, 8, 15]     相対日の配列
  usage_type     drip | one-shot | oral
  route_code / method_code / line_code       注射(既存の ROUTE_OPTIONS / METHOD_OPTIONS / LINE_OPTIONS のコード)
  infusion_minutes / rate(mL/h) / device_note(器材)
  usage_code / dose_days                     内服(用法コード・投与日数)
  note                                       投与時注意
master_regimen_drugs             … ステップの中の薬剤(step_id で結ぶ。regimen_code は検索用の冗長列)
  drug_role      anticancer | fluid | antiemetic | premedication | supportive | other
  medicine_code  → master_medicines
  dose_basis     bsa(mg/m²) | weight(mg/kg) | auc | fixed(mg/body) | unit(製剤単位)
  dose_value(基準値) / dose_unit / dose_max(上限値)
master_regimen_lab_criteria      … 適応基準のうち検査結果値
  category       renal | hepatic | blood | other
  analyte_code   JLAC11 分析物 5 桁(空可。CCr など計算値は名称だけ)、item_name、unit、lower_limit、upper_limit
master_regimen_adverse_events    … 副作用(term = CTCAE 用語の自由記述、grade 1〜5)
```

- ［決定］外部キーは張らず、子は `regimen_code`(薬剤は `step_id`)で結ぶ。整合性はコントローラの transaction で守る(他マスタと同じ)。
- ［決定］子は **配列を丸ごと置換**する(`order_sets` の entries と同じ)。`create` / `update` は本体 + 子を 1 リクエストで受け、
  送られてきた種別だけ置換し、`display_order` は配列順で振り直す。子の検証に落ちたら本体も登録しない。
- ［決定］薬剤名・薬価算定単位・YJ コードは保存せず、詳細 API が薬剤マスタを LEFT JOIN して添える(`Master::RegimenDrug.with_names`、
  `rad_dataset_detail.rb` と同じ)。内服の用法名も用法マスタから添える。適応疾患の病名・ICD10 だけは表示用に写す
  (病名マスタは差し替えが前提で、管理番号だけでは一覧が出せなくなるため)。
- ［決定］1 クールの長さは投与期間と休薬期間で持ち、和は導出する。添付図の「インターバル = 投与期間 + 休薬期間」をそのまま表にした。
  投与日が 1 クールを超えるステップは画面で止める(backend は日数を知らないので検証しない)。

## 3. 投与ステップ = 注射 RP との対応

| ステップ | `InjectionRpValues` | 備考 |
|---|---|---|
| `usage_type` drip / one-shot | `usageType` | oral は処方(`RpValues`)へ |
| `route_code` / `method_code` / `line_code` | `routeCode` / `methodCode` / `lineCode` | コード表を共用(`injectionHelpers.ts`)。手技は `methodForRoute` で経路から自動 |
| `infusion_minutes` | — | 注射側の「投与時間」は画面内の値で FHIR に残らないため、用法コメントに「点滴時間 120 分(2 時間)」と写す(§8.13 N-8) |
| `rate` | `rate` | レジメンが速度を指定するときだけ入る(空なら総量 ÷ 時間) |
| `days` | — | オーダー化時に開始日 + (day − 1) で実日付に展開する。注射の連日展開(`injectionDates`)の相対日版 |
| drugs `dose_value` × 算出基準 | `medicines[].dose` | 基準 × 体格 で力価(mg)を出し、**力価のままオーダーに載せる**(§7.2)。製剤数は払出で換算する |
| `device_note` | — | 注射側に器材の入力が無い。オーダー化時は用法コメントに写す |

- ［決定］**同時に開始する薬剤は 1 つの RP にまとめない**。mFOLFOX6 のオキサリプラチンとレボホリナートは同じ 2 時間を
  並行して落とすが、配合変化があるので別ルートの別ボトルで、混注ではない。RP は「同じ容器に混ぜる薬剤」なので、
  ステップを分ける。1 つの RP にすると注射箋・ラベル・調製指示が「混ぜてよい」と読めてしまう。
- ［決定］**「同時に開始する」ことは `note`(自由記述)に書く。専用の列は持たない**。「混ぜてはいけない」という
  安全上の事実は RP を分けたこと自体が構造で表しており、残る「並行して落とす」は時間の情報でしかない。
  点滴時間(`infusion_minutes`)を合計する処理はどこにも無く(化学療法の予約も所要時間を計算しない)、
  構造として読む当てが無い列を安全側の顔をして持つと、後から必ず「合計時間はこの列を見ているはず」と誤解される。
  両方のステップの `note` に相手の名前を書き(「オキサリプラチンと同時に開始」)、用法コメント経由で注射箋・
  ラベルまで運ぶ。適用画面でも登録前に `note` を出す。
  将来、投与時間の合計や無菌調製の指示(§7.6 E-3)が並行を計算に使うようになったら、そのとき構造化する。

## 4. 投与量の算出基準と単位

- ［事実］化学療法の用量は体表面積あたり(mg/m²)が多く、体重あたり(mg/kg)、AUC(カルボプラチン、Calvert 式)、固定量(mg/body、
  分子標的薬など)、製剤単位(補液 1 袋)が混在する。基準の種類が無いと「基準値 85」を解釈できないので `dose_basis` を必須にした。
- 上限値(`dose_max`)は基準値と同じ単位で、ビンクリスチン 2 mg のような「体表面積で計算しても超えない量」。基準値以上でなければ登録できない。
- 画面では薬剤を選んだとき、**薬効分類(薬価基準収載医薬品コードの上 4 桁)**から種類と算出基準の既定を決める
  (`defaultDrugSettings`、§8.9)。分からない薬剤だけ、注射容量 100 mL 以上の袋・瓶・キットを補液とみなす
  (名称の「点滴静注用」では判定しない。レボホリナート点滴静注用のような主薬が補液になるため)。種類も基準も後から直せる。

## 5. 適応基準

- ［決定］検査結果値の基準だけ構造化し(検査項目 + 下限 / 上限)、中止基準・減量基準・適応の補足は自由記述にした。
  第 1 段階では表示のみで、将来の投与前チェック(§7)がこの行を読む。
- 検査項目は JLAC11 の分析物 5 桁で持つ(材料・測定法の違いをまとめる。身長・体重と腎機能の読み取りと同じ流儀)。
  検査項目マスタの選択モーダル(`LabItemSearchModal`)から選ぶと `jlac11_code` の先頭 5 桁と名称・単位が入る。
  CCr のような計算値は分析物を空にして名称だけで持てる。
- 減量レベル表(レベル × 薬剤 × %)は第 1 段階では作らない(§7)。

## 6. 画面

- **一覧**(`pages/RegimenListPage.tsx`、`/regimens`): 名称・カナ / 診療科 / 状態 / 有効期間内のみ で絞り込み、行クリックで編集へ。
  メニューは「マスタメンテ > 化学療法 > レジメン」(承認制の施設マスタなので、医師が育てるオーダーセット(診療業務)とは置き場を分けた)。
- **編集**(`pages/RegimenEditorPage.tsx`、`/regimens/new`・`/regimens/:id`): 1 レジメン 1 ページ。本体と子をローカルの draft
  (`fhir/regimenHelpers.ts` の `RegimenDraft`)に持ち、「保存」で 1 リクエスト。
  - ［決定］外側を `<form>` にしない。薬剤・病名・用法・検査項目の検索モーダルは非ポータルの `Modal` で、フォームの中に開くと
    入れ子の form が外側の submit を誘発する(オーダーセット登録画面と同じ理由)。保存はボタンの onClick。
  - 検証は `validateRegimenDraft`(画面でしか分からないもの: 薬剤未選択・投与日の書式と重複・クール外の投与日・上限 < 基準値)に閉じ、
    `useValidationError` + `ErrorBanner` で出す。サーバーの検証(名称必須・有効期間の前後など)は `{errors}` をそのまま出す。
  - 読み込んだレジメンの id が変わったときだけ draft を作り直す(同じ id の再取得で入力中の値を上書きしない)。保存後は返ってきた
    詳細で draft を作り直す(採番されたコードと解決された名称を反映)。
  - ステップのカードは「見出し・投与日・用法種別」の行 + 用法(注射: 経路・手技・ライン・点滴時間・速度・器材 / 内服: 用法・投与日数)
    + 薬剤表。↑↓(ゴミ箱と同じ大きさのアイコンボタン)で順序、＋ 注射 / 内服のステップ で追加。見出し欄のラベルはステップ番号で、
    投与日・用法種別のラベルと同じ行に並べる。select はブラウザ既定の内部余白が input と違うので、画面の中だけ高さを実寸で
    固定して並んだ入力欄を揃えている(通常 30px、表の中 26px)。
  - ［決定］用法(注射: 経路・手技・ライン・点滴時間・速度・器材 / 内服: 用法マスタ・投与日数)は**医薬品の下**に置く。
    処方・注射のオーダー画面がどちらもその並び(医薬品の表 → 医薬品追加 → 用法)で、同じ順に読めた方が迷わない。
    内服の用法は処方と同じ「ラベル + 横 1 行(用法を選択 / 用法名 / 投与日数 N 日分)」にして、用法名が折り返さない幅を取る。
  - ［決定］薬剤 1 件は**表の 2 行**で表す(1 行目 = 医薬品名、2 行目 = 種類・算出基準・基準値・単位・上限値・コメント)。
    医薬品名は「オキサリプラチン１００ｍｇ２０ｍＬ注射液」のように長く、他の入力欄と同じ行に置くと必ず折り返して読みにくい。
    2 行の組は `tbody` で括り、名前行の下罫線を消して 1 件に見せる。
  - **Day 表**(読み取り専用): 列 = Day 1〜1 クール、行 = ステップ(見出しの名前だけ。薬剤名まで出すと横に長く、日の列が押し出される)。
    どの日に何が入るかを ● で示す。内服は開始相対日から投与日数ぶん連続で塗る。
  - 複製は保存済みの内容をサーバー側で写す(未保存の編集は写らない)。新しいコードで下書きになり、承認は引き継がない。

## 7. レジメンオーダー(患者への適用)

### 7.1 FHIR の構造

```text
ServiceRequest(ヘッダ = 適用 1 件)          intent = plan、status = active | revoked
  category      order-type|chemo-regimen、prescription-setting|inpatient/outpatient
  code          CodeSystem/regimen(code = レジメンコード、display = 名前)
  identifier    Identifier/regimen-instance = 適用 1 件の uuid
  instantiatesUri  http://fhir-client.local/regimen/{code}(マスタは backend。FHIR 上は URI で指すだけ)
  occurrenceDateTime  最初のクールの Day 1
  extension     StructureDefinition/regimen { cycleDays, treatmentDays, plannedCycles, bsa, height, weight }
  reasonReference / requester / order-department / order-ward / note  他のオーダーと同じ
ServiceRequest + MedicationRequest(日オーダー)  通常の注射・処方そのもの
  requisition   Identifier/regimen-instance = 上と同じ uuid
  extension     StructureDefinition/regimen-order { regimen(→ヘッダ), cycle, day, code, name }
```

- ［決定］日オーダーは**通常の注射・処方そのもの**にする。注射一覧・払出・実施入力・経過表・処方箋・承認は
  何も変えずに動く。どの適用の何クール目の何日目かは、ヘッダに焼く `regimen-order` 拡張と requisition で読む。
- ［決定］日オーダーはヘッダを `basedOn` で指さない。この codebase は「basedOn を持たない ServiceRequest = オーダーのヘッダ」を
  至る所で使っており(`isHeaderEntry`、カルテの `based-on:missing`、部門一覧の振り分け)、basedOn を付けると日オーダーが
  明細扱いになって全部の画面から消える。参照は拡張に置き、上流で検索できない分は患者 + 開始日以降のオーダーを読んで
  画面側で拡張を見る(`useRegimenDayOrders`。1 患者の化学療法は多くても数十件)。
- ［決定］注射の連日展開(`injection-series`)は使わない。Day 1, 8, 15 のような間引きは `InjectionSchedule` で表せず、
  `injectionSeriesDay` が「連日 8 日目」と誤読するため。日オーダーの requisition をレジメンの uuid に差し替え、series の
  拡張は落とす(`stampRegimenOrder`)。注射の編集・中止に出る「この日以降」はレジメンでは出ない(レジメン側が担う)。
- ［決定］ヘッダはカルテのカードにしない(看護指示と同じで、化学療法タブの暦で見る)。`karteTimeline` で外す。
  承認画面には「化学療法」として出る(`orderKindOf`)。
- ［決定］日オーダーのカードは、**種別バッジも「化学療法」**にする(`karteItemKindLabel`)。注射/処方であることより
  「化学療法の一部」であることが先に読めた方がよい。どちらのオーダーかは副題に「mFOLFOX6 C1 Day1 | 注射」と添える。
- ［決定］同じ日の注射ステップは 1 つの注射オーダー(RP = ステップ)、内服ステップは 1 つの処方にまとめる。ステップの
  見出し・器材・投与時注意は RP の用法コメントに写す(注射箋・ラベルに出る)。
- 来歴(Provenance)は `useCreatePrescription` が付ける(ヘッダ + 日オーダーの全ヘッダ + MedicationRequest が target)。

### 7.2 投与量の算出

- 体表面積は DuBois 式(`bodySurfaceArea`)。身長・体重の初期値は直近のバイタル(`useBodyMeasures`)で、画面で直せる。
  変えると全薬剤を出し直す(手で直した投与量も上書きされる)。
- 基準 × 体格 = 量(mg など)→ 上限値で頭打ち → 投与量換算マスタ(`master_medicine_dose_conversions` の `from_unit` = 基準の単位)で
  製剤数(薬価算定単位)に直す(`planDrugDose`)。製剤数は小数第 2 位までで、丸めは薬剤部の運用に任せる。
  ［決定］薬剤コメントに写すのは**力価だけ**(「148.75 mg」)。オーダーに載るのは製剤数(1.49 瓶)なので、
  指示の実体である力価を添える。算出の式は書かない — 体表面積・体重は適用のヘッダに、基準はレジメンマスタに
  残っており、カードや注射箋で毎回読ませるほどの情報ではない。
- ［決定］**入力は力価が基本**。抗がん剤も補液も、指示は「148.75 mg」「250 mL」の形で出すものなので、
  換算マスタで製剤数に直せる薬剤はすべて力価で入力し、製剤数は換算して下に併記する(「≒ 1.49 瓶(1 瓶 = 100 mg)」)。
  「1.49 瓶」だけでは何 mg か読めない。力価を直すと製剤数が追随する。
  - 製剤単位が基準のレジメン設定(補液の「1 袋」)でも、画面では容量・力価に直して入れる。単位は換算マスタにある
    ものから mL → mg → g … の順で選ぶ(`PACK_BASIS_UNITS`)。輸液は容量で指示するのが自然なため。
  - AUC(カルボプラチン)は Calvert 式で出す(§8.8)。GFR が出せないときだけ力価(mg)を手で入れる。
  - 換算を持たない薬剤(規格が読めない粉末バイアルなど)だけ、製剤数を直接入れる(力価は目安として出す)。
- ［決定］**オーダーに保存するのは力価**(`doseQuantity` = 148.75 mg。2026-09-06 に製剤数から変更、§8.5)。
  指示の実体が力価なので、カード・注射編集・実施入力・注射箋・ラベルはすべて力価が主になる。
  読む側は `doseQuantity.unit` を尊重する(手入力の注射・処方は製剤数 + 薬価算定単位のままで、混在しても壊れない)。
  **製剤数が要るのは払出だけ**で、払出・調剤の登録画面が換算マスタで力価 → 製剤数に直して初期値にする
  (`fhir/doseConversionHelpers.ts`)。換算を持たない薬剤(規格が読めない粉末バイアルなど)だけ製剤数のまま保存する。
  薬剤コメントには製剤数の目安を添える(「≒ 1.19 瓶」。払出の当たりになる)。
- ［決定］**内服の基準値は 1 日量**(処方の用量が 1 日量なので揃える)。カペシタビン 1000 mg/m² なら 1 日 1750 mg → 錠数。
- AUC(カルボプラチン)は Calvert 式 AUC × (GFR + 25) で出す(§8.8)。GFR は画面で出どころを選び、手で直せる。
- 換算行が無い薬剤(粉末バイアルで力価が読めないなど)も手入力。理由を行に出す。
- 使った身長・体重・体表面積はヘッダに残す(後から「どの体格で出したか」を辿れる)。

### 7.3 クール

- 適用は「開始日(Day 1)から N クール」を登録する(一度に 3 クールまで)。次のクールは詳細パネルの「第 n クールを登録」で、
  既定の Day 1 は前のクールの Day 1 + 1 クールの日数(移動していればそれに追随)。投与量はそのときの体格で出し直す。
- クールの Day 1 は保存せず、日オーダーの日付 − (Day − 1) から逆算する(`cycleStartDates`)。移動しても矛盾しない。
- 予定クール数に達すると登録ボタンを止める(継続なら止めない)。

### 7.4 中止・移動

- **中止**(日): 注射は注射の Task、処方は処方の Task を `cancelled` にする(既存の中止と同じ器)。「この日のみ / この日以降すべて」。
  実施済は止めない。中止取消は `requested` に戻す。
- **移動**(日): 内容は変えず日付だけ差し替えて同じ id へ PUT(`buildRegimenMoveBundle`。注射の時刻も注射日から決まるので一緒に動く)。
  「この日以降すべて」で後続の日も同じ日数ずらす(延期)。実施済は動かさない。
  - 入口は 2 つ。右ペインの投与日パネル(日付を入れて「移動」)と、**暦のドラッグ＆ドロップ**。
  - ［決定］暦の D&D は HTML5 の drag イベントで、投与日のマス(実施済だけの日は掴めない)を月内の別の日に
    落とすと確認モーダル(`RegimenMoveModal`)が開き、反映範囲(この日のみ / この日以降すべて)を選んで書き込む。
    落とし先は決まっているので、残る選択は範囲だけ。注射の中止と同じ 3 ボタンの形にした。
  - 「暦は表示に徹する」方針の例外。日を掴んで別の日に落とすのは暦でしかできない操作なので、
    ドラッグ状態と確認モーダルだけ暦が持ち、書き込みはモーダルが行う(暦自身は mutation を持たない)。
- **レジメンの中止**: ヘッダを `revoked` にし、未実施の日オーダーをすべて中止にする(1 transaction)。

### 7.5 画面

    どちらの器で出ているかは暦で判断することではない)。薬剤名も出さない。

    用法コメントへ写してあるので、マスタを引き直さずに読める(`dayOrderStepNames`)。3 つまでで残りは件数。
  - ［決定］**休薬期間を地の色で示す**。登録済みクールの Day 1(`cycleStartDates`)から各日のクール内の位置を出し
    (`cyclePositionOf`)、投与期間(`treatmentDays`)を過ぎた日に「休薬」と薄い地を敷く。投与の無い日でも

  - ［決定］タブの中を **カレンダー / レジメン詳細** で切り替える(`view` パラメータ。URL に残るのでリロード・共有で戻れる)。
    暦も詳細も「その適用を読む」ための面なので、右ペインに出し分けず左ペインに並べる。
    **レジメン詳細**(`RegimenDetailView`)は適用の概要(レジメン・状態・開始日・クール・体格・プロブレム・コメント)と
    クール一覧(クール / Day 1 / 投与日)で、投与日を押すと右ペインの投与日パネルが開く。左ペインは幅があるので
    概要は 2 列で読ませる。レジメンの中止もここに置く(確認だけで済む操作で、フォームを持たないため)。
- **右ペイン**(オーダーを作る・直す操作): 「化学療法」ボタン → レジメン選択(承認済かつ有効期間内)→ 適用フォーム(`RegimenApplyPanel`)。
  投与内容の表は「種類 / 医薬品 / 基準 / 投与量(力価入力 + 製剤数の併記)」の 4 列(§7.2)。算出の式は画面に出さず
  (基準と投与量があれば読めるので冗長)、薬剤コメントにだけ残す。ステップごとに別のテーブルなので、
  `table-layout: fixed` と明示幅でどのステップでも列位置が揃うようにする(処方内容の表と同じ考え方)。
  レジメン詳細の「第 N クールを登録」→ `RegimenCycleLoader`(ヘッダの id だけ渡し、何クール目か・Day 1 はそこで出す)。
  暦のマス → `RegimenDayPanel`
  (その日のオーダー・編集(注射編集 / 処方編集へ)・移動・中止)。暦は表示に徹し、操作は右ペインに集める(食事と同じ)。
  ［決定］投与日パネルのオーダーの中身は、カルテのカードと同じ組み(`.karte-rp` で RP ごとに薬剤 → 用法)にする。
  同じオーダーを 2 か所で違う形に見せない。「反映範囲」の fieldset は素のままだと周りと揃わないので
  `.injection-scope` にスタイルを当て、注射の編集パネルと共用する。

### 8.3 投与前チェック・レジメンの情報・体格の変化(§7.6 A-1 / A-2 / A-3、2026-09-06)

- **A-1 投与前チェック**(`fhir/regimenCheckHelpers.ts` + `components/RegimenPreCheck.tsx` の `RegimenLabCheck`):
  適応基準(`lab_criteria`)を患者の直近の検査結果に当て、適用フォーム・次クール登録フォームの**最上部**に
  「項目 / 基準 / 直近値 / 採取日 / 判定」の表を出す。上に「基準外 n 件 · 値なし n 件 · 7 日より前の結果 n 件」を添える。
  - ［決定］**基準外でも登録は止めない**。減量して続ける、当日の再検を待つ、という判断は医師のもので、
    システムが塞ぐものではない。読める形にすることだけを担う(バリデーションには入れない)。
  - ［決定］**単位は倍率を解釈して換算する**(`parseUnit` / `convertToUnit`)。血算は「X10*3/μL」で報告されるので、
    「/μL」で書かれた基準とそのまま比べると血小板 15.0 と 100000 を比べて必ず基準外になる。`10*n` と `10^n` の
    形だけを倍率とみなし(「1000/μL」のような書き方を取り違えないため)、μ を u に寄せ、全角を NFKC で畳んで比べる。
    基本単位まで違うときは**判定しない**(桁を取り違えた「適合」は、判定しないより危ない)。行に理由を出す。
  - ［決定］計算値(CCr・eGFR)は分析物コードを持たない基準行を**名称で**引き当てる(§5 のとおり、検査項目マスタに
    無い項目は名称だけで登録できる)。`derivedKeyOf` が「CCr」「クレアチニンクリアランス」「eGFR」などを拾う。
  - **採取日の古さ**: 開始日から `LAB_RESULT_STALE_DAYS`(7 日)より前の結果には「古い」を出す。次クールの登録では
    開始日が先の日付なので既存の結果はたいてい古くなるが、それは「投与前に採り直す」という正しい読みになる。
  - CCr は **Cockcroft-Gault**(`bodyMeasureHelpers.calculateCreatinineClearance`)。体表面積で補正する eGFR とは
    別物なので、画面では「計算値」と単位(mL/分)を添えて出す。**体重はこの画面で直した値を使う**ので、体重を
    変えると CCr も投与量と一緒に動く。プロファイルの「腎機能」区画にも CCr を並べた。
  - 検査結果は `useRecentLabResults`(旧 `useRenalResults` を汎用名に変更。中身は患者の検体検査を新しい順に 200 件)。
    分析物 5 桁での突き合わせは上流が索引していないので画面側で行う(腎機能・感染症と同じ流儀)。
- **A-2 レジメンの情報**(`RegimenInfoView`): 分類(治療目的・制吐リスク)・適応疾患・適応の補足・中止基準・減量基準・
  想定される副作用(CTCAE Grade)・参考文献を**投与内容の直前**に置く。
  ［決定］折り畳まない。投与量を決める前に読むべきもので、隠すと読まれない。位置を投与内容の隣にしたのは、
  減量基準と副作用が「この薬をいくつにするか」の判断材料だから(投与前チェックは「進めてよいか」なので最上部)。
- **A-3 体格の変化**(`RegimenBodyChange` + `compareWeight`): 次クール登録で前回(ヘッダに焼いた身長・体重・体表面積)を
  並べ、体重の差を「−9.4 kg（14.6%）」で出す。±10%(`WEIGHT_CHANGE_WARN_RATIO`)以上なら赤。差が 0 なら出さない。
  ［保留］次クールでヘッダの体格を更新するかは B-2(前クールの投与量の引き継ぎ)と一緒に決める。いまはヘッダに
  最初の適用の体格が残り、投与量だけがその時の体格で出る。

### 8.4 減量と前クールの引き継ぎ(§7.6 B-1 / B-2、2026-09-06)

- **B-1 減量**: 投与内容の表に**投与率(%)**の入力を足し、力価を 基準 × 体格 × 率 で出す(`planDrugDose` の第 4 引数)。
  率を入れられるのは基準から量を出せる薬剤だけで、補液(製剤単位)と AUC は出さない(`canReduceDose`)。
  - ［決定］**上限値は率を掛けた後に当てる**。先に上限で頭打ちにすると、減量したのに量が戻ってしまう。
  - ［決定］薬剤コメントに率を添えるのは**減量したときだけ**(「119 mg（80%）」)。標準量に「100%」と書いても
    情報が増えず、率を書いていないこと自体が「標準量」の意味になる。
  - ［決定］減量理由は**適用(クール)に 1 つ**で、薬剤ごとには持たない。理由は「前クールの有害事象」という
    ひとつの出来事であることが多く、薬剤の行に理由の欄を置くと表が横に伸びて読めなくなる。日オーダーの
    `regimen-order` 拡張に `reduction` として焼く。減量が無ければ焼かない(引き継いだ理由が残らないように)。
  - 入力欄は減量している薬剤があるときだけ「減量」の fieldset として出す。
- **B-2 前クールの引き継ぎ**: 次クール登録で「第 N クールと同じ量 / いまの体格で出し直す」を選ぶ。
  - ［決定］**既定は「前クールと同じ量」**。2 クール目以降で体格から出し直すと、手で入れた減量が黙って標準量に
    戻る(いちばん危ない側に倒れる)。減量中は選択肢に「減量中」の印を出す。
  - ［決定］引き継ぐのは率だけでなく**力価そのもの**(端数調整や手入力を持ち越すため)。単位が変わっていれば
    率だけを引き継ぐ(単位違いの数字をそのまま入れる方が危ない)。
  - 引き継いでいる間は体格を変えても量は動かない(体表面積と CCr の表示には効く)。率を直すと引き継ぎは外れる。
- **保存**: 薬剤 1 件の投与量は MedicationRequest の拡張 `regimen-dose`(`drug` = レジメンマスタの薬剤 id、
  `ratio`、`amount` + `unit` = 力価、`packs` = 製剤数)。
  - ［決定］`doseQuantity` だけでは前クールを再現できない(標準量の何%だったか、どの薬剤だったかが読めない)。
    レジメンマスタの薬剤 id を持たせて、クールをまたいでも薬剤を取り違えない。RP 番号と RP 内の順で焼く
    (`stampRegimenDrugs`)。
  - ［決定］**移動でも拡張を写す**(`carryRegimenDoses`)。移動は `parseInjectionForm` でフォームに戻してから
    組み直すので、写さないと日を動かしただけで減量の記録が消える。

### 8.5 投与量の保存を製剤数から力価へ(2026-09-06)

「力価で登録しても、カルテカード・実施入力などが製剤量になってしまう」という指摘を受けて、保存の形を変えた。

- **前**: `doseQuantity` = 製剤数(1.19 瓶)。力価は薬剤コメント(「119 mg」)だけ。カード・注射箋は括弧に力価が出るが、
  ラベル・払出・実施入力・注射編集には出ない。
- **後**: `doseQuantity` = 力価(119 mg)。薬剤コメントは製剤数の目安と率(「≒ 1.19 瓶（80%）」)。
- ［決定］**読む側は `doseQuantity.unit` を尊重する**。カード・詳細・注射編集(`medicineFromCoding` が `unit_name` に
  `doseQuantity.unit` を入れる)・実施入力・注射箋・処方箋・ラベルは元からそうなっていたので、保存を変えるだけで
  全部が力価になった。「mg で保存すると注射編集が『148.75 瓶』と出る」という当初の懸念(§7.2 旧)は事実誤認だった。
- ［決定］**製剤数が要るのは払出だけ**。注射の払出登録(`InjectionDispenseModal`)と処方の調剤登録(`RxDispenseModal`)は、
  換算マップ(`useMedicineDoseFactors`。`factors` に加えて薬価算定単位 `packUnits` も返すようにした)を読んでから
  初期値を作り、力価のオーダーは `toPackQuantity` で製剤数に直す(単位が薬価算定単位そのものなら従来どおり、
  換算が無ければ数量を空にして手入力)。`MedicationDispense.quantity` は製剤数 + 薬価算定単位のまま。
- 実施記録(`MedicationAdministration.dosage.dose`)は力価(119 mg)になる。医学的にはこちらが正しい記録。
- 換算を持たない薬剤(`input = "pack"`)は製剤数で保存する。同じオーダーの中で力価の薬剤と製剤数の薬剤が混在しうるが、
  読む側は単位を尊重するので問題ない。

### 8.6 完了・休止・中止理由・治療歴(§7.6 C-1 / C-2 / C-4、2026-09-06)

ヘッダの状態機械を閉じた。`active` → `on-hold`(休止)→ `active`(再開)、`active` / `on-hold` → `completed`(完了)、
`active` / `on-hold` → `revoked`(中止)。遷移はすべてレジメン詳細のボタンで、ヘッダを PUT する(`regimenStatusEntry`)。

- **完了**(`completeRegimenEntry`): ［決定］予定クール数に達しても**自動では完了にしない**。最後のクールを実施したか、
  途中で終えるかは医師が決める。中止と同じく未実施の日オーダーは止める(完了したのに予定が残るのは矛盾。
  Task の理由は「レジメン完了」)。完了日を `regimen` 拡張の `completedOn` に残す。
  予定クール数まで登録済みのときは「すべて実施したら『完了にする』で閉じます」と案内する。
- **休止 / 再開**(`holdRegimenEntry`): ［決定］ヘッダの状態だけを変え、**登録済みの日オーダーは触らない**。休止は可逆で、
  再開したら残りの投与日をそのまま使えるようにするため。休止中は次クールを登録できない(ボタンを出さない)。
  投与日を止めたければ投与日パネルから「この日以降すべて」を中止する(休止と独立の操作)。
- **中止理由**(`revokeRegimenEntry`): 区分(病勢進行 / 有害事象 / 患者希望 / 治療変更 / その他。`REGIMEN_DISCONTINUATION_REASON_OPTIONS`)
  と自由記述を `regimen` 拡張(`discontinuationReason` / `discontinuationNote` / `discontinuedOn`)に残す。
  ［決定］「完遂」は中止理由に入れない(それは「完了」)。理由を入れるので確認は `window.confirm` ではなく
  モーダル(`RegimenRevokeModal`)。一緒に止める日オーダーの Task には区分の名前を `statusReason` に写す。
- **日オーダーの中止理由**: 投与日パネルの「中止」に理由(自由記述 1 欄)を足し、`Task.statusReason.text` に入れる。
  中止取消(requested に戻す)で消す。投与日パネルの状態の横に出す(「中止 / 発熱のため延期」)。
- **クールの進捗**(`cycleProgressOf`): レジメン詳細のクール一覧に「進捗」列(予定 / n/m 実施 / 完了 / 中止)。
  「完了」は全部が実施済か中止で、少なくとも 1 件は実施済のクール。全部中止なら「中止」(投与しなかったクール)。
- **治療歴**(`RegimenHistoryView`、`view=history`): 化学療法タブの 3 つ目のビュー。患者の全適用(完了・中止を含む)を
  「レジメン / 期間 / クール(実施 / 登録 / 予定) / 状態 / 中止理由」で新しい順に並べる。期間の終わりは中止日か完了日
  (無ければ最後の投与日)。行を押すとその適用のレジメン詳細に切り替わる。
  ［決定］治療歴では適用のタブと暦の概要を出さない(患者単位の面で、1 つの適用を選ぶ面ではない)。
- 適用のタブの並びは 適用中・休止 → その他 の順(休止も「いま扱っている」適用)。

### 8.7 有害事象(CTCAE Grade)の記録(§7.6 C-3、2026-09-06)

- **保存の形**(`fhir/adverseEventHelpers.ts`): 1 件 = 1 Observation。category は独自の `adverse-event`(検体検査・
  バイタルの一覧に混ざらない。上流の category 検索で引ける)、`code.text` = CTCAE 用語(自由記述)、`valueInteger` = Grade、
  `effectivePeriod` = 発現日〜回復日(継続中は end 無し)、`note` = 対処・経過。適用とクールは `regimen-order` 拡張
  (regimen / cycle / code / name。日は持たない)で結ぶ。
  - ［決定］上流に AdverseEvent が無く、JP Core のプロファイルも無いので Observation にした。Flag と同じ手順で
    上流に AdverseEvent を足すこともできるが、患者コンパートメント・category 検索・拡張がそのまま使える方を採った。
    上流の受け入れは curl で確認した(独自 category + effectivePeriod + 拡張で 201、category 検索で 1 件)。
  - ［決定］用語は自由記述。レジメンマスタの「想定される副作用」を候補(datalist)に出す。CTCAE 用語マスタは §7.6 F。

- **入口**: レジメン詳細のクール一覧に「有害事象」列を足し、記録済みの用語と Grade(3 以上は赤、継続中は印)を並べ、

- ［決定］登録してもパネルは閉じない(他のパネルと違う)。1 クールに複数の有害事象を続けて入れるのが普通で、

### 8.8 Calvert 式(AUC の投与量、§7.6 B-3、2026-09-06)

カルボプラチンの投与量を **AUC × (GFR + 25)** で出す(`planDrugDose` の `case "auc"`。定数 25 は `CALVERT_ADD`)。
出した力価はほかの基準と同じ流れ(減量 → 上限 → 換算マスタで製剤数)に乗る。

- ［決定］**GFR は画面の入力欄**にした(`values.gfr` / `gfrSource`)。出どころを CCr(Cockcroft-Gault)/ eGFR /
  手入力から選ぶ。125 mL/分 での頭打ちは施設ルールなので、システムでは丸めず、医師が値を直す形にした
  (自動で丸めると「なぜその量になったか」が画面から読めなくなる)。
- ［決定］**eGFR は非補正に換算してから使う**(`uncorrectedGfr` = eGFR × 体表面積 ÷ 1.73)。Calvert 式が使うのは
  個別の GFR で、体表面積で標準化した eGFR をそのまま入れると小柄な患者で過量、大柄な患者で過少になる。
  CCr はもともと非補正なので換算しない。
- 既定は CCr、無ければ eGFR。身長・体重を変えると出どころに応じて追随する(CCr は体重、eGFR の換算は体表面積)。
  手で直すと出どころが「手入力」になり、以降は体格を変えても動かない。
- GFR が出せない(クレアチニンが無い・年齢や性別が未登録)ときだけ、従来どおり力価を手入力する。
- ［決定］基準の表示は **「AUC 5」**(`doseBasisLabel`)。AUC は単位を後ろに付けて読むものではない。
  マスタの `dose_unit` には Calvert 式で出した**力価の単位**(mg)を入れる(換算マスタを引くのに要る)。
- 入力欄は AUC の薬剤を含むレジメンでだけ出す(`regimenHasAuc`)。

#### 検証したこと(2026-09-06、テスト太郎)

検証用にレジメン 000003「カルボプラチン + パクリタキセル(TC)」(カルボプラチン AUC 5、1 日 + 休薬 20 日)を作った。

| 操作 | GFR | 力価 | 製剤数 |
|---|---|---|---|
| 既定(CCr、体重 50 kg) | 64.5 | 447.5 mg | 0.99 瓶 |
| eGFR に切り替え | 55.6 | 403 mg | 0.9 瓶 |
| 手入力 125 | 125 | 750 mg | 1.67 瓶 |
| CCr に戻して体重を変更 | 64.5 | 447.5 mg | 0.99 瓶 |

基準の列は「AUC 5」。コンテナ内 `npx tsc -b` 成功。

### 8.10 アレルギー照合・予約枠・薬剤部監査(§7.6 A-4 / D-3 / E-1、2026-09-06)

#### アレルギー照合(A-4)

- 照合は `fhir/allergyHelpers.ts` に置いた(処方・注射からも使える共通の器。`docs/order-common-backlog.md` §3)。
  `matchMedicationAllergies(yjCode, allergies)` が薬剤 1 件に当たるアレルギーを返す。
- ［決定］**銘柄(YCM)と成分(GCM)の両方を見る**。患者のアレルギーは「カロナール錠200(YCM + YJ コード 12 桁)」と
  「アスピリン(GCM + 一般名コード)」の 2 系統で登録される。一般名コードは YJ コードの規格・銘柄部を ZZZ にした形
  なので(`GCM4291410A1ZZZ` ⇔ YJ `4291410A1070`)、薬剤の YJ コードから両方を作って突き合わせる。銘柄だけ見ると
  成分で登録されたアレルギーを取りこぼす。成分一致には「・同成分」を添える。
- ［決定］**否定(refuted)は外す**。「疑ったが違った」記録で、警告に出すと本当の警告が埋もれる。
- ［決定］**登録は止めない**(投与前チェックと同じ)。薬剤の行に出し、フォームの上に件数のサマリを出す。
  重篤度が「高」なら赤、それ以外は橙。反応は title に入れる。
- **YJ コードを持たない薬剤は照合できない**(HOT コードマスタに無い医薬品。開発環境ではオキサリプラチンがこれ)。
  黙って通るので、実運用では薬剤マスタの取り込み範囲が照合の穴になる。

#### 外来化学療法室の予約(D-3)

- 枠の種別に `chemo`(化学療法予約)を足した(`scheduleHelpers.ts`)。リハ・栄養指導と同じで
  「同じ時間帯に複数の患者・定員あり・部屋が actor」の性質。
- ［決定］**予約はレジメンの適用と同じ transaction に入れない**。1 つの適用に投与日が何日もあり、日ごとに枠を取る
  ものなので、リハビリ・栄養指導と同じ「オーダーは先に立て、予約は投与日ごとに都度取る」形にした
  (`buildChemoAppointmentBundle`)。適用時に自動で取ると、枠が空いていないときに適用そのものが止まる。
- ［決定］`basedOn` は**その日の注射オーダー**を指す(適用ヘッダではない)。予約は日単位で、移動・中止もその日の
  オーダーに従うため。入口は投与日パネルの**専用の欄**「外来化学療法室」(`RegimenDayBooking` + `ChemoBookModal`)で、
  注射のオーダーごとに「予約 / 日時変更 / 予約取消」を出す。
  ［決定］予約はオーダーの中身ではなく「その日に化学療法室をいつ押さえるか」なので、注射オーダーの箱の中ではなく
  外に置く(反映範囲・移動と同じ形の枠)。
- 予約タブには「化学療法」バッジを出し、日時変更・取消は投与日パネルへ誘導する(オーダーと一組で動かすため)。

#### 薬剤部のレジメン監査(E-1)

- 注射ワークリストの行に「mFOLFOX6 C1 Day1」を出す(`regimenOrderOf`。日オーダーの拡張で判るので追加の取得が要らない)。

- 注射内容(`InjectionDetailPanel`)に「化学療法」の行(レジメン名・クール・体格・減量理由)と、薬剤ごとの

- 前クールとの差分は入れていない(ワークリストの 1 行から前クールを引くと患者ぶんの日オーダーを読むことになる)。

### 8.14 中止・完了の来歴、DO の封鎖、区分の引き継ぎ(§7.6 の着手順 7、2026-09-08)

#### N-10 進捗・状態を変える活動の来歴

代行入力の来歴(`docs/order-common-backlog.md` §2.4 / §2.5)は登録・編集にしか付いておらず、
**誰がレジメンを中止・完了・休止したか、誰が投与日を止めたかがどこにも残っていなかった**。

- **活動の語彙を広げた**(`fhir/provenanceHelpers.ts` の `OrderActivity`)。すべて既存の
  v3-DataOperation の語彙で、`CANCEL`(中止)・`REACTIVATE`(中止取消)・`COMPLETE`(完了)・
  `SUSPEND`(休止)・`RESUME`(再開)を足した。表示名は `orderActivityLabel`。
- **`buildActivityProvenanceEntry(targets, requester, activity, enterer)`** を足した。登録・編集の

  拾うが、中止・完了の Bundle には Task とヘッダの状態しか無いので拾えない。そこで
  **対象のオーダーと指示医師は呼ぶ側が渡す**形にし、中身の組み立ては共通にした。
  - ［決定］**target はオーダー(ServiceRequest)にする**。承認待ち一覧は target のオーダーから
    行を組む(`pendingApprovalRows`)ので、Task を指すと行が出ない。投与日の中止はその日の
    オーダー、レジメンの中止・完了・休止はヘッダを指す(日オーダーはヘッダから辿れる)。
- **書く場所**は `useUpdateRegimenDayStatus`(中止・中止取消)・`useRevokeRegimen`(中止)・
  `useUpdateRegimenStatus`(完了・休止・再開)の 3 つ。移動は `useMoveRegimenDays` が
  登録・編集と同じ来歴を書く(§8.13 N-5)。
- **承認一覧**の「活動」列は登録・編集の 2 値だったので `orderActivityLabel` に替えた

### 8.15 ヘッダの編集・クール単位の取消・重なりの検出(§7.6 の着手順 8、2026-09-08)

#### C-6 ヘッダの編集

適用のヘッダを右ペインで直せるようにした(`RegimenHeaderPanel`、`regimen-header`)。入口はレジメン詳細の
「適用を編集」。直せるのは**入外区分・予定クール数・対象プロブレム・コメント**の 4 つ。

- ［決定］**投与内容と体格は直させない**。投与内容はレジメンマスタのもので、体格は登録済みの投与量の
  根拠だから(出し直すと既に出したオーダーと食い違う。§7.6 B-8)。
- ［決定］**入外区分は次に登録するクールから使う**。登録済みの日オーダーは触らない(部門はもう動いている)。
  画面に注記を出す。
- 主目的は**予定クール数の延長**。これまでは予定数に達すると「第 N クールを登録」が止まり、続けるには
  適用し直すしかなかった。登録済みのクール数より小さい値は弾く。
- 更新は `useUpdatePrescription` を通すので、来歴(UPDATE)が付き、代行なら承認待ちに並ぶ。

#### C-7 クール単位の取消

レジメン詳細のクール一覧に「取消」を足した(`useDeleteRegimenCycle`)。そのクールの日オーダーを
薬剤・進捗ごと削除し、化学療法室の予約も取り消す。

- ［決定］**中止(Task を cancelled)ではなく削除**にする。中止だと暦に打ち消し線の行が残り続け、
  「予定していたが止めた」と「そもそも登録が誤りだった」が区別できなくなる。
- ［決定］**部門が動き出したクールは取り消せない**(`canDeleteCycle`。依頼済か中止の日だけのクールに限る)。
  受付・払出・実施の記録が宙に浮くため。その場合は日ごとの中止を使う。
- 進捗の Task も一緒に消す(他種別の削除では残る既知の課題だが、ここは対象が手元にある)。

#### N-13 の残り(日オーダーの削除)

§8.14 では「クール単位の取消ができてから削除を塞ぐ」としていたが、**塞がないことにした**。

- ［決定］クール取消(C-7)ができても、**移動で 1 日だけずれた投与日**のような単発の後片付けには
  日オーダーの削除しか道具が無い。塞ぐと逃げ場が消える。
- 代わりに**削除で予約も取り消す**ようにした(`useDeleteInjectionSeries`)。N-13 で問題だったのは
  「暦から黙って消える」ことと「予約が孤児になる」ことで、後者は実害なので直し、前者は
  削除モーダルの注意書き(クールから抜けること・中止と取消の使い分け)で伝える。

#### A-7 重なり・重複の検出

［決定］どれも**止めない**(投与前チェックと同じ。§8.3)。読める形にするだけ。

- **新規適用**(`applicationConflicts`): 同じレジメンが適用中・休止中なら「二重に適用しようとしていないか」、
  別のレジメンが進行中ならその名前を出す。
- **開始日**(`startDateWarnings`): 過去日はどちらのモードでも、「登録済みの投与日と重なります」は
  次クールの登録で出す(前のクールの最終投与日以前に Day 1 を置くと、暦の休薬期間もクールの進捗も読めなくなる)。
  日付の入力に追随する。

#### 検証したこと(2026-09-08、テスト太郎、seed の 900001 を一時的に承認済にして)

- 9/8 開始で適用 → もう一度レジメンを選ぶと「このレジメンは適用中です(mFOLFOX6、開始 2026-09-08)。
  二重に適用しようとしていないか確かめてください。」、開始日を 9/1 にすると「開始日が過去の日付です」。
- 「適用を編集」→ 予定クール数 12 → 2 に変更 → 詳細の「予定 2 クール」に反映。ヘッダの拡張は

### 8.16 部門・病棟へ化学療法であることを届ける(§7.6 の着手順 9、2026-09-08)

化学療法の日オーダーは**通常の注射・処方そのもの**(§7.1)なので、印を出さない画面では普通のオーダーに
見える。部門と病棟が「これは化学療法だ」と気付ける場所を揃えた。

#### E-5 処方側の印

内服の日オーダーは、注射側(§8.10 E-1)と違って処方のどの画面にも印が無かった。**処方一覧の内容欄**
(`RxWorklistPage`)・**表示のモーダル**(`RxOrderViewModal` の見出し行)・**調剤登録**(`RxDispenseModal` の処方共通)・
**処方の詳細**(`PrescriptionDetailPanel`)に「カペシタビン単剤 C1 Day1」と減量の印を出す。
どれも日オーダーの `regimen-order` 拡張を読むだけで、追加の取得は要らない。

#### E-6 注射ラベル

ラベルは薬剤名と力価しか刷っていなかった。

- **最下段にレジメンの行**を足した(`regimen`。「mFOLFOX6 C1 Day8 ｜ 減量」)。化学療法でなければ空行になる。
- **薬剤欄の最後に用法コメント**(ステップ名 / 点滴時間 / 器材 / 投与時注意)を足す。混ぜる人がボトルを見て
  「血管外漏出注意」に気付けるようにするため。［決定］**化学療法のときだけ足す** —— 薬剤欄は 4 行しかなく、
  手入力の多剤混注(TPN)で薬剤名が押し出されるのを避ける。
- backend が `regimen-order` 拡張を読むのは初めてなので、`InjectionReport::REGIMEN_ORDER_EXT_URL` と
  `InjectionMeta.regimen_label` / `regimen_reduction` を足した。
- ［事実］**ラベルは 60×40mm で、1 行に入るのは 6pt で全角 26 文字ほど**。長い投与時注意は行末で切れる
  (全文は注射箋にある。注射箋は用法の後ろに括弧書きで全部出す)。ラベルを増やす・大きくするのは
  施設の運用の話なので、ここでは「切れても気付ける」ところまでにした。
- レイアウトは `docs/report-mappings/gen_injection_tlf.py` を直して再生成する(手書きしない)。
  `usage` を y=97 h=9 から y=96 h=8 に詰め、空いていた最下段 y=104 h=8 に `regimen` を置いた。

#### E-7 化学療法だけの絞り込みと、化学療法室の当日一覧

- **注射一覧に「化学療法のみ」**のチェックを足した(画面側の絞り込み。`regimenOrderOf` があるかで判定)。
  薬剤部がその日の化学療法だけを抜き出して調製の段取りを組めるようにする。
- **外来化学療法室の当日一覧**(`/chemo-room-worklist`、部門業務メニュー)を新設した。
  ［決定］注射一覧(オーダー軸)と別の面にする。化学療法室はベッド・椅子の**時間割**で回る部門で、
  知りたいのは「誰が何時に来て、どのレジメンの何クール目で、投与が済んだか」だから。
  予約(`Appointment` の `service-type=chemo`)を軸に、患者は `_include`、注射オーダーと進捗は
  `basedOn` の id で引き直す(`useChemoRoomList`。2 往復)。

#### E-8 患者帯の「化学療法中」

適用中・休止中のレジメンがあるとき、患者帯に**点滴バッグのピクトグラム**を出す(`chemotherapy`)。
アレルギー・感染症と同じ作りで、押すと吹き出しにレジメン名・状態・開始日・予定クール数が並び、
化学療法タブへ飛べる。

- ［決定］注意区分マスタには載せない(感染症・アレルギーと同じ。適用から直接引く情報で、区分として
  登録させると二重管理になる)。`CAUTION_PICTOGRAM_KEYS` には足すが `NON_MASTER_KEYS` で選択肢から外す。
- ［決定］**色は赤ではなく紫**。感染症・アレルギーの赤は禁忌の合図で、化学療法中は「いま何をしている
  患者か」の情報なので、同じ赤にすると禁忌の重みが薄まる。
- 完了・中止した適用では出さない(いまの状態ではないため。治療歴は化学療法タブで読む)。

### 8.17 承認済の凍結と承認の記録、内容の検証(§7.6 の着手順 10、2026-09-08)

適用は `instantiatesUri` でレジメンコードを指すだけなので、承認済のレジメンを後から書き換えると
**過去のオーダーの根拠が変わってしまう**(§7.6 F-1)。版を持つのではなく、**承認済を凍結する**ことで
この問題そのものを無くした。

#### なぜ版管理にしなかったか

［決定］**承認済のレジメンは不変**にする。版管理(改訂のたびに版レコードを作る)と比べて:

- 版を入れると子 6 テーブルがコードと版の組で引くことになり、読み書き・表示順・薬剤名の結合・
  「この薬剤を含むレジメン」の逆引きが全部書き換えになる。さらに一覧・検索・適用の候補の
  すべてで「最新の承認済版」を選ぶ条件が要る。
- 不変にすれば、適用が持つコードだけで当時の内容が一意に決まる。版の識別子が要らない。
- N-2(マスタ編集で薬剤 id が振り直され、次クールの減量が戻る。§8.14)の**根本原因も消える**。
  医薬品コードでの引き当ては保険として残す。
- 改訂の契機は年に数回で、審査を通すので人が新しい版として意識する。複製で新しいコードにするのと
  運用の手間は変わらない。
- ［決定］代わりに **`copied_from_code`(複製元のコード)を 1 本だけ持つ**。これが無いと改訂の系列が
  名前でしか繋がらず、「このレジメンで何人治療したか」をコードをまたいで数えられない。
  将来ここを軸に版管理へ育てられる。

#### 凍結の範囲

- 変更できないのは**本体の内容と子**。承認済・廃止で内容を送ると 422 で拒む(`frozen_change?`)。
- **状態・有効期間・表示順だけは動かせる**(`FROZEN_EDITABLE_ATTRS`)。使うのをやめる・並び順を
  変えるのは内容の変更ではなく、運用に必須のため。
- ［決定］**承認済・廃止から下書きには戻せない**。戻せると「下書きにしてから直す」で凍結をすり抜ける。
  使わないようにするときは廃止にする。誤って承認したレジメンは廃止にして残す。
- **削除は下書きだけ**。承認済・廃止は施設の記録で、患者への適用が指している。

#### 承認の記録

`status` が承認済に変わったときに、**サーバーが**承認日(今日)と承認者(ログイン中の医療従事者の
practitioner id)を入れる。画面の手入力欄は消し、表示だけにした(名前は `usePractitionerOptions` で引く)。
認証なしモード(開発)ではパラメータの `approved_by` を通す(オーダーセットの持ち主と同じ扱い)。

#### 内容の検証(§7.6 F-2)

［決定］**下書きは緩く、承認で厳しく**。書きかけを保存できるのは編集の前提で、承認は「これで運用する」
という宣言だから。画面の `validateRegimenDraft` は入力中の案内で、API を直に叩けば素通りするので、
どの入口からでも効く検証を backend に置いた(`validate_content!`)。

- 常に効く: 投与日が 1 クールを超えない、内服が `days + dose_days − 1` でクールをはみ出さない。
- 承認のときだけ: ステップがある、各ステップに薬剤がある、全薬剤に基準値と単位がある、
  薬価基準から削除・経過措置になった医薬品を含まない。
- ［事実］薬価基準の日付欄は「なし」を `99999999`(削除日)や `0`(経過措置日)で表す。空欄にならないので、
  **8 桁で 99999999 でないときだけ実在の日付**とみなす(`retirement_date`。frontend も同じ規則)。
  開発 DB では削除日は全件 99999999、経過措置日は 683 件が 2026-03-31。

#### 画面

- 承認済・廃止を開くと、内容の入力を `fieldset[disabled]` でまとめて止める(206 個の入力・ボタンが
  一度に止まる)。上に「直すときは『複製』して…こちらを廃止にします」と出し、削除ボタンは消す。
- 「運用」の欄を独立させ、状態・有効期間・表示順だけを凍結中も触れるようにした。状態の選択肢からは
  下書きを外す(サーバーが拒むため)。
- 凍結中の保存は**運用の項目だけを送る**(`operationalPayloadFromDraft`)。子を送ると内容の変更として
  弾かれるため。
- 薬剤の行に削除・経過措置の印を出す(選んだ時点で気付けるように)。複製元があれば見出しの下に出し、
  元のレジメンへ飛べる。

#### 検証したこと(2026-09-08)

- `rspec spec/requests/master/regimens_spec.rb` 24 件成功。承認済の内容変更・子の置換・削除・
  下書きへの差し戻しがすべて 422、状態と有効期間の変更は 200、承認で承認日が入る、
  クールを超える投与日と内服のはみ出しが 422、基準値なしでの承認が 422、経過措置の医薬品で 422
  (削除日 99999999 は「なし」として扱われる)を確認。
- 画面: seed の 900001 を承認済にして開くと、内容の 206 個の入力がすべて無効、運用の 4 項目だけが
  有効、承認欄は「2026-09-08 / 児玉 義憲」。有効終了日を 2026-12-31 にして保存でき(内容は送らない)、
  「複製」で下書きの複製に移り「複製元: 900001」が出る。確認後に片付けて下書きへ戻した。
- コンテナ内 `npx tsc -b` 成功。

  同じく組み直すので、`preserveRegimenStamp` で印を写している(§8.13 N-1)。**日オーダーに新しい拡張を足すときは

- 薬剤の種類・算出基準の既定は薬効分類で決める(§8.9)。分類が無い薬剤だけ注射容量で補液を拾う。

  2 期間は days = [1, 22] + dose_days = 14 で表す。
- **承認済・廃止のレジメンは内容を凍結**してある(§8.17)。直すときは複製して新しいコードで承認し、元を廃止にする。

  (`useApplicableRegimens`)。
