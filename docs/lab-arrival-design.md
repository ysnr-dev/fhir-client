# 検体到着確認の設計メモ

検体ラベル(`docs/lab-label-design.md`)の続き。採取した検体が検査室に着いたことを、
ラベルのバーコード(検体ラベル番号)をスキャンして記録する。前メモで持ち越した
§7-2(到着の粒度)・§7-5(Specimen への一本化)・§7-7(発行済みの見える化)を
ここで決める。

調査日: 2026-08-19。上流 fhir-server の `Task?focus=` 検索・`ServiceRequest?_id=` 検索
(+ `_revinclude` / `_include` の併用)は同日に開発サーバーの実機で動作確認済み。
本メモの範囲(§2〜§4)は 2026-08-19 に実装済み。同日中に §6-1 の一本化(台帳を上流の
Specimen へ移す)も実装したため、§2〜§4 に出てくる `lab_label_records` ベースの実装は
Specimen ベースに置き換わっている。現行の形は §6-1 を参照。

- **［事実］** = FHIR R4 / JP Core の仕様、またはこのリポジトリ・上流の実装で確認した内容
- **［導出］** = 仕様・実装から論理的に導ける内容
- **［提案］** = 本ドキュメントの設計提案

## 1. スコープ

到着確認でやりたいことは次の 3 つ。

1. 検体(採取管)1 本ずつの到着を、バーコードのスキャンで記録する
2. オーダーの全部の管が着いたら、一覧のステータスを「到着済」に進める
3. 検体検査一覧で、管ごとの発行・到着の状況が見える

### 含めないもの

- **結果登録との接続**(到着済でないと結果を登録できない等の制約)。運用を見てから(§6-4)。
- **独立 Specimen リソースの作成**。今回も見送る(§2 の設計判断と §6-1)。
- **未着レポート**(発行済みで未到着の検体の横断一覧)。台帳にデータは揃うので、
  必要になったら画面を足すだけでよい(§6-2)。

## 2. 到着の粒度と記録先

**［導出］** 到着は管単位で起きる(1 オーダーの血算の管だけ先に届くことがある)。
一方、進捗の Task はオーダー単位で持っている(`labTaskHelpers.ts`)。粒度の違いは
「管ごとの事実の記録」と「オーダーごとの進捗表示」を別の場所に持てば解消する。

**［提案］** 管ごとの到着は **`lab_label_records` に列を足して記録する**。

```ruby
add_column :lab_label_records, :arrived_at, :datetime   # 到着時刻。NULL = 未到着
add_column :lab_label_records, :arrived_by, :string     # 記録したユーザーの login_id(認証なし運用では NULL)
```

発行記録はもともと「バーコード番号 → オーダー・検体・採取管」の台帳なので、
番号のスキャン → 行の特定 → 到着の記録が 1 テーブルで一本の線になる。
ラベルを発行していない管はバーコードが無くスキャンもできないため、
「到着を記録できるのは発行済みの管だけ」という制約が構造から自然に出る。

設計判断: 採らなかった代案。

- **到着時に FHIR の独立 Specimen を作り、status / receivedTime で表す** — FHIR 的には
  素直だが、(1) 今はその Specimen を読む画面・処理が無く、作りっぱなしになる、
  (2) 結果登録が別に独立 Specimen を作る実装のままなので二重になる、
  (3) オーダー削除時の掃除など管理対象が増える。結果登録との統合を設計するときに
  改めて判断する(§6-1)。それまで到着の事実は backend の台帳で持つ。
- **管ごとに Task を作る** — Task がオーダー単位である現行設計(放射線と共通)を
  崩す割に、得られるのは台帳の列 1 本で足りる情報だけ。

**［提案］** オーダー単位の Task は、**その時点のオーダー内容(検体グループ)の全部に
到着記録が付いたら `completed`(到着済)へ進める**。判定と Task 更新は画面側(frontend)が行う。

- 判定を「発行記録が全部到着したか」ではなく「今のオーダーの検体が全部到着したか」に
  するのは、発行後にオーダーが訂正されることがあるため。検体が減っていれば古い
  発行記録は無視してよく、増えていれば新しい管の到着を待つのが正しい。
  オーダー内容を知っているのは FHIR を読む frontend なので、判定もそちらに置く。
- Task の書き込みは既存の `useUpdateLabTaskStatus`(transaction Bundle)をそのまま使う。
  `completed`(到着済)の語彙・バッジ・絞り込みはラベル機能の実装時に用意済み。

## 3. API

**［提案］** `lab_label_records` の読み書きを backend のプレーン JSON REST で足す。
認証は `/reports` と同水準(`UserAuthentication`。ログインセッション必須)。

| メソッド | パス | 役割 |
|---|---|---|
| POST | `/lab_labels/arrivals` | 到着の記録。body `{label_number}` |
| DELETE | `/lab_labels/arrivals/:label_number` | 誤スキャンの取消(arrived_at を消す) |
| GET | `/lab_labels?order_ids=a,b,c` | オーダーごとの発行・到着状況(一覧・スキャン画面の表示用) |

- POST は冪等。既に到着済みの番号は上書きせず `already_arrived: true` と元の時刻を返す
  (二重スキャンは日常操作なのでエラーにしない)。
- 応答には行の中身(`order_fhir_id` / `specimen_code` / `container_code` / `arrived_at`)を
  含める。画面はこれを手掛かりに上流からオーダー文脈を引く(§4-1)。
- エラー: 番号が台帳に無い → 404 `unknown_number`。11 桁の数字でない・チェックデジット
  不一致 → 422 `invalid_number`(スキャナの誤読・手入力ミスをここで弾く。
  検証は `LabLabelRecord.check_digit` を使う)。
- GET は `order_ids`(カンマ区切り)でまとめて引く。検体検査一覧が表示中の行の
  状況をまとめて取るための形(採取管マスタの `container_code` 複数指定と同じ流儀)。
- `arrived_by` は `current_user&.login_id`(認証なし運用・administrator では NULL)。

## 4. 画面

### 4-1. 到着確認(スキャン)画面

**［提案］** 部門業務メニューに「検体到着確認」(`/lab-arrivals`)を足す。スキャンに
専念する画面で、検体検査一覧とは分ける(一覧は日付で絞って眺める画面、到着確認は
届いた箱の管を日付に関係なく次々に読む画面で、動きが違う)。

- **スキャン入力欄**: 常時フォーカス(処理後に必ずフォーカスを戻す)。ハンディの
  1 次元リーダーはキーボード入力 + Enter で届く前提なので、Enter で確定する。
  手入力のフォールバックも同じ欄(11 桁 + チェックデジットを送信前に検証)。
- **1 スキャンの流れ**:
  1. POST `/lab_labels/arrivals` で到着を記録
  2. 応答の `order_fhir_id` で上流から
     `ServiceRequest?_id={id}&_revinclude:iterate=ServiceRequest:based-on&_revinclude=Task:focus&_include=ServiceRequest:subject`
     を 1 リクエスト読み(**［事実］** この組み合わせは実機確認済み)、患者・検体・進捗を得る
  3. 結果フィード(新しい順)に 1 行積む: 時刻、患者番号・氏名、検体（採取管）、結果
     (「到着」/「到着済み(HH:MM に記録済み)」/ エラー)
  4. 今のオーダーの検体グループ全部に到着記録が付いていれば、Task を `completed`
     (到着済)へ更新し、フィードに「全検体到着 → 到着済」と添える
- **確認のための表示**: フィードの行に患者氏名と検体を必ず出す。スキャンした管と
  画面の表示が食い違ったら貼り間違いに気付ける(ラベルの目的そのもの)。
- **中止オーダーの検体**: 到着は記録した上で、フィードに「このオーダーは中止されています」と
  警告を出す(記録してから文脈を読むため。現物が届いた事実は残す方が調査に役立つ)。
  行の「取消」でそのまま消せる。
- **誤スキャンの取消**: フィードの各行に「取消」(DELETE)。台帳の arrived_at が消え、
  Task を到着済まで進めていた場合は受付済へ戻す。

### 4-2. 検体検査一覧

**［提案］** 検査内容の検体グループ行(「血清（分離剤管） | TP・AST」)に、管ごとの
状況バッジを添える: **未発行**(台帳に行が無い)/ **発行済** / **到着済**。
データは表示中の行のオーダー id で GET `/lab_labels?order_ids=...` を 1 回引く。
これが前メモ §7-7(発行済みの見える化)の答えになる。

**［提案］** ケバブメニューに「到着済にする」(手動遷移)を足す。スキャナが使えない
場面のフォールバックで、受付済のときだけ出す。手動遷移では管ごとの到着記録は
付かない(Task だけ進む)ことを許容する — 台帳はスキャン運用の記録であって、
Task の進捗の必要条件にはしない。

## 5. 実装メモ(流用する既存部品)

- 番号の検証・台帳: `LabLabelRecord`(`check_digit` 実装済み)
- Task の語彙・遷移・書き込み: `labTaskHelpers.ts` / `useUpdateLabTaskStatus`
  (`completed` = 到着済のバッジ・絞り込みは実装済み)
- 1 オーダーの文脈取得: `ServiceRequest?_id=` + revinclude(§4-1。fetchLabWorklist と
  同じ振り分けロジックを単一オーダー向けに使う)
- グルーピング: `groupBySpecimen`(到着判定の「今のオーダーの検体グループ」に使う)

## 6. 未決事項・申し送り

1. **独立 Specimen への一本化(実装済み 2026-08-19)**。台帳を backend のテーブルから
   上流の Specimen へ移した。現行の形:
   - **発行**(`LabLabelReport`)が管ごとに独立 Specimen を作る。accessionIdentifier =
     ラベル番号、request = ヘッダオーダー、type / container = 検体・採取管。二重発行は
     conditional create(`If-None-Exist: request=...&type=...`)で防ぎ、再発行は既存
     Specimen の番号をそのまま刷る。発行時点では status を付けない(未採取)。
   - backend に残るのは番号の採番だけ(`lab_label_numbers`。行 = 採番 1 回で、番号は
     id + チェックデジット)。`/lab_labels` の到着・照会 API は廃止し、frontend は
     FHIR を直接読み書きする。
   - **到着**は Specimen の `receivedTime` + `status: available`(取消はその削除)。
     記録者はローカル拡張 `lab-arrival-recorder`(Practitioner 参照)。スキャンの逆引きは
     `Specimen?accession=`、管の更新とオーダー進捗(Task)は 1 つの transaction で書く。
   - **一覧・揃い判定**は ServiceRequest 検索への `_revinclude=Specimen:request` で
     同じ応答から読む(発行済み = Specimen がある、到着済み = receivedTime がある)。
   - **結果登録**はオーダーに紐付くとき、材料が一致するラベル Specimen を参照する
     (`labResultHelpers` の planSpecimens。referenceOnly で、書き換え・削除はしない)。
     所有権はラベル番号の有無で見分ける(`isLabelSpecimen`)。ラベルの無い材料や
     オーダー未紐付けの結果は、従来どおり結果側で Specimen を作って所有する。
     結果を削除してもラベル Specimen(発行・到着の記録)は残る。
2. **未着レポート**。「発行済みで N 時間未到着」の横断一覧。台帳(issued/arrived)で
   作れるが、まず日々の運用で必要かを見る。
3. **オーダー訂正で消えた検体の発行記録**。行は残るが、到着判定は今のオーダー内容で
   行うため実害はない(前メモ §3-3 と同じ扱い)。スキャンされたら「オーダーに
   この検体はありません」と警告する余地はある。
4. **結果登録との接続**。到着済を結果登録の前提条件にするか、結果登録時に自動で
   到着済へ進めるか。検査室内の運用が固まってから。
