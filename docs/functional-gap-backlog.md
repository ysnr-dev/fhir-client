# 機能一覧(functional.xlsx)との照合 — 取り込み候補

`backend/tmp/functional.xlsx`(498 機能、機能名称 / 機能概要 / 機能詳細の 3 列。大規模病院向け商用電子カルテの機能一覧)を
本リポジトリの実装(readme.md・docs/features/*.md・docs/*-design.md・frontend/src・backend)と突き合わせ、取り込めそうな機能を
**既存機能の拡張**と**新規機能**に分けて整理したもの(2026-10-08)。

凡例:

- **［対応物］** = 本リポジトリに既にある土台
- **［不足］** = xlsx の機能詳細にあって本リポジトリに無い要素
- **［当たり］** = 実装の置き場所の目安(FHIR リソース・既存部品)
- **既載** = 既存の backlog / design に同じ課題が書いてある
- 必要度 **高 / 中 / 低** は、日本の病院(急性期〜ケアミックス)の電子カルテとしての必要度

## 0. 結論の要約

- 498 機能のうち、**オーダー 16 種別・部門ワークリスト・カルテ・看護(指示簿・計画・サマリ・プロファイル)・パス・
  化学療法・予約枠・病棟マップ・データ抽出・レセコン連携・マスタ群**は骨格が揃っており、機能名単位では
  過半が「既にある」か「拡張候補」に入る。
- 無いものは次の塊に集中する。
  1. **制度・ガイドライン要件**: 職種別アクセス権限、制限患者(VIP)、閲覧ログ、自動ログオフ・パスワードポリシー、
     修正・削除の理由、診療記録の一括出力(開示・監査)
  2. **患者誤認・投与事故の防止**: 顔写真、同姓同名警告、死亡患者のオーダー抑止、外泊中・退院後のオーダー検知、
     食物アレルギーと食事オーダーの照合、輸血の払出記録と突合・2 名確認、リストバンド + 患者認証
  3. **まるごと無い部門・業務**: 透析(血液浄化)、地域連携(紹介の台帳と返書管理)、チーム医療(NST / ICT / 褥瘡)、
     看護必要度、管理日誌、麻酔科術前診察、栄養管理計画書、DPC コーディング
  4. **入院運用の横断画面**: ベッドスケジュール(病床ガント)、病床稼働の集計、入退院文書の作成状況一覧、
     看護師の「患者の 1 日」ワークシート、業務分担(勤務帯の受け持ち)
  5. **帳票**: 予約票、麻薬施用票、持参薬鑑定書、カルテ控え印刷、病棟 × 日の一覧印刷、退院サマリー PDF
  6. **入力効率**: 文例・定型文、科別頻用病名、患者別セット、処方の RP 単位の中止・再開、入院処置の継続指示、
     祝日マスタ、予約の連続取得・仮予約
- xlsx 側で**対象外**にしたもの: IC カード・静脈・指紋認証、カードリーダ、スクリーンセーバ常駐、外部 EXE、
  Windows クライアント配布(マスタアップロード・端末マスタ・プリンタマスタ・ランチャー・SE ツール)、
  ベンダー製品連携(DICS-PS・Simplewrite・ARENA・HumanBridge・麻酔器・勤務割)、排他ロック(楽観ロックで代替)、
  保険情報の保持(レセコン正本)、IME 辞書、Excel チャート、移行ツール。
- 海外 EHR(Epic・NHS ほか)との照合で出た候補は §5(2026-10-18)。要フォロー推奨の追跡、退院時の薬剤調整、警告のガバナンス、
  NKDA、計算スコア、Health Maintenance、SMART on FHIR アプリ起動が上位。
- 国内の既出候補にも海外照合にも無いものは §6(2026-10-27)。麻薬帳簿、ライン・ドレーン管理、感染サーベイランス、植込みデバイスの UDI 台帳、
  退院カルテの点検、ADR 報告、オンライン診療が上位。上流は Immunization・Device・RelatedPerson・Group・`$export` を既に持つ。

## 2. 分野別の候補

### 2.1 認証・権限・監査(ガイドライン要件)

- **職種別アクセス権限**(新規、高)
  - ［対応物］ホームの職種分岐(`homeCards.ts` の `defaultHomeCards`)、画面側の「医師か」判定(オーダーセット・チャート定義)。backend は職種を知らない。
  - ［不足］職種ごとの文書種別(書込・閲覧)・画面・一覧・プロファイルへの既定権限と、利用者ごとの上書き。
    師長などの役職権限(看護サマリー承認の `features/nursing.md` が「未実装」と明記)。
  - ［当たり］backend に role × 機能のマトリクス、`/auth/me` で返して `useCanXxx` に集約、`/master`・`/reports` の書込で検証。
- **制限患者(VIP・職員患者)**(新規、高)
  - ［不足］患者ごとに閲覧できる利用者を限定、閲覧時の再認証・警告、閲覧の記録。院外利用者(連携先・治験モニター)の閲覧範囲。
  - ［当たり］`Flag(category: security)` か backend `patient_access_restrictions`、`KartePage` 入口と FhirGateway で判定。
- **アクセスログ参照**(新規、高)
  - ［対応物］上流 `AuditEvent` は OAuth クライアント単位のみ(`server-improvement-backlog.md` 既載)。
  - ［当たり］backend の `/fhir` プロキシで患者に関わる読み取りを `access_logs`(user, patient, resource, at)に記録し、管理画面に利用者別・患者別の一覧。上流を直さず済む。
- **ログインポリシー・自動ログオフ**(拡張、高)
  - ［対応物］`User`(has_secure_password、8 文字以上)、セッション 12 時間固定。
  - ［不足］文字種条件・誤入力ロック・有効期限・本人によるパスワード変更、無操作時の画面ロック(外来 / 病棟で時間を分ける)、前回ログイン日時。
  - ［当たり］`users` に failed_attempts / locked_at / password_changed_at、施設設定にポリシー、frontend にアイドルタイマー + ロック画面。
- **修正・削除の理由**(拡張、中〜高)
  - ［対応物］`_history`、Provenance(登録・編集)。削除・中止は理由を持たない(`order-common-backlog.md` §2 障壁 4)。
  - ［不足］文書種別・科ごとに修正・削除時の理由選択を求める、理由の定型文マスタ。警告を無視した理由(共通チェック (37))は `advisory-design.md` で対応済み。
  - ［当たり］`Provenance.reason` / `activity=DELETE`、理由候補は backend の小マスタ。
- **承認要否の設定**(拡張、中): 研修区分・科・項目(麻薬・抗がん剤)ごとに事前 / 事後承認を設定。
  「承認前でも部門へ流す」方針と衝突するので事前承認は要検討。
- **権限の委譲**(拡張、中): 不在時に期間を切って他医師へ承認を委譲(`approval_delegations`、`useCanApproveOrder` に加味)。

### 2.2 診療記録の出力・文書管理

- **診療記録出力(患者 × 期間の一括 PDF)**(新規、高)
  - ［対応物］帳票はオーダー単位・回答単位のみ。診療経過記録(カルテ 2 号用紙)は「カルテ印刷」(印刷用ページ `pages/KartePrintPage.tsx` + `window.print`、期間指定・履歴の差分つき)で印刷できる。
  - ［不足］表紙(入退院歴)・1 号用紙(カルテ 1 号用紙: 患者・保険・病名・労災)・病名 / プロブレムリスト・退院サマリー・プロファイル・診療経過記録(シェーマ・埋め込み文書を含む)・看護計画・経過表・看護プロファイル・レポート・検歴・指示簿を 1 つの PDF に束ねる。複数患者の一括出力。
  - ［当たり］`GET /reports/patients/:id/records.pdf?from&to&sections=`。長文は ThinReports に向かないので HTML → PDF(Gemfile 変更 = 再ビルド)か frontend の印刷用ビュー + `window.print`。まず「診療経過記録 + 病名 + プロブレム + 退院サマリー」から。保険情報はレセコン(`patientgetv2`)から。
- **カルテ控え・オーダー控え・指示歴の印刷**(拡張、高): カルテ控え(2 号用紙)はカルテ印刷で対応済み。オーダー控え・指示歴は同じ印刷用ページの基盤で足せる。
- **病棟 × 日の一覧印刷**(拡張、中): 入院患者一覧・病棟マップ・移動予定・指示簿・注射実施シート・検歴。エンドポイントを 1 種類作れば横展開できる。
- **同意書の状態管理と文書の横断一覧(文書受取管理)**(拡張、高)
  - ［対応物］文書テンプレート(docx / xlsx、PDF / 画像の様式に項目を置いて入力し PDF と回答を残す。2026-10-24)、ファイルタブ。手術・輸血の「同意書確認」はチェックボックスのみ。
  - ［不足］文書の状態(作成 → 印刷 → 同意済 → 原本保管 / 受取済)、スキャン原本との結び付け、横断一覧、過去文書を見ながらの作成、印刷部数。
  - ［当たり］`DocumentReference.docStatus` + 拡張(同意日・保管日)、`/document-worklist`、手術・輸血の確認欄を文書参照に置換。
- **入退院文書の作成状況一覧**(新規、高) — **対応済み(2026-10-10、`/admission-documents`。入院診療計画書・退院時サマリー・看護サマリー)**
  - ［対応物］退院時サマリーの督促 Task だけ。
  - ［不足］入院診療計画書(7 日以内)・退院時サマリー・退院療養計画書・看護サマリーなどの作成状況を病棟・科・担当医で横断、対象文書は施設設定、一覧から作成。
  - ［当たり］入院 × 文書種別(`Composition.type` / `QuestionnaireResponse.questionnaire` + `encounter`)の突き合わせ。入院実施の transaction に計画書の下書きを 1 件積む。
- **退院サマリーの横断一覧と PDF、科別レイアウト**(拡張、高): `Composition?type=18842-5&ward=&status=` + 退院 Encounter で未作成を出す。PDF は `discharge-summary-design.md` §6 既載。前回サマリー複写、DPC 様式 1 の病名取込。
- **文書参照(説明書・パンフレットのライブラリ)**(拡張、中): `document_templates.kind = reference`、右ペインから「印刷のみ」。
- **移行カルテ**(新規、中・導入時のみ): `Composition`(category legacy)+ 取込バッチ(demo-seed と同じ Node 経路)。

### 2.3 患者誤認・オーダー安全(横断チェック)

- **顔写真**(新規、高): `Patient.photo` に `Binary`、患者編集に写真欄、`PatientHeader` にサムネイル。ファイル取込の `Binary` 経路を流用。
- **同姓同名警告・死亡患者のオーダー抑止・二重登録患者**(拡張、高)
  - ［対応物］患者帯の死亡表示(赤)。`features/` が死亡患者のオーダー抑止を「未実装」と明記。`Patient.link` 未使用。
  - ［当たり］カルテを開いたとき `Patient?name=<カナ>` を 1 本引いて件数 > 1 なら帯に警告、死亡は右ペインの登録ボタンで止める。二重登録は `Patient.link(replaced-by)` + `/karte-pane/:patientId` を並べる。
- **患者状態チェック(種別非依存)**(拡張、高)
  - ［対応物］薬剤安全性チェック(`medicationSafetyHelpers`、アレルギー・重複・相互作用・用量・年齢・腎機能)、`PregnancyNotice`。
  - ［不足］外泊中・退院済の患者への入院オーダー警告、退院時に適用中パスの未評価警告(`clinical-pathway-backlog.md` A-6)、伝票・配膳の締切超過、オーダー発行可能時間、診療科限定薬・利用者限定薬、麻薬施用者免許のチェック、感染症との照合。
  - ［当たり］器は `advisory-design.md`(`Advisory`、重さ `block` = 止める)にある。各チェックを `block` の種別として足す。
- **退院後オーダーの検索と一括中止**(拡張、高)
  - ［対応物］退院モーダルは食事・リハ・指導・看護指示・持参薬だけを終了する。
  - ［不足］注射の連日展開・入院処方・検査予約・処置など退院日より後に実施予定日を持つオーダーの一覧と選択中止、入外変更、死亡退院時の自動起動。
  - ［当たり］`ServiceRequest?patient=&occurrence=gt{退院日}&status=active` を退院モーダルに並べ、`revoked`。
- **食物アレルギー × 食事オーダーの照合**(拡張、高) — **対応済み(2026-10-14)**。有効な食物アレルギーをオーダーの `supportingInfo` に写し(SS-MIX2 の AL1 相当)、`MealOrderForm` の一覧・食事タブの注意帯で未反映・解消済みを出す。アレルギーの登録・更新は進行中の食事オーダーあての通知 `meal-allergy-check` を同じ transaction で作る・取り下げる(`docs/meal-order-design.md` §2.12)。食種そのものとの照合(食種マスタのアレルゲン列)は残り(同 §7-12)。
- **感染症の表示**(拡張、高): 放射線・生理・内視鏡フォームと手術一覧・カレンダーの行(清掃順の判断)。 — **放射線・生理・内視鏡のフォームと一覧は対応済み(2026-10-11)。手術一覧・カレンダーは残り**。`PregnancyNotice` と同じ位置に `InfectionNotice`、行の背景色。`rad-backlog.md` B-4 既載。

- **スキャン依頼オーダー・スキャン実施一覧**(新規、中): スキャンセンターを置く中〜大規模向け。`ServiceRequest`(`order-type|scan`)+ Task、実施 = ファイル取込で `DocumentReference.basedOn`。
- **汎用オーダー(テンプレートで作る部門依頼)**(新規、中): ME 機器貸出・清掃・通訳など 16 種別に無い依頼。`ServiceRequest`(`order-type|generic` + 施設定義の依頼種別マスタ)+ `supportingInfo` → `QuestionnaireResponse`、他科依頼の構造を写して宛先を部門に。

- **Todo(手動のお知らせ・回覧・リマインダ)・患者単位の申し送りメモ(患者掲示板)**(拡張、中〜高)
  - ［対応物］通知 Task はシステム発生のみ、`Flag`、施設掲示板、患者フォルダのメモ。`Communication` は上流未対応。
  - ［当たり］通知レジストリに `manual-message`(宛先は職種・病棟 → 医療従事者に展開)。患者メモは `Composition`(type ローカル `patient-memo`)+ category、タイムラインに出さず患者帯のアイコンから。付箋(記録単位のメモ)も同じ器。

- **産科(プレグノグラム・正常新生児マップ・分娩台帳)**(新規、中・産科のみ): 妊娠を `Condition` / `EpisodeOfCare`、健診テンプレート + Observation 生成 + チャートの横軸を「妊娠週数」に。新生児は `Patient.link(seealso)` で母子、`Encounter.partOf`、マップのカードに「新生児 n」。分娩は `Procedure` + テンプレート、台帳はデータ抽出のプリセット。
- **歯科(歯式入力・歯科病名処置・歯周チャート・衛生実地指導・ユニット枠)**(拡張、中・歯科のみ): `Condition.bodySite` / `Procedure.bodySite` に FDI 歯番、歯式部品(SVG 32 歯 + 乳歯)を病名・処置・テンプレートの項目型として共通化、歯周は歯ごとの `Observation`(component)から `PERIO_SUM_01` へ自動集計、ユニット枠は `Appointment.participant` に Practitioner と Location。算定チェックは日レセ側。

## 5. 海外 EHR との照合(2026-10-18)

§1〜§4 は国内商用カルテの機能一覧と国内制度からの候補だった。ここには、海外 EHR(Epic / Oracle Health / MEDITECH Expanse /
athenahealth / eClinicalWorks / NHS England / 北欧の Cambio・DIPS / Alcidion Miya / OpenMRS O3 / Medplum ほか)と HL7 標準の
2024〜2026 年の動向を調べ、本リポジトリと突き合わせて**海外に特徴的で本リポジトリに無い(または土台だけある)もの**を並べる。
§1〜§4 に既に載っているもの(顔写真、全文検索、ヒストリカルビュー、患者メモ、音声入力、電子カルテ情報共有サービスなど)は除いた。

### 5.1 海外 EHR に共通して見える差

- **患者アクセスが法・国の基盤で義務になっている**: 米国の 21st Century Cures Act(情報ブロッキング禁止)で結果は医師確認前に患者へ届くのが標準。
  豪州 My Health Record は病理・画像の既定共有を法定(2026-07)、独 ePA はオプトアウトで 7,300 万件、NHS App は登録 4,100 万人。
  一方で悪性・遺伝の結果だけ 72 時間保留する州法(テキサス、2025)も出た。
- **外部アプリと判断支援を差し込む標準の経路**: SMART App Launch 2.2、CDS Hooks 2.0〜3.0(override reason の feedback を含む)、
  Epic Showroom(旧 App Orchard)、Medplum・OpenEMR の SMART 対応。医師自身がテンプレート・警告を作る文化と、
  それを統制する CDS ガバナンス委員会(発火数・上書き率の定期見直し)が組になっている。
- **記録の出自**: Epic は本文を文字単位で手入力 / コピー / テンプレートに分けて保持し、色分けで見せる。
  入院の経過記録の 80% 超がコピー・転記という報告(UCSF)が背景。HL7 も「AI Transparency on FHIR」(AI 由来データの印)を検討中。
- **閉ループの台帳化**: 偶発所見のフォロー、退院時の Medication Reconciliation、Health Maintenance(予防・定期項目の期限)を
  患者ごとに追い、未完了を可視化する。
- **評価・批判**:
  - アンビエント記録は燃え尽きの改善には証拠があるが、時間短縮・ROI の証拠は弱い。2026 年は EHR 同梱・無償化が主流になった。
  - 敗血症・急変の予測モデル(Epic Sepsis Model / Deterioration Index)は AUROC 0.63〜0.79 で施設差とアラート負担が大きい。
    米国では予測型 CDS に透明性の開示(HTI-1 の source attributes)が求められた。
  - In Basket(受信箱)は医師 1 人あたり週 243 件、うち 114 件がシステム自動生成。削減の手順は「自動生成を減らす」が先で、AI 下書きは後。
  - 北欧の大規模一体型導入(Region Skåne の Millennium 廃止、ノルウェー Helseplattformen への会計検査院の批判)は、
    退院要約・紹介などの機関間データが確実に届くことを最優先にすべきと示している。

    海外では警告の上書き率 95.7% という報告があり、Northwestern は高頻度の警告 19 件を廃止して入院あたりの割り込みを 35 → 16.6 件にした。
  - ［当たり］純関数 `fhir/advisoryHelpers.ts` に `Advisory {kind, severity, message, source}` を定め、既存の各ヘルパーをこれに寄せる。表示は `AdvisoryNotice` 1 部品。
    無視は登録の transaction に `Provenance`(activity = override、`reason` に理由の Coding)を積み、理由の候補は §2.1 の定型文マスタと共用。
    集計は backend `advisory_events`(kind・severity・outcome・user・at)に記録し、管理画面「警告の集計と設定」に種別 × 月の発火数・無視率。
- **アレルギー「無し(確認済)」の明示(NKDA)**(拡張、高・小)
  - ［対応物］`AllergyIntolerance.verificationStatus`(未確定・否定)、患者帯のアレルギー表示。
  - ［不足］「既知のアレルギー無し」を記録して「未確認」と区別する。海外 EHR では入院時の必須項目で、未確認のまま処方すると警告が出る。
  - ［当たり］`AllergyIntolerance`(code = SNOMED CT 716186003 No known allergy、verificationStatus = confirmed)を 1 件。`allergyHelpers.ts` に判定関数、
    患者帯は「無し(確認日)」と「未確認」を出し分ける。未確認のまま処方・注射を登録するときは上記の警告の器で「表示のみ」。食物アレルギー照合も同じ判定を使う。
- **医療計算スコアの同梱と自動充填**(拡張、中〜高・小)
  - ［対応物］テンプレートの `calculatedExpression` と `%` 変数(`fhir/populateContext.ts`)。eGFR・CCr・体表面積・NEWS2・qSOFA・ブリンクマン指数・Barthel・DESIGN-R はある。
  - ［不足］CHA2DS2-VASc・HAS-BLED・A-DROP(日本呼吸器学会、CURB-65 の国内版)・Child-Pugh・MELD・Wells・FRAX の雛形。
    海外では MDCalc on FHIR のように患者の値を自動で埋め、結果を記録に書き戻す。
  - ［当たり］seed に Questionnaire(テンプレートカテゴリ「スコア」)を同梱。`populateContext` に「病名コードの有無」を返す汎用の変数を足し(「コードを指定して直近の検査値」は `%labs` で対応済み)、
    病名・検査値から初期値を埋める。結果は既存の Observation 生成で時系列に乗せる。根拠の弱い予測スコア(再入院の LACE など)は入れない。
- **Health Maintenance(患者単位の定期検査・検診の期限)**(新規、中〜高)
  - ［対応物］データ抽出の指標(集団単位)、Flag、`%` 変数。患者ごとに期限を出す仕組みは無い。
  - ［不足］年齢・性・病名・薬剤から定期項目の期限を出し、期限超過を患者帯・プロファイルに出す。
    例: ワルファリン → PT-INR、メトホルミン → eGFR、ステロイド長期 → 骨密度、糖尿病 → 眼底・尿アルブミン、年齢 → がん検診・肺炎球菌ワクチン。
  - ［当たり］backend `health_maintenance_rules`(条件: 年齢範囲・性・病名コード・薬剤 YJ の前方一致 → 項目コード・間隔・根拠)。
    画面側は `Observation` / `Procedure` / `Immunization` を項目コードで `_count=1` 引いて最終実施日を出す。患者ごとの延期・対象外は理由つきの `Flag`(category `health-maintenance`)。
    督促 Task は作らず画面表示だけから始める(受信箱を自動生成の通知で埋めない)。
- **SMART on FHIR アプリ起動**(新規、中〜高・上流)
  - ［対応物］上流の OAuth クライアント管理(Backend Services と対話型 launch の登録、`features/admin-integration.md`)。外部アプリをカルテに埋め込む機能は無い。
  - ［不足］EHR launch(`launch` パラメータ、`launch/patient` scope)で患者・利用者の文脈を渡し、外部アプリ(計算ツール・PHR ビューア・AI 記録製品・院内開発の小画面)を
    カルテのタブに出す。アンビエント記録などを自前で作らず、施設が選んだ製品を差し込める。
  - ［当たり］上流に SMART App Launch 2.2 の EHR launch(launch context の発行・`fhirContext`・`.well-known/smart-configuration`)。
    client は backend `smart_apps`(名称・launch URL・client_id・表示場所)と管理画面、カルテに「SMARTアプリ」タブ(iframe に `iss` と `launch`)。
    アプリは `/fhir` プロキシを通らず上流に直接認可されるので、CORS とトークン寿命は上流で決める。

### 5.4 中くらいの候補

- **記録の出自表示**(拡張、中)
  - ［対応物］Tiptap の記録エディタ、テンプレートの前回複写、変更履歴の差分。LLM 記録支援(`llm-assist-design.md`、設計のみ)は生成文を空欄にだけ入れ、Provenance に `assembler = Device` を付ける。
  - ［不足］本文の各部分が手入力・前回複写・テンプレート・AI 下書きのどれかを保持して色分けで見せる。
  - ［当たり］Tiptap の mark(`data-origin` に copied / template / ai、`data-source` に元の記録)を複写・下書きの挿入時に付け、手入力で書き換えた部分は mark を外す。
    保存する HTML(`Composition.section.text.div`)に属性ごと残し、閲覧時はテーマ変数の下線色で示す。LLM 記録支援の実装と同時に行う。
- **申し送り(ハンドオフ)の器と自動下書き**(新規、中)
  - ［対応物］看護ワークシート・業務分担、看護サマリー、NEWS2、未指示受けの件数。`llm-assist-design.md` §3 が「申し送り(I-SBAR)は記録の器が無い」と明記。
  - ［不足］看護の勤務交代と医師の当直への引き継ぎを、1 患者 1 枚の構造(I-PASS: 重症度・要約・すること・起こりうることと対応・読み返し)で残す。
    Epic の Handoff は別画面だったため記入率 40〜50% で定着しなかったので、ワークシートの行から開く形にする。
  - ［当たり］`Composition`(category `handover`、I-PASS を section に)を診療記録タイトルマスタのプリセットに。初期値は NEWS2・未実施の予定・直近に変わったオーダー・未確認の結果から `%` 変数で埋める。
    LLM 下書きは `llm-assist-design.md` §3 の機能に 1 行足す。
- **ACP・コードステータスの構造化**(拡張、中・上流)
  - ［対応物］注意区分 Flag の DNAR・輸血拒否(患者帯のピクトグラム)。Consent での構造化は `patient-profile-design.md` §2.6 で第 3 段階に先送り。
  - ［不足］いつ・誰と話し合い、どこまでの処置(蘇生・挿管・透析・人工栄養)を望むか、代理決定者、再確認日。入院ごとの再確認。
  - ［当たり］上流に `Consent`(Flag と同じく HL7 基本定義 + 手書きバリデータ)。`provision` に処置ごとの可否。登録時に患者帯用の Flag を同じ transaction で書く。
- **患者向けの結果公開と患者入力の継続**(拡張、中・中〜大)
  - ［対応物］Web 問診(期限付きの使い捨てトークン・生年月日照合・QR、`web-intake-design.md`)。患者ポータル・予約の Web 取得は同書で対象外。
  - ［不足］検査結果・次回予約・薬一覧を患者が見る経路と、公開の段階(即時 / 医師確認後 / 悪性・遺伝は保留)。症状スコア(PRO)や家庭血圧・血糖を繰り返し入力させて経過表に乗せる。
  - ［当たり］第 1 段は Web 問診の器の延長。職員が発行する期限付きリンクに「結果の控え」「次回予約」「薬一覧」を載せ、患者の繰り返し入力は予約ごとにリンクを出し直す。
    入力値は Observation 生成で `performer = Patient` の Observation に。公開の段階は結果項目マスタに列を 1 つ。
    患者アカウント(継続ログイン・代理人)は第 2 段で、§4.1 のマイナポータル・§4.5 の PHR と合わせて判断する。
- **薬剤師の処方監査キューと介入記録**(拡張、中) — **対応済み(2026-10-25、`docs/rx-verification-design.md`)**
  - ［対応物］疑義照会(照会中は調剤・払出を止める)、注射の受付 → 払出、レジメン監査の目印。
  - ［不足］「監査済」の状態、未監査の処方の一覧、介入(プレアボイド)の種別(用量・相互作用・重複・腎機能など)と月次の集計。
  - ［当たり］通知レジストリに `rx-verification`(処方確定で薬剤部あてに作り、監査で完了)。介入は `Task.output` に理由の Coding。集計はデータ抽出の記録タブに「薬剤師介入」。
    監査前の実施を止めるかは施設設定で選ぶ(「承認前でも部門へ流す」方針と揃える)。
- **術者別プリファレンスカードと手術室ボードの術中時刻**(拡張、中・手術のある病院)
  - ［対応物］手術申込(執刀医・助手・麻酔科医)、実施入力の明細、手術室カレンダー日ビューの状態の色分け。術式ごとの定型明細は `surgery-result-design.md` §8 の将来案。
  - ［不足］術式 × 術者ごとの器械・材料・体位・特記事項の雛形(Epic OpTime の中核)。入室・執刀・閉創・退室を術中に押し、ボードが自動で更新される。
  - ［当たり］backend `surgery_preference_cards`(術式コード × 医療従事者、明細 JSON)を申込・実施入力の初期値に。術中の時刻は実施入力と同じキーでカレンダーのカードから 1 回ずつ書き、
    日ビューは一定間隔で読み直す。清掃時間(ターンオーバー)は §2.8 手術申込の重なり判定と共用。

### 5.5 小さめの候補・上流待ちの候補

- **病理のシノプティックレポート**(拡張、中): 組織診の診断はいま自由文(valueString)。癌取扱い規約の項目(組織型・深達度・脈管侵襲・断端・TNM)を臓器別の所見テンプレートにし、
  `Observation.component` に落とす。`exam-report-design.md` の所見テンプレートの器で足せ、§4.1 のがん登録の材料にもなる。
- **口頭指示の区分と事後署名の期限**(拡張、中): 代行入力の Provenance に口頭指示の区分を足し、指示医の承認期限(例: 24 時間)を `order-approval` の派生 Task で督促する。
  復唱確認(read-back)は指示を受けた人が付ける欄 1 つ。
- **予約リマインド**(新規、中): `Integrations::ExternalSystems::DEFINITIONS` に SMS / LINE の送信先を 1 要素、backend の日次処理で翌日の `Appointment` に送る。
  連絡先と送信の同意は `Patient.telecom` の拡張。NHS は紙の通知をアプリ通知に置き換えて 2,250 万通を減らした。
- **創部・褥瘡の写真の部位への紐付けと経時表示**(拡張、中): ファイル取込の `DocumentReference` に部位(`bodySite`)と褥瘡の `Condition` 参照を足し、DESIGN-R の経過の横に写真の列。
  カメラでの撮影は §4.5 のモバイル対応と同時。
- **予防接種**(新規、中・上流): 上流に `Immunization`(JP Core あり)。患者プロファイルの区画と、Health Maintenance(§5.3)の入力源。小児科・高齢者施設で効く。
- **FHIR Subscription による自動更新**(新規、中〜低・上流): 上流に Subscriptions Backport(Task の作成、パニック値の Observation を topic に)を足し、ベル・病棟の一覧をポーリングから更新通知に切り替える。
  規格の普及が萌芽期なので急がない。
- **IPS と SMART Health Links**(拡張、低〜中・上流): `Patient/$summary`(IPS IG 2.0.1)を上流に足し、患者が持ち運ぶ QR(SMART Health Links)にする。
  §4.1 の電子カルテ情報共有サービス(JP-CLINS)が先で、IPS はその派生として扱う。

### 5.6 取り込まないもの

- **全顧客共通の匿名データベースと基盤モデル**(Epic Cosmos / Look-Alikes / CoMET): 単一施設の製品では成り立たない。独立した検証も無い。
- **敗血症・急変の予測モデル**(Epic Sepsis Model / Deterioration Index): 性能の施設差とアラート負担が大きい。規則型の NEWS2 / qSOFA(実装済み)にとどめる。
- **第三者のアンビエント記録製品の個別統合**: 2026 年は EHR 同梱・無償化が主流。差し込み口(§5.3 SMART)を整え、製品は施設が選ぶ。
- **受信箱型の通知の拡大**: 通知 Task はシステム発生が中心のまま。種別を足す前に、§5.3 の警告の集計で無視率を見て削る運用を置く。
- **音声主体の画面設計**(Oracle Health の新 EHR): 稼働は外来のみで評価が無い。音声入力は §4.4 のまま。
- **大規模な統合データ基盤**(NHS Federated Data Platform 型): データ抽出・ダッシュボードで足りる規模。

- **ICU 重症系記録**(拡張、中、中〜大): 経過表の種別「ICU」(`flowsheet-design.md` §12 の種別は新生児・透析・パルトグラムのみ): 人工呼吸器設定(モード・FiO2・PEEP・TV)、

### 6.4 診療・運用の横断

- **研究利用のオプトアウトと仮名化エクスポート**(新規、中、中): 倫理指針のオプトアウト(患者ごとの拒否を `Flag` category research-optout、患者帯に表示)、
  データ抽出の結果 → 上流 `Group` → `Group/$export`(上流に Bulk Data 有り)、backend で患者番号 → 研究 ID の対応表と日付シフト・自由文除去の仮名化を通して ZIP 出力。
  治験(§2.11 の ResearchSubject)の受け皿にもなる。
- **施設基準の要件モニター**(拡張、中、中): 平均在院日数・在宅復帰率・看護必要度割合(有り)・特定入院料の算定上限日数(ICU 14 日など、該当患者の残日数)・重症度の基準を
  月次で機械算出し、届出前に減算リスクを見る。データ抽出「指標」タブに「施設基準」カテゴリ、入院患者一覧に残日数列。
- **待合・診察進捗の表示板**(新規、中、中)— **対応済み(2026-10-28)**: 受付番号(backend の日別連番、レセコン連携は受付 ID)、
  診察室ごとの公開画面 `/board/<token>`、データ抽出の外来に「待ち時間(分)」。`docs/waiting-board-design.md`。
  放射線の受付待ち(`rad-backlog.md` E-6)は「撮影中」の状態が無いので先送りのまま。
- **学会・公的レジストリの汎用登録基盤**(拡張、中、中): がん登録・NCD・感染症発生届は個別実装。「対象の判定条件(データ抽出の保存条件)+ テンプレート + 列順 CSV + 期限」を
  施設定義のレジストリとして一般化し、JROAD・J-TDB(外傷)・透析学会統計調査・JCS を足せるようにする。3 本のリファクタを伴う。
- **通院中断の検知の横断化**(拡張、中、小〜中): 糖尿病プリセットの「受診中断」(`data-extract-design.md`)を病名に依らない仕組みに(定期処方の投与終了日 + 最終受診 + 予約無し)、
  連絡(電話・手紙)の記録と結果(再受診・転院・死亡)を残し、Health Maintenance(§5.3)の患者帯表示と並べる。
- **専門科の図式入力部品**(拡張、低〜中、中): オージオグラム・視野・眼底図・関節可動域を Questionnaire の項目型(歯式の部品方式)として足し、`Observation.component` に落とす。
- **小粒**: 特定行為研修修了看護師の手順書(包括指示 `ServiceRequest` → 実施 `Procedure` + 医師報告)、保険薬局のトレーシングレポート・残薬報告の受取(処方医へ通知、電子処方箋が先)、
  研修医の経験症例ログ(カウンターサインの指導医グループで集計)、中材の滅菌ロットと手術器械セットのトレーサビリティ(`Procedure.usedReference`)、
  室料差額の管理(`Location` 拡張 + 同意 + 日レセ)、精神科の入院形態・隔離拘束の法定記録(§4.3 身体拘束の派生)。
