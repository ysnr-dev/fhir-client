# 手術説明・同意書 テンプレート・帳票一式

手術の説明内容を記録し、患者が署名する同意書を PDF で出すための 3 ファイル。
入院診療計画書(`admission-plan-01.md`)と同じ「テンプレート + ThinReports レイアウト +
マッピング定義」方式。公的な標準様式は無い(施設ごとに作る文書)ので、レイアウトは
本アプリ用に起こしたもの。

| ファイル | 用途 |
|---|---|
| `sur-consent-01.questionnaire.json` | テンプレート(Questionnaire)のエクスポートファイル。テンプレート一覧のインポートから取り込む(name: `SUR_CONSENT_01`、`http://fhir-client.local/Questionnaire/sur-consent-01\|1.0.0`) |
| `sur-consent-01.tlf` | A4 縦の同意書レイアウト |
| `sur-consent-01.mapping.json` | 「輸血の可能性」あり/なしに○を出し分けるマッピング定義 |

カテゴリ **「手術」**(code `9c4e1f37-8a52-4bd6-b071-3f8e2a5c9d14`)を拡張に持たせてある。

## 使い方

1. テンプレート一覧 → インポートで `sur-consent-01.questionnaire.json` を選択して保存。
2. `/report-layouts` で新規登録: 対象テンプレートにこのテンプレートを選択し、
   `sur-consent-01.tlf` をアップロード。**マッピング定義に
   `sur-consent-01.mapping.json` の中身を貼る**(空にすると○が出ない)。
3. カルテ →「テンプレート」→ 手術 → 手術説明・同意書で説明内容を記入して登録。
   カードの「PDF」から帳票を出し、紙で患者に渡して署名をもらう。

**説明した医師はメタ情報の記入者(`qr_author`)、説明日は記入日時(`qr_authored`)が持つ**
ので、項目としては置いていない。署名欄(同意日・患者署名・代諾者署名・続柄)は
レイアウト側の静的な線で、紙の上で記入する。署名済みの紙の取り込み(スキャン)は対象外。

## 項目と帳票の対応

linkId = レイアウトのアイテム ID の規約で流れるため、値の出力にマッピングは要らない
(マッピングが要るのは○の出し分けだけ)。

| グループ | 項目 | linkId | 型 |
|---|---|---|---|
| 病名・予定術式 (`grp_target`) | 病名(診断) | `disease_name` | 短文(初期値式 `%conditions`) |
|  | 予定術式 | `op_name` | 短文 |
|  | 手術予定日 | `op_date` | 日付 |
|  | 予定麻酔 | `anesthesia_plan` | 短文 |
| 説明内容 (`grp_explain`) | 手術の目的・必要性 | `purpose` | 長文 |
|  | 手術の内容・方法 | `method` | 長文 |
|  | 予想される合併症・危険性 | `risks` | 長文 |
|  | 代替可能な治療法 | `alternatives` | 長文 |
|  | 手術を行わない場合の見通し | `no_treatment` | 長文 |
|  | 輸血の可能性 | `transfusion` | 選択(ラジオ) yes=あり / no=なし |
|  | 術式の変更・追加の可能性 | `conversion` | 長文 |
| 説明の記録 (`grp_record`) | 同席者 | `attendees` | 短文 |
|  | 質問と回答 | `questions` | 長文 |
|  | 備考 | `remarks` | 長文 |

**メタ情報**: 患者氏名 → `pt_name`、患者番号 → `pt_id`、生年月日 → `pt_birthdate`、
説明日 → `qr_authored`、説明医師 → `qr_author`。

- 病名はフォームを開いた時点で転帰「継続」の傷病名(Condition)が初期値として
  流し込まれる(編集可。手術の対象病名がプロブレムに無ければ書き換える)。
- 術式の変更・追加の可能性を独立の欄にしているのは、術中の開腹移行などを
  **あらかじめ**説明したことを残すため(同意文にも「了承します」の一文がある)。
- 手術オーダーのヘッダに「取得済み同意書」のチェック(拡張)があるが、これは
  申込時の確認フラグで、この文書はその根拠になる説明の記録。二つは独立に動く
  (自動では連動しない)。

## 「輸血の可能性」の○

「あり　・　なし」の文字の上に `mark_transfusion_yes` / `mark_transfusion_no` という
`display: false` の **ellipse** アイテムを重ね、マッピング定義の `show` ルールで
回答の code に応じて表示している(admission-plan-01 は文字「○」を重ねたが、
「あり/なし」は 2 文字で囲むため楕円にした)。未回答なら両方出ない。
「あり」の場合に輸血同意書を別に取得する旨は帳票の注記にある。

```json
[
  {"linkId": "transfusion", "code": "yes", "show": ["mark_transfusion_yes"]},
  {"linkId": "transfusion", "code": "no", "show": ["mark_transfusion_no"]}
]
```

## レイアウトの構成

A4 縦・余白 20pt。上から: 表題 / 説明日・患者氏名(記入線 + 「殿」)・患者番号・
生年月日 / 説明内容の表(項目名列 x=55〜175、記入欄 x=175〜540。手術予定日と
予定麻酔は 1 行に同居) / 「上記のとおり説明しました。」+ 説明医師(記入線に
`qr_author` を印字) / 同意文 3 行 / 同意日・患者署名・代諾者署名(続柄)の記入線 /
代諾の注記。値の text-block は `vertical-align: top`(長文欄は `multiple-line: true`)。

## 検証済みの内容

- `Reports::ThinreportsRenderer` による PDF 生成を、**全項目記入・「なし」のみ選択・
  完全未記入**の 3 パターンで確認(値の流し込み、○の出し分け、未記入時に両方の○が
  出ないこと、署名欄・注記の配置、text-block のデザイン時初期値が残らないこと)。
- 開発環境(2026-08-28)で: インポートが上流 JASPEHR 検証を通る(配布ファイルは
  取り込み後に保存された形へ戻した正規形)→ `/report-layouts` にレイアウト +
  マッピング登録 → カルテで記入(病名の `%conditions` 初期値と上書き、
  輸血「あり」)→ 登録 → カードの「PDF」で帳票が出て、患者メタ・全項目・
  「あり」への○・説明医師・署名欄を確認。

## 施設名を入れていない理由

予約プレースホルダーに施設名が無い(`qr_institution` は保険医療機関番号)。宛先
(「○○病院長 殿」)や施設ロゴは施設ごとの様式の領分なので、必要になったら
レイアウトを複製して静的テキストで足す。帳票メタに自院名を足す共通拡張は、
他の帳票(紹介状など)と合わせて検討する方が筋がよい。
