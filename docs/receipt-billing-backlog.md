# 医事会計(診療行為送信)の不足機能

2026-09-21 に、日レセの API 仕様書と現行実装を突き合わせて洗い出した未対応の記録。
種別ごとの送り方と段階分けは `docs/receipt-billing-design.md`(2026-09-22)にあり、
本メモの各項目には対応する節を添えてある。
`feature/orca_integration` で `/api21/medicalmodv2`(中途終了データ)による会計送信までは
動いており、**不足は「送り方が仕様と違うもの」と「そもそも送っていない診療行為」に分かれる**。

連携全体の設計方針は `docs/receipt-computer-integration.md`。ここはその「会計送信」の部分だけを
他種別の backlog(`docs/lab-backlog.md` など)と同じ形で棚卸ししたもの。

- **［事実］** = このリポジトリの実装、または API 仕様書で確認した内容
- **［導出］** = 事実から論理的に導ける内容
- **［提案］** = 本メモの提案

参照した仕様書(いずれも 2026-09-21 に取得):

| 内容 | URL |
|---|---|
| API 一覧 | `https://www.orca.med.or.jp/receipt/users/tec/api/overview.html` |
| 中途終了データ作成 medicalmodv2 | `.../api/medicalmod.html` |

## 0. 現状(実装済みの範囲)

洗い出しの前提として、動いているものを先に挙げる。

- **送信**: `medicalmodv2` class=01 で中途終了データを登録。`Api_Result=80`(同日登録済み)を
  受けたら `tmedicalgetv2` で `Medical_Uid` を引いて class=03(置換)に倒す(`orca/medical_api.rb:52-70`)。
  取消は class=02(`:72-87`)。
- **病名**: `medicalmodv2` の `Disease_Information` は使わず `/orca22/diseasev2` に別送
  (`orca/disease_api.rb`)。修飾語は `ZZZ` + レセ電算 4 桁で接頭語 → 病名 → 接尾語 の順に並べる。
- **送信対象**: 処方(内服 210 / 頓用 220 / 外用 230)と 7 種別 — 検体検査・細菌(項目マスタの
  `receipt_code`)、生理・内視鏡・放射線・処置・手術(実施記録の手技・薬剤・材料・コメント。
  区分は診療行為マスタの章から。2026-09-22、設計書 §1〜2)。
- **送れない項目の報告**: 黙って捨てず理由つきで `skipped` に積み、プレビュー・ログ・送信結果に出す。
- **結果判定**: `Api_Result` / `Medical_Result` / `Disease_Result` の 3 層と各警告を畳み込む
  (`orca/api_result.rb`)。桁数が API ごとに違うので「ゼロだけなら成功」で判定する。
  `Api_Result=90`(他端末使用中)と HTTP 502/503/504 はリトライ。
- **Medical_Uid を持たない**: 送信済み判定はそのつど `tmedicalgetv2` に訊く(設計方針)。
- **画面**: 外来一覧と診察終了時に医事送信モーダル。保険組合せを選んで送信・送り直し・取消。

## A. 仕様に反しているもの(請求内容が狂う)

### A-1. 病名の転帰区分が仕様に無い値・別の意味の値になっている — 対応済み(2026-09-23: resolved → F、inactive → N)

［事実］`orca/disease_message.rb:9` は中立の転帰を次のように変換している。

```ruby
OUTCOME = { resolved: "C", inactive: "D" }.freeze
```

［事実］diseasev2 の仕様書にある `Disease_OutCome` の値は次のとおりで、**`C` は存在しない**。

| 値 | 意味 | 日レセ内部の転帰 |
|---|---|---|
| `F` | 治ゆ | 1 |
| `D` | **死亡** | 2 |
| `N` `R` `S` `U` `W` | 不変 / 軽快 / 後遺症残 / 不明 / 悪化 | 3(中止) |
| `O` | 削除 | — |

［事実］中立側の出どころは FHIR `Condition.clinicalStatus` で、`resolved` → `:resolved`、
`inactive` → `:inactive`(`receipt_computer/diagnosis_collector.rb:61-64`)。

［導出］**治ゆ(`resolved`)には仕様に無い `C` を送っており、転帰が付かない。**
さらに深刻なのは `inactive` で、カルテでは「もう活動していない病名」の意味だが、
**日レセには `D` = 死亡として登録される。** 患者が死亡した扱いの病名がレセプトに載る。

［提案］`resolved` → `F`(治ゆ)、`inactive` → `N`(不変)あるいは `R`(軽快)に直す。
`inactive` を中止群のどれに寄せるかは運用判断が要る(レセプト上はいずれも「中止」に丸まる)。
併せて病名の削除に使う `O` も中立側に足す。

> なお `medicalmodv2` の `Disease_Information` にも同名の項目があり、値の定義は diseasev2 と同じ。
> 現在は病名を diseasev2 に別送しているのでそちらだけ直せばよい。

### A-2. 外来の送り直しに class=03(置換)を使っている — 対応済み(2026-09-23: 02 → 01。再登録で落ちたら「医事側のデータは消えています」と出す)

［事実］`orca/medical_api.rb:58-69` は `Api_Result=80` を受けると class=03 に倒す。

［事実］仕様書の原文は「**置換処理は、入院のみ可能です**」(`Api_Result=05`)、
「**入院外(外来)に関しては、削除のみ可能となります**」。class=04 は「追加処理は、外来のみ可能です」。

［事実］実機(WebORCA オンプレ版 receipt 20260825-1)では外来でも class=03 が通り、
新しい `Medical_Uid` が返ってくることを確認済み。

［導出］現在動いているのは仕様に無い挙動への依存で、日レセの版やクラウド版で塞がれると
送り直しが一斉に失敗する。

［提案］**外来は class=02(削除)→ class=01(再登録)に変える**(2026-09-21 決定)。
「全体を揃える」という取り込み側の方針とも揃う。ただし削除と登録の間で失敗すると
中途データが消えた状態で残るので、そのときは画面に「送り直しに失敗し、医事側のデータが
消えています。もう一度送ってください」と明示する必要がある。

［提案］class=03 は入院(B-13)を入れるときに、入院用の正規の経路として残す。

### A-3. 送信対象をオーダー発行日(`authoredOn`)で集めている — 対応済み(2026-09-22、設計書 §1)

［事実］`receipt_computer/billing_claim_builder.rb` は `MedicationRequest` / `ServiceRequest` を
`authoredon` で検索し(`:52` `:153`)、`authoredOn` の日付が一致するものだけ採る(`:45`)。

［事実］`docs/order-common-backlog.md` の決定(2026-09-01)で、`authoredOn` は**オーダー登録日時**、
`occurrenceDateTime` が**オーダー開始日**と定義されている。

［導出］会計は実施した日のものを立てるが、現在は登録した日で集めている。次のずれが出る。

- 予約検査・後日実施の手術など、**先に入れたオーダーが登録日の会計に載り、実施日には載らない**。
- **実施していないオーダーも載る**。`status` が `revoked` / `entered-in-error` / `draft` のものは
  除いているが、「オーダーしたが当日実施しなかった(`active` のまま)」は素通りする。
- 放射線・処置・手術の**実施入力(Procedure)で確定した数量・薬剤・材料が一切反映されない**(B-4)。

［提案］収集の軸を `occurrence` + 実施記録に変える。実施入力のある種別(放射線・処置・手術・
内視鏡・生理)は Procedure を、それ以外は `occurrence` を軸にする。種別ごとに実施の表し方が
違うので、`OrderCatalog` の定義に「何をもって実施済みとするか」を足すのが素直。

### A-4. 「登録はされたが一部が落ちた」警告を成功として扱っている — 対応済み(2026-09-23: W02/W04/W05 は失敗、M 系は「送れなかった項目」、保険組合せ番号を応答と照合)

［事実］`orca/api_result.rb:99-107` は `Api_Result` がゼロなら `ok?`、警告があれば `warning?`
という扱いで、警告の中身では成否を変えない。

［事実］仕様上、次の警告は**実質エラー**にあたる。

| コード | メッセージ | 実際に起きること |
|---|---|---|
| `W02` | 保険組合せをゼロで登録しました | 保険組合せ番号が不正でも**エラーにならず、保険未確定で登録される** |
| `W04` / `W05` | 入院期間中です / 入院中ではありません | その入外区分では展開できない |
| `M01` | 点数マスタに登録がありません | **その明細だけ取り込まれない** |
| `M02`〜`M05` | セット未登録 / 全角変換エラー / 入力対象外 / 診療種別区分なし | 同上 |

［導出］W02 を見逃すと、保険が付かない中途データが日レセに残る。M01 は送った項目が
静かに消えるので、画面に「送信成功」と出たのに請求されない項目が出る。

［提案］W02・W04・W05 は失敗相当に格上げする。併せて応答が返す
`Patient_Information/HealthInsurance_Information/Insurance_Combination_Number` を
送信値と照合し、食い違ったら失敗にする。

［提案］M 系は `Medical_Warning_Position`(何番目の剤か)と `Medical_Warning_Item_Position`
(何番目の明細か)、`Medical_Warning_Code`(対象コード)が返るので、既存の `skipped` と同じ器に
入れて「送ったが日レセに取り込まれなかった項目」として画面に並べる。器は既にあるので足すのは変換だけ。

### A-5. 日レセ側で展開済み・会計済みかどうかを見ていない — 対応済み(2026-09-23: `billing_status` が none / sent / opened / settled を返し、opened・settled は画面で送信・取消を止める)

［事実］`orca/medical_api.rb:30-50` の `find_uid` は `Medical_Uid` の有無しか見ていない。

［事実］`tmedicalgetv2` は `Medical_Mode`(1: 展開中)、`Medical_Mode2`(1: 日レセ画面の中途終了登録分)を
返す。仕様書には「**日レセ API で登録しても、一旦画面展開し再度中途終了した場合は Medical_Uid の
値が消される**」とあり、そうなると API から削除・変更ができなくなる。展開済み・内容変更済みの
データへの削除・置換は `Api_Result` 31 / 33 で失敗する。

［事実］会計が済んだかどうかは `/api01rv2/acceptlstv2`(class=01 受付中 = 会計待ち、02 会計済)で引ける。

［導出］医事課が日レセ側で会計を打った後にカルテから送り直すと、失敗するか、
既に確定した会計と食い違う中途データを作る。現在は「送り直す」ボタンがいつでも押せる。

［提案］`billing_status` に「医事側で処理中 / 処理済み」の状態を足し、
送信ボタンを止めて理由を出す。`Medical_Mode` と `acceptlstv2` の会計済み判定を使う。

### A-6. `Perform_Time` を送っておらず、時間外を表す手段が無い — 対応済み(2026-09-23: 当日の外来 Encounter の period.start を送る。時間外加算そのものは送らず日レセの判定に任せる)

［事実］`orca/medical_api.rb:97-112` は `Perform_Time` を送っていない。

［事実］`medicalmodv2` には CLAIM の `timeClass` に当たる項目が無く、時間外・休日・深夜は
**加算コードを `Medication_Code` として送る**。仕様書には「初診・再診料等の診察料が 1 件目の
1 行目になるように送信します(**診察料に含まれる時間外コードはこれ以降に送信されたものに
対してのみ反映され、それ以前のものには反映されない**ため)」とある。

［導出］時間外・休日・深夜の加算が一切取れない。

［提案］`Perform_Time` を送る(診察の時刻はカルテが持っている)。加算そのものを送るかは
B-10(診察料の扱い)と一緒に決める。

### A-7. `Medication_Usage_Code` は公開仕様書に無い項目 — 現行のまま(2026-09-23: 根拠を `medical_message.rb` のコメントに記載。明細 1 行方式は日レセ側の用法マスタが要るため)

［事実］`orca/medical_message.rb:53-60` は剤の各行に `Medication_Usage_Code` を付けている。

［事実］`medicalmodv2` の公開仕様書のリクエスト項目一覧に `Medication_Usage_Code` は無い。
仕様上、用法は**用法コードを `Medication_Code` として剤の中に 1 行置く**形。

［事実］実機のレコード定義(`xml_medicalv2req.db`)には在り、電子処方箋の 16 桁用法コードが
そのまま通ることを確認済み(メモ `weborca-api-gotchas`)。

［導出］A-2 と同じく、仕様に無い項目に依存している。版やクラウドで落ちたときに用法が消える。

［提案］用法コードを明細の 1 行として送る形に寄せる。現行のまま残すなら、
「公開仕様には無いがレコード定義には在る」という根拠をコードのコメントに書いておく。

## B. 送っていない診療行為・項目(算定漏れ)

### B-1. 注射(310 / 320 / 330 / 340 / 350) — 対応済み(2026-09-23: 実施記録から薬剤を送り、区分は手技・点滴・経路で決める。外来化学療法加算は未対応)

［事実］`orca/medical_message.rb:12-17` の `MEDICAL_CLASS` に注射の区分が無い。
処方のうち用法基本区分が 3(注射)・4(注入)のものは `billing_claim_builder.rb:93-102` で
`nil` になり「内服・外用のいずれでもないため送れません」で落ちる。`injection` オーダーは
`OrderCatalog` に定義が無く「この種別はまだ医事会計へ送りません」で落ちる。

［事実］区分は 皮下・筋肉内注 `310`、静脈内注射 `320`、点滴注射 `330`、その他注射 `340`、
中心静脈注射 `350`。手技料を取らない場合の `311` / `321` / `331` もある。

［提案］注射オーダー(`docs/injection-order-design.md`)を `OrderCatalog` に足し、
注射方法から区分を決める。薬剤は `301`… ではなく剤の中に並べる(注射は手技 + 薬剤で 1 剤)。

### B-2. 未対応のオーダー種別 — 対応済み(2026-09-23、設計書 §5。輸血・病理・リハビリ・栄養指導・放射線治療・麻酔・化学療法の加算)

［事実］`OrderCatalog::ALL` は 7 種別。カルテが持つオーダー種別のうち次が未対応で、
すべて「この種別はまだ医事会計へ送りません」になる。

| 種別 | 診療種別区分 | 設計書 |
|---|---|---|
| 輸血 | `510` | `docs/transfusion-order-design.md` |
| 病理 | `640` / `643` | `docs/patho-order-design.md` |
| リハビリ | `800` | `docs/rehab-order-design.md` |
| 麻酔 | `540` / `541` / `542` | `docs/anesthesia-chart-design.md` |
| 化学療法レジメン | 注射 + 医学管理 | `docs/chemo-regimen-design.md` |
| 食事 | 入院(B-13 と一緒) | `docs/meal-order-design.md` |

［提案］他科依頼・看護指示は、それ自体を出来高で請求する項目が無いので対象外と考えている。
ここは運用で確かめる。

### B-3. 薬剤・材料・加算の子区分が無く、手技コード 1 本しか送れない — 対応済み(2026-09-22、設計書 §2)

［事実］`MEDICAL_CLASS` は種別ごとに 1 つの区分しか持たず、`build_order_item`
(`billing_claim_builder.rb:190-210`)は項目マスタの `receipt_code` を 1 行ずつ並べるだけ。

［事実］仕様では剤の中身を区分で分ける。処置 `400` に対し薬剤 `401` / 材料 `402` / 加算 `403`、
手術 `500` に対し `501` / `502`、検査 `600` に対し `601` / `602` / `603`、
画像診断 `700` に対し薬剤 `701` / 材料 `702` / **フィルム `703`** / 加算 `704`、
造影剤の注入手技 `731` / `732`。

［導出］実施入力で記録した薬剤・材料・フィルムを送る器がそもそも無い。

### B-4. 放射線の撮影部位・フィルム・造影剤・器材 — 造影剤・器材・撮影部位(項目マスタの 820 コメント)は対応済み。フィルムの分画は設計書 Phase 5

［事実］放射線は `Master::RadItem.receipt_code` を 1 本送るだけ。

［事実］仕様上の送り方:

- **撮影部位**は CLAIM の `location` ではなく、**通常の明細として部位コードを `Medication_Code` に
  置く**。日レセが配る部位コードは参考で、**医療機関側で日レセとカルテに同じコードを作る**必要がある。
- 部位 + 撮影料から**写真診断料は自動算定される**ので送らない。
- **フィルムは「枚数 × 分画数」を `x-y` 形式で数量に設定**する。分画数入りのコード
  (`700060000` 大四ツ切(2分画)など)もある。
- 2024 年 6 月診療分以降は、日レセの部位コードに**撮影部位の選択式コメントコード**
  (例 `820181000` 撮影部位(単純撮影):頭部)を設定してあれば部位の送信自体が不要。

［事実］カルテ側には器材マスタ(`master_rad_materials`)と実施入力(造影剤の
`MedicationAdministration`、器材の `Procedure.usedCode`)が既に在る(`docs/rad-result-design.md`)。

［導出］送る材料は揃っていて、足りないのは変換だけ。ただし A-3(実施日基準)を先に直さないと
実施入力に手が届かない。

### B-5. 数量と回数が常に "1" — 対応済み(2026-09-22、設計書 §1〜2)

［事実］オーダー系の明細は `BillingLine.new(code:, name:, quantity: "1")`
(`billing_claim_builder.rb:205`)、`Medical_Class_Number` も処方以外は `"1"`
(`orca/medical_message.rb:37`、`BillingItem#days` が未設定)。

［事実］`Medical_Class_Number` は**回数または日数**。内服は投与日数、処置・手術・リハビリは回数。
`Medication_Number` は数量。

［導出］同じ処置を 2 回行っても 1 回分しか請求されない。

### B-6. コメントコード — 対応済み(2026-09-23: コメントマスタを取り込み、疾患名・発症日(リハ)、照射部位(放射線治療)、撮影部位(放射線)をカルテのデータから自動生成。850/851/852/831 の送り分けも実装)。UI からの手入力は作らない方針で、作れないコメントは医事側で入力する。コメント関連テーブルも取り込み、設定画面でコメントコードの候補を出す(2026-09-23)

［事実］コメントを送る経路が無い。

［事実］仕様上の入力方法はコードの種別ごとに違う。

| コード | 送り方 |
|---|---|
| `842XXXXXX` | `Medication_Number` に数値(`+1.25` のような符号付きも可)。`Medication_Name` に書いても破棄される |
| `830XXXXXX` | `Medication_Name` に**マスタのコメント文は入れず、入力するコメント文だけ**を設定。**全角 50 文字を超える場合は明細を分けて連続設定**(まとめてはくれない) |
| `810000001` | フリーコメント。名称をそのまま取り込む。**最大 80 バイト** |
| 区分 `.990` / `.991` | コメント単独の剤。**診療行為に付けるコメントはこれを使わず、対象の剤の中に入れる** |

［事実］診療行為コードに紐づく選択式コメントの一覧は
`/api01rv2/medicationgetv2`(Request_Number=02、最大 200 件)で引ける。

［導出］レセプトで必須のコメント(検査値、部位、実施時間など)が付けられない。

### B-7. 一般名処方を送らずに落としている — 対応済み(2026-09-23: 一般名コードから薬価最安の銘柄を引き `Medication_Generic_Flg=yes`)

［事実］`billing_claim_builder.rb:119-127` は、銘柄のレセ電算コードが無く一般名処方コードしか
無い処方を「一般名処方はレセプト電算コードに解決できません」で落としている。

［事実］`medicalmodv2` には `Medication_Generic_Flg` があり、`yes` で一般名、`no` で銘柄指示。
有効なのは内服・外用・頓服。システム予約コード `099209908`(一般名記載)を薬剤の直下に置く方法もあるが、
**`Medication_Generic_Flg` の指示があればそちらが優先**される。

［導出］一般名処方の薬剤が丸ごと請求から落ちている。一般名処方加算も取れない。

［提案］一般名処方でも銘柄のレセ電算コード(代表銘柄)を送り、`Medication_Generic_Flg=yes` を付ける。
後発変更不可などのシステム予約コード(`099209903` / `099209905` / `099209906` / `099209910` /
`099209911`)も同時に検討する。

### B-8. 院内 / 院外・臨時・包括の区分 — 院内 / 院外は対応済み(2026-09-23: 処方の区分から 211/212 系を明示)。臨時・包括は未対応

［事実］処方は `210` / `220` / `230` の 3 つだけを使っている。

［事実］**院外処方でも通常は `210` 系でよい**(院内 / 院外は日レセの「1001 医療機関情報」か
画面の院外処方区分で決まる)。混在させたいときだけ院内専用 `211` / `221` / `231`、
院外専用 `212` / `222` / `232` を明示する。包括は `213` / `223` / `233`、臨時は `290` 系。

［事実］`Medication_Internal_Kinds`(内服 1 種類区分)、`Medication_Continue`(継続コメント区分)も未送信。

［導出］院内と院外の処方を同じ日に出すと区別できない。

### B-9. 外用の日数の入れ方が内服と同じ — 対応済み(2026-09-23: 外用は日数を送らず総量 × 1)

［事実］`prescription_count`(`billing_claim_builder.rb:105-113`)は内服・頓用・外用を区別せず、
`expectedSupplyDuration` → `timing.repeat.count` → `"1"` の順で `Medical_Class_Number` を決めている。

［事実］外用薬は原則「総量 × 1」で入力する。日数を入れるのは特定疾患処方管理加算を算定できる
場合(28 日以上)だけ。

［導出］外用薬に日数が入ると請求が狂う可能性がある。

### B-10. 診察料・医学管理料・在宅 — 栄養食事指導料(130)は対応済み(2026-09-23)。他の医学管理料・在宅は未対応

［事実］`billing_sender.rb:51` が `auto_basic_fee: true` を固定で渡し、
`Medical_Fee_Auto="Yes"` で日レセに診察料を自動算定させている。

［導出］自動算定で出るのは初診料・再診料だけ。**医学管理等(`130`)・在宅(`140` 系)は
カルテに入力する手段が無く、指導料が一切算定されない。**

［事実］当日算定すべき診察料は `/orca11/acceptmodv2` の **`Request_Number=00`(受付情報・診察料照会)**
で引ける。「新規患者は初診、以外は再診。当日に受診があれば同日再診。会計済みなら返さない」
という判断まで日レセがしてくれる(当日算定不可の判断はしない)。

［提案］自動算定のままでよいかを運用で決める。自分で送るなら A-6 のとおり
1 件目の 1 行目に 1 つだけ置く。医学管理料は入力する画面から要る。

### B-11. 自費・労災・自賠責

［事実］いずれも未対応。自費コードを `Medication_Code`、金額を `Medication_Number`(7 桁)に
置く形と読めるが、**自費用の診療種別区分の値は API 仕様書にも外来版マニュアル 2.6 にも記載が無い**。
労災・自賠責は `809`(その他)や `409`(処置の労災読み替え対象外)がある。

### B-12. 剤 40・明細 40 の上限を超えた分を捨てている — 剤は対応済み(2026-09-23: 41 剤目以降を class=04 で追記)。1 剤 40 明細超は報告して切る

［事実］`orca/medical_message.rb:42-48` は 40 剤を超えた分を「1 回に送れる剤は 40 までです」で落とす。

［事実］外来は class=04(外来追加)で追記できる。一致条件は患者番号・診療日付・診療科・保険組合せで、
**ドクターコードが違うとエラー(41)**、**日レセ画面で作った中途データには追記不可(42)**、
剤番号が最大なら 43。

［提案］A-2 で送り直しを 02 → 01 にするなら、40 剤を超える分は続けて class=04 で送る。

### B-13. 入院 — 設計書 §6(方針のみ)

［事実］`orca/medical_api.rb:99-100` で `InOut` は空(外来)固定。コメントに「入院(I)は第 2 段階」とある。

［事実］入院では `InOut=I`、`Admission_Date`(2025-05-02 追加)を送る。
`Medical_Class_Number` は複数診療日のまとめ入力のため 50 桁まで拡張されている。
**入院は class=03(置換)が正規の訂正方法**(A-2 の裏返し)。

### B-14. 自動発生コードの明示送信

［事実］処方料・処方箋料・調剤料・薬剤情報提供料・調基・検査判断料・入院調剤料は
送っても破棄される。現在は送っていないので問題は出ていない。

［事実］2026-06-24 追加の **`Medication_Import_Flg=yes`** を付けると、上記の破棄対象コードを
破棄せずに取り込める。ただし(減)・内服逓減などの逓減コードと外来調剤料は設定があっても破棄される。

## C. 接続・運用・併用 API

### C-1. WebORCA クラウド版に接続できない

［事実］`orca/gateway.rb:121-128` の Faraday 接続は Basic 認証だけで、SSL / クライアント証明書の
設定が無い。

［事実］クラウド版は電文はオンプレと同じだが、URL が
`https://weborca.cloud.orcamo.jp:443/api/<各API>` で、**Basic 認証とクライアント証明書(`.p12`、
パスワードは別ファイル)の両方**が要る。初回接続時はスクリプト実行中で HTTP 503 と
「マスター更新中です。しばらくお待ちください。」が返るのでリトライが要る(503 は既にリトライ対象)。

［提案］`ExternalSystemConnection` の `options` に証明書のパスとパスワードを足す。
現在 `options` にあるのは `api_prefix` だけ。

### C-2. 会計結果をカルテに戻していない — 対応済み(2026-09-23: 状態照会が会計済みのとき収納情報(請求額・入金額・未収額・点数)を返し、外来一覧にその日の会計済みを印で出す。PUSH の patient_account は使わず、一覧は 30 秒で再取得)

［事実］`medicalgetv2` / `incomeinfv2` / PUSH の `patient_account` を使っていない。

［導出］カルテ側で「この受診は会計が済んだか」「請求はいくらか」が分からない。
患者に金額を伝える画面も作れない。A-5 の判定にも要る。

### C-3. 送信前のチェックが無い

［事実］次の API を使っていない。

| API | 使いどころ |
|---|---|
| `/api01rv2/acsimulatev2` | 送信前に請求額を試算する |
| `/api01rv2/medicationgetv2` | 入力コード → 診療行為コードの解決、選択式コメントの取得 |
| `/api01rv2/contraindicationcheckv2` | 併用禁忌チェック |
| `/orca51/masterlastupdatev3` | 点数マスタの同期判定 |

［導出］レセ電算コードが日レセの点数マスタに在るかを送る前に確かめられないので、
A-4 の M01 は送ってから気づくしかない。

### C-4. 受付側の状態を更新していない

［事実］受付は取り込む方向だけで、`acceptmodv2` の登録・取消を送っていない。
送受信状態(`Request_Number=04` の `Claim_Send_Info` = 00 送信済み / 01 閉塞 / 02 送信誤り /
03 会計待ち)も更新していない。

［導出］医事課の受付一覧から見て「カルテから送信済みかどうか」が分からない。

### C-5. `Api_Result` を種類別に扱っていない

［事実］`orca/adapter.rb` はゼロ以外をまとめて `Rejected` にし、画面はメッセージをそのまま出す。

［導出］利用者が次に何をすればいいか分かるのは一部だけ。特に次は文言を分ける価値がある。

| コード | 意味 | 利用者に伝えるべきこと |
|---|---|---|
| `31` / `33` | 内容が更新されている | 医事側で触られた。画面を見てから送り直す |
| `05` | 置換は入院のみ | A-2 を直すまでの保険 |
| `20` / `21` | 病名だけ / 中途データだけ失敗 | **部分成功**。どちらが通ったか |
| `90` | 他端末使用中 | 日レセで同じ患者を開いていないか |

［事実］`20` / `21` は片方だけ成功する状態を表すが、現在は病名と診療行為を別 API に分けて
順に送っているので、この 2 つは出ない。ただし**別送でも「病名は通って会計は落ちた」状態は起きる**ので、
画面はその区別を出している(`BillingSendModal.tsx`)。

### C-6. 画面と記録

［事実］送信項目の個別選択・数量の修正・コメントの追加ができない(その日の全オーダーを一括送信)。
診療日・診療科・担当医もモーダルでは変えられない。送信履歴は JSON Lines のログだけで
画面から見られない。

［導出］ログを画面に出さない方針(`docs/receipt-computer-integration.md`「状態はレセコンと
カルテ本体にしか置かない」)は保ちつつ、「いつ何を送ったか」は `tmedicalgetv2` と
`medicalgetv2` から引き直せる。**記録を持つのではなく引き直す形**なら方針と両立する。

### C-7. テストが無いところ

［事実］`BillingSender` / `MedicalMessage` / `DiseaseMessage` / `billings_controller` に spec が無い。
`MedicalApi` / `ApiResult` / `Gateway` / `Adapter` / `BillingClaimBuilder` にはある。

［導出］A-1(転帰区分)は `DiseaseMessage` の spec があれば仕様書と突き合わせた時点で気づけた。

## 仕様書から確認できなかったもの

推測で埋めていないので、着手時に一次資料を当たる。

- **各項目の桁数**。HTML 版の仕様書にはほぼ書かれていない(明記があるのは `Medical_Class_Number` 50 桁、
  `Medication_Number` 7 桁、`Disease_Name` 全角 40 文字、830 系コメント全角 50 文字、
  フリーコメント 80 バイトだけ)。正典はサーバー同梱のレコード定義
  `/opt/jma/weborca/releases/receipt/<ver>/record/xml_*.db`(`weborca-dev` の
  `scripts/dump-record-defs.sh` で取り出せる)。
- **自費用の診療種別区分の値**(B-11)。
- **入院系 API(`hsptinfmodv2` / `hsacctmodv2` / `hsmealv2`)の項目表**(B-13)。
- **`Doctors_Fee` と `Medication_Input_Info`**。どちらも `medicalmodv2` の公開仕様書には存在しない。
  会計まで行う拡張 API(HAORI)側の項目で、仕様書はベンダー契約者向け配布のため参照できていない。
- **CLAIM `timeClass` の「乳幼児時間外特例」に対応するコード値**。公式ページの表でセルが欠落している。
