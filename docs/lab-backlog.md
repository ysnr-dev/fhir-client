# 検体検査(オーダー・部門業務・結果)の不足機能

2026-09-09 に検体検査の実装を棚卸しして洗い出した未実装の記録。オーダー入力・部門業務
(ラベル発行・到着確認)・結果登録・時系列表示までは動いており、**不足は結果側に集中している**。

検体検査には `*-order-design.md` が無く(マスタ・ラベル・到着確認の 3 メモに分かれている)、
他種別が各設計書の「§8 未実装・今後」に置いている内容をここにまとめる。オーダー種別をまたぐ
課題は `docs/order-common-backlog.md`、上流サーバー側の課題は `docs/server-improvement-backlog.md`。

- **［事実］** = このリポジトリ・上流の実装で確認した内容
- **［提案］** = 本メモの提案

着手の推奨順は **§1 → A → B-1 → B-2/B-3 → C**。§1(結果項目マスタ)は A の各属性の置き場になる
前提、A は結果の読み違いに直結し、B-1(結果の取込)は運用に乗せるための前提になる。

## 0. 現状(実装済みの範囲)

洗い出しの前提として、動いているものを先に挙げる。

- **オーダー入力**(`components/LabOrderForm.tsx`): 検査伝票(レイアウト)と項目検索の 2 方式、
  パネルの自動展開、検体(材料)ごとのグルーピングと採取管の決定、至急区分、検査コメント、
  オーダーセットへの対応、DO(過去オーダーの流用)。
- **部門業務**: 検体検査一覧(`pages/LabWorklistPage.tsx`)の絞り込みと進捗、検体ラベル発行
  (`backend/app/services/lab_label_report.rb`、CODE128・11 桁・上流採番)、バーコードスキャンによる
  到着確認(`pages/LabArrivalPage.tsx`)、Task の 依頼済 → 受付済 → 実施済 / 中止
  (`fhir/labTaskHelpers.ts`)。
- **結果**(`components/LabResultForm.tsx` / `fhir/labResultHelpers.ts`): 手入力での登録・編集・削除、
  オーダーからの検査項目の自動展開、データ型(PQ/CD/CO/ST)に応じた入力、H/L の手入力、
  検査分野ごとのグルーピング表示、累積表(`LabResultTimelinePanel.tsx`)とグラフ
  (`LabTimelineChart.tsx`)、タブ区切りでのクリップボードコピー。
- **マスタ**: オーダー項目・パネル構成・検査伝票レイアウト・検体(材料)・採取管・共有項目 JLAC
  コードマスタ。

## 1. 結果項目マスタの持ち方(施設マスタを本体に、JLAC11 / JLAC10 を属性で併記)

2026-09-09 に検討した。A の各項目(基準値・パニック値・前回値)はすべて「結果項目 1 件」に
ぶら下がる属性なので、その置き場を先に決める必要がある。

> **実装済み(2026-09-10)**。§1.4 / §1.5 のとおり `master_lab_result_items` と
> `master_lab_order_item_results` を新設し、結果登録・時系列・検査分野のグルーピングを
> 施設コードに寄せた。実装の要点は readme「検体検査の結果項目マスタ」。決めたことの補足:
> - 初期投入は単項目オーダー項目からの 1:1 派生(`Master::LabResultItemDerivation`。migration と
>   `db:seed` の両方から呼ぶ)。単項目なのに複数の結果を返す 6 件(尿沈渣 2 種・蛋白分画・血液ガス
>   分析・精液一般・髄液一般)は分解した結果項目を `db/seed_data/lab_result_items.csv` /
>   `lab_order_item_results.csv` で同梱した。
> - 蓄積済みの結果(施設コード無し)は読み出し側で JLAC11 から読み替える。試薬単位の 17 桁は
>   マスタの代表コードと下 5 桁が違うので、**測定物・識別・材料の 12 桁**で引き当てる
>   (`jlac11AliasKey`)。材料コードまで違う旧結果(211 と 212 など)は読み替えられず別行のまま。
> - 配布コードマスタは `master_jlac_items`(`Master::JlacItem`、`/master/jlac_items`)へ改名した
>   (2026-09-10。§1.5)。施設の項目マスタと名前が紛らわしく、役割が伝わらないため。
> - 残課題: A-2 以降(パニック値・デルタチェックは結果項目マスタの行にぶら下げる)、
>   CSV での結果項目マスタ取込(B の器で扱う)。

### 1.1 現状

**［事実］** 結果項目の実体は共有項目 JLAC コードマスタ(当時の `master_lab_items`。現 `master_jlac_items`。電子カルテ情報共有
サービスの配布 CSV、32 列)で、`jlac11_code` が NOT NULL、`jlac10_code` は任意
(`backend/db/schema.rb:326-363`)。結果入力の項目選択(`components/LabItemSearchModal.tsx`)は
このマスタから選び、`Observation.code` には JLAC11 の coding と略称の補助 coding だけを書く
(`fhir/labResultHelpers.ts:285-300`)。JLAC10 もローカルコードも書いていない。

**［事実］** 配布マスタの収載は電子カルテ情報共有サービス対象の 43 検査項目 + 5 感染症項目
(約 3,000 行)に限られ、ヘマトクリット単独や白血球分画単独のコードすら未公開
(`docs/lab-order-master-design.md` §1)。そのため、この範囲外の項目は結果として登録できない。

**［事実］** 突き合わせはすべて JLAC を直接キーにしている。オーダー項目から結果項目への展開は
JLAC11 / JLAC10 での引き当て(`hooks/useLabOrderResultLines.ts:42-44`。引けなければ
「展開していません」)、腎機能・レジメン基準・感染症は JLAC11 の分析物 5 桁での突き合わせ
(`api/queries.ts:5461` の `useRecentLabResults`)。

### 1.2 結論: 施設の結果項目マスタを本体にする(二者択一ではない)

**［提案］** 施設の結果項目マスタを持ち、JLAC11 と JLAC10 はその行の属性として併記する。
施設マスタは JLAC11 の穴埋めの妥協ではなく、標準コードだけでは成り立たない構造上の要件。

- **JLAC11 は公開範囲が拡がっても施設の選択工程が要る**。測定法コードが試薬・機器の製品単位で
  (CRP だけで 103 コード併存)、自院の結果にどの 17 桁を付けるかは分析装置と試薬で決まる。
  ［事実］は `docs/lab-order-master-design.md` §1・§2。
- **標準コードには結果を表示するための属性が無い**。JLAC10 は単位を持たず(同 §2)、小数桁・
  表示順・基準値・データ型はどの標準にも無い。いま配布マスタで済んでいるのは、配布側が
  単位・データ型・コード選択肢を付けてくれているからで、JLAC10 で範囲を補うと同じ属性を
  施設が持つしかない。
- **累積表・前回値の突き合わせは施設項目で行うべき**。試薬更新で JLAC11 の 17 桁が変わると
  標準コードをキーにした時系列は切れる。施設項目をキーにすれば切れない。分析物 5 桁での
  突き合わせはこの代用で、施設項目があれば不要になる。
- **設計メモが既にこの方向を出している**。`docs/lab-order-master-design.md` §4 は施設が独自採番した
  概念を本体にし、JLAC11・JLAC10・LOINC をマッピング行として持つ設計。足りないのは
  「結果としてのみ存在する項目」(好中球など)を置く場所で、テーブルの分け方は §1.5 で変えている。

### 1.3 JLAC10 の役割

**［提案］** 併用する。ただし本体ではなく、JLAC11 が未公開の項目を標準コードで表すための属性。

- ［事実］JLAC10 コード表(分析物約 2,900)と MEDIS 臨床検査マスター(HS014、厚労省標準規格)で
  全域を覆える(`docs/lab-order-master-design.md` §2)。
- ［事実］電子カルテ情報共有サービスは 43+5 項目について JLAC10 / JLAC11 のどちらでも
  受け付け、対象外の項目はローカルコード(標準化不能時は `99999999999999999`)でよい
  (同 付録A)。JLAC10 で付けた結果も共有対象から外れない。
- ［事実］特定健診は JLAC10 のみ(同 付録A)。外注ラボ・分析装置との交換(B-1 / B-2)でも
  JLAC10 が突き合わせのキーになる場面が多い。
- ［事実］JLAC10 と JLAC11 は 1:1 に対応せず、公式対応表は廃止された(同 §2)。施設項目を
  挟めば、JLAC11 が公開されたときに属性を張り足すだけで済み、蓄積した結果データは変わらない。

### 1.4 具体的な形

1. **結果項目マスタの列**: 項目コード(施設採番)、名称、略称、カナ、検査分野、材料、データ型
   (PQ/CD/CO/ST)、表示単位と UCUM、コード選択肢、小数桁、表示順、有効期間、
   `jlac11_code` / `jlac10_code` / `loinc_code`(いずれも任意)。基準値(A-1)・パニック値(A-2)・
   デルタチェックの閾値(A-5)はこの行にぶら下げる。
2. **`Observation.code`** は施設コードの coding を先頭に、JLAC11・JLAC10 の coding を持っていれば
   併記する。FHIR は複数 coding を許すので、標準への出力と施設内の突き合わせが両立する。
   読み出し・突き合わせのキーは施設コードに寄せる。
3. **オーダー項目 → 結果項目の対応**は、いまの JLAC 引き当てをやめて対応表で明示的に持つ
   (§1.5)。読み出し先は結果展開の `hooks/useLabOrderResultLines.ts` で、「展開していません」の
   通知は不要になる。
4. **供給元は 3 段階**: 配布の共有項目マスタ(JLAC11 と JLAC10 の両方を持つ 43+5 項目)を初期
   取込 → 残りを JLAC10 コード表か MEDIS 臨床検査マスターから追加 → 単位・型・基準値を施設で
   補う。既存の取込(`backend/app/services/master_import/lab_item_importer.rb`)は配布マスタの
   写しとして残し、施設マスタへの取込元にする。
5. **既存データ**: 蓄積済みの `Observation.code` は JLAC11 のみなので、読み出しは JLAC11 での
   引き当てを残せば今のまま動く。施設コードは新規の書き込みから付ける。

### 1.5 テーブルの置き方(オーダー項目と結果項目は分ける)

**［提案］** 既存の 2 表はそのままに、結果項目マスタと対応表を新設する。

| テーブル | 責務 |
|---|---|
| `master_lab_order_items`(既存) | **頼む単位**。検体・採取管・実施区分・レセ電算コード・伝票レイアウトへの配置 |
| `master_lab_panel_items`(既存) | **パネル → 構成オーダー項目**。必須/任意/条件付き、入れ子 |
| `master_lab_result_items`(新設) | **返る単位**。データ型・単位・小数桁・コード選択肢・基準値・パニック値 |
| `master_lab_order_item_results`(新設) | **オーダー項目 → 結果項目**(1:N)と表示順 |

**［提案］** 当初は設計メモ §4 どおり `master_lab_order_items` に orderability(order / observation /
both)を足す 1 テーブル案を書いていたが、次の 2 点で採らない。

- **パネル構成テーブルに別の関係が 2 つ載る**。「パネル → 構成オーダー項目」(末梢血液一般が
  RBC・WBC を含む)と「オーダー項目 → 結果項目」(血液像 1 件が好中球など 20 件を返す)は別の関係。
  **血液像はパネルではなく単項目**なので、後者を panel として表すと panel の語が 2 つの意味を持つ。
  テーブル名のずれよりこちらの方が深刻。
- **属性も更新周期も重ならない**。オーダー項目は診療報酬改定と院内運用で変わり、結果項目は
  試薬・装置の更新で変わる。共通なのはコード・名称・略称・カナ・検査分野・JLAC・有効期間だけ。

**［導出］** 分けると **orderability のフラグが要らなくなる**。好中球のように単独で頼めない項目は
結果項目マスタにだけ存在する、という事実がテーブルの所属で表れる。フラグで区別するより素直。

**［事実］** 基準値・パニック値を配布マスタ側(`master_jlac_items`)に持たせることはできない。
取込が**全件洗い替え**で(`backend/app/services/master_import/jlac_item_importer.rb` 冒頭の
「replaces master_jlac_items wholesale」)、次の配布ファイルの取込で消える。

**［提案→対応済み(2026-09-10)］** 配布のコードマスタは施設の項目マスタと役割が違うので、
`master_lab_items` を **`master_jlac_items`** に改めた(モデル `Master::JlacItem`、API
`/master/jlac_items`、取込画面の種別名「共有項目JLACコードマスタ」)。機能は変えていない。

**［提案］** 設計メモ §4 の `lab_concepts`(1 テーブル + orderability)と違えるのは、あれが
何も無い状態からの設計だから。いまはオーダー側の表が実在し、オーダー固有の属性を持っている。
LOINC の ORDER_OBS も「規範的ではなく最良近似」(同メモ 付録A)で、コード体系の属性であって
施設マスタの構造を決めるものではない。

## A. 検査結果の品質・安全

結果は「値と H/L を手で入れて final で確定する」段階で止まっている。臨床で結果を読むための
材料(基準値・報告状態・確認者)がまだ無い。

### A-1. 基準値と H/L の自動判定 — **対応済み(2026-09-10)**

> `master_lab_reference_ranges`(結果項目 × 性別 × 年齢帯の下限・上限)を新設し、結果登録画面で値を
> 入れた時点の自動判定、保存時の `Observation.referenceRange`、内容表示・時系列の基準値列まで入れた。
> 初期値は 148 行 / 128 項目を `db:seed` でのみ投入(JCCLS 共用基準範囲・代表的なカットオフ値・参考値の
> 3 通りで、出どころは行の備考にある)。単位が無かった項目には単位の初期値も同梱。
> 詳細は readme「基準値と H/L の自動判定」。
> 感染症判定の `interpretation` 依存への切り替えは、旧結果(自動判定前の N)が残るので行っていない。

**［事実］** H/L は人が選ぶ。フォームで未選択のまま保存すると `interpretation` は `N`(正常)に
なる(`fhir/labResultHelpers.ts:74-83`)。`Observation.referenceRange` はどこにも書いていない。
共有項目マスタは基準値の材料(`reference_lower_flag` / `reference_upper_flag` /
`reference_judgment_flag` / `value_lower_limit` / `value_upper_limit`。`backend/db/schema.rb:347-352`)を
取り込んでいるが、`api/masterClient.ts` の `LabItem` 型に含めておらず、画面・判定とも未使用。

**［提案］** §1 の結果項目マスタに基準値(性別 × 年齢帯で複数行)をぶら下げ、結果登録時に
`Observation.referenceRange` を焼き付け、値と突き合わせて H/L を自動判定する。手入力での
上書きは残す(装置由来の判定を人が直す場面がある)。配布マスタの上下限は初期値の供給元に留め、
施設値をマスタで持つのは基準値が測定系ごとに変わるため。

**［事実］** 感染症の陽性・陰性判定(`fhir/infectionHelpers.ts`、readme「感染症」)が
`interpretation` を信用できず値の文字列を先に読んでいるのは、この「未選択は N」が原因。
A-1 が入れば判定の根拠を `interpretation` に戻せる。

### A-2. パニック値(緊急異常値)

**［事実］** 閾値も通知も無い。コードベースに panic / critical に相当する処理は無い。

**［提案］** 閾値マスタ(項目ごとの下限・上限)、`interpretation` の `HH` / `LL`、登録時に依頼医への
通知、医師が受け取ったことの記録までを一組で入れる。通知の器はオーダー承認と同じ経路
(`Provenance` の署名)ではなく、宛先と未読を持てる `Task`(`code = lab-panic`、`owner` = 依頼医)が
向く。患者帯の `Flag` に出す案もあるが、パニック値はその 1 件の結果に閉じた事象なので
オーダー・結果に紐づく Task の方が実態に合う。

### A-3. 報告状態(暫定・確定・訂正)

**［事実］** `Observation` も `DiagnosticReport` も `status: "final"` の固定
(`fhir/labResultHelpers.ts:277` / `:384`)。培養のような途中経過報告、訂正報告が表現できない。
細菌検査・病理は `preliminary` / `amended` を実装済みなので、検体検査だけが持っていない。

**［提案］** 暫定(`preliminary`)・確定(`final`)・訂正(`corrected`)を選べるようにし、訂正時は
旧値を残す(上流の `_history` があるので、画面から前の版を読めるようにするだけで足りる)。
訂正が起きた結果は累積表・カルテで印を出す。

### A-4. 医師の結果確認(既読)

**［事実］** 結果が出たことを医師が知る仕組みも、確認した記録も無い。カルテの検査結果タブを
開けば見えるだけで、未読の区別が無い。

**［提案］** 「誰がいつ確認したか」は代行入力の承認と同じ `Provenance`(`agent.type = verifier` +
`signature`)に載せる(`docs/order-common-backlog.md` §2.5 で作った器がそのまま使える)。
画面は診療業務メニューの「未確認の検査結果」一覧と、カルテのタブ・タイムラインの未読バッジ。
A-2 のパニック値通知とは分ける(パニック値は宛先を決めて push、既読は全結果を対象に pull)。

### A-5. 前回値表示とデルタチェック

**［事実］** 結果入力フォームに前回値が出ない。値の飛びを検出する処理も無い。

**［提案］** 入力行に前回値・前回採取日を並べ、項目ごとの閾値(絶対差・比)を超えたら警告を出す。
読み出しは既存の `useRecentLabResults`(`api/queries.ts:5461-5480`)の JLAC11 分析物 5 桁での
突き合わせに乗る。取り違え・入力ミスの検出が主目的なので、警告は登録を止めない。

### A-6. 結果に付随する情報

**［事実］** いま `Observation` に入るのは 値 / 単位 / `interpretation` / 材料 / 採取日だけ。
次が保存されていない。

- 項目ごとのコメント(`Observation.note`)
- 検査室の総合所見(`DiagnosticReport.conclusion`)
- 実施者・実施施設(`performer`。他の検査系は持っている)
- 報告日時(`issued`)。いまは採取日しか無く、いつ報告されたかが残らない
- 測定法(オーダー項目のマスタには JLAC があるが、結果に測定法を残していない)

**［提案］** まとめて足す。A-3(訂正)・B-1(取込。装置と実施施設が入る)と同じ場所を触るので、
どれかに着手するときに一緒に入れる。

## B. 取込・外注・出力

### B-1. 結果の取込(手入力しかない)

**［事実］** 結果登録の経路は 2 つ(カルテの検体検査タブ、検体検査一覧の行から)とも手入力。
CSV・JAHIS 臨床検査データ交換規約(HL7 v2.5)・分析装置からの取込はバックエンドにもフロントにも無い。

**［提案］** 取込は backend に置き、上流へは既存の結果登録と同じ形(DiagnosticReport +
Observation + Specimen)で書く。突き合わせのキーはラベル番号(`accessionIdentifier`)を第一に、
JLAC + 患者番号 + 採取日を第二にする。ラベル番号は既に上流採番で管の同一性を表しているので、
装置がバーコードを読む運用ならそのまま繋がる。マスタに無い項目・引き当てに失敗した行は
保留にして取込画面で人が処理する。**運用に乗せるうえで最大の欠落**で、A-1 の基準値と
A-6 の実施者・報告日時が同時に必要になる。

### B-2. 外注(外部ラボ)

**［事実］** オーダー項目マスタに実施区分(`execution_type` = 院内 / 外注)を持ち、マスタ画面で
編集できる(`pages/LabOrderItemPage.tsx`)。しかし参照しているのは型定義だけで
(`api/masterClient.ts:616` / `:687`)、オーダー・部門業務・結果のどこも見ていない。

**［提案］** 外注先マスタ(連携先 Organization を使う)、外注分の依頼一覧と外注伝票、
検体の送り出しの記録、結果の未着一覧、外注ラボの CSV 取込(B-1 と同じ器)。ラベルの
`Specimen` に送付先を持たせれば到着確認と同じ線で追える。

### B-3. 帳票(検査依頼書・結果報告書)

**［事実］** 検体検査の帳票は検体ラベルだけ(`backend/app/controllers/reports/` に
lab_label / injection / injection_label / prescription / questionnaire_response しか無い)。

**［提案］** 検査依頼書(伝票)と検査結果報告書の 2 種を、同梱 `.tlf` + Thinreports の既存基盤に
足す。結果報告書は累積表の形(項目 × 採取日)も要る。マッピングは `docs/report-mappings/` に
既存帳票と同じ形で残す。

### B-4. 検査室側の未処理一覧

**［事実］** 検体検査一覧は検査日 1 日ぶんの表示で、「実施済(到着済)なのに結果が未登録」
「発行済みなのに未到着」を横断して見る画面が無い。後者は `docs/lab-arrival-design.md` §6-2 で
先送りした未着レポートそのもの。

**［提案］** 部門業務に 2 つの一覧を足す。データは既に揃っている(結果登録済みかは
ワークリストが `reportId` として持っている。未到着は `Specimen` の `receivedTime` の有無)。

### B-5. 累積表・グラフの拡張

**［提案］** A-1 が入った後に効くもの。基準値の列、異常値のみに絞る表示、グラフへの基準範囲帯、
カルテ本文への貼り付け(いまはタブ区切りのクリップボードコピーのみで、診療記録に貼るには
手作業が要る)。

## C. オーダー入力と採取の運用

### C-1. 重複・回数のチェック

**［事実］** 登録時の検証は「検査項目 1 件以上・検査日必須」だけ(`components/LabOrderForm.tsx:271-284`)。
同じ日に同じ項目を二重にオーダーしても何も出ない。

**［提案］** 同日・同項目の重複、直近 N 日以内の同項目(月 1 回までの算定制限がある項目)を
登録前に警告する。止めるのではなく警告に留める(必要で出す場面がある)。

### C-2. 項目ごとの採取条件と採取時刻

**［事実］** コメントはオーダー単位に 1 本だけ(`LabOrderForm.tsx:352-381`)。空腹時・負荷後・蓄尿・
時間指定採血を項目ごとに指示できない。検査日も日付のみで、採取予定時刻を持たない。

**［提案］** 明細 `ServiceRequest` に採取条件(コード + 自由文)を持たせ、ラベルにも刷る。負荷試験は
JLAC の識別コードが「負荷後 60 分」を別項目として持つので、マスタ側で項目を分ける方が素直な
ケースもある。どちらで表すかは項目ごとの判断になる。

### C-3. 採取(採血)の記録

**［事実］** ラベル発行(= 受付)と検査室への到着は記録するが、**誰がいつ採ったか**が残らない。
`Specimen.collection.collectedDateTime` は結果登録時に「検体採取日」として書くだけで
(`fhir/labResultHelpers.ts:257`)、採取者(`collection.collector`)は持っていない。

**［提案］** 採血の実施入力を足し、`Specimen.collection` に採取者・採取日時を記録する。
ラベル発行済みの `Specimen` が既にあるので、そこへ書き足す形になる。病棟採血なら看護
ワークシート(`pages/NursingWorklistPage.tsx`。**いま検体検査への参照が無い**)にその日の採血予定を
出し、そこから実施入力へ飛べるようにする。注射の同じ課題
(`docs/injection-order-design.md` §8 C)と並べて扱うとよい。

### C-4. 同一検体の複数本採取

**［事実］** オーダー構造に本数の概念が無く、`groupBySpecimen` は検体コードで 1 つにまとめる。
`docs/lab-label-design.md` §1・§7-3 で対象外にしたまま。

**［提案］** 検体量の多い項目を含むとき、外注と院内で管を分けるときに要る。オーダー側の
データ構造から見直しになるので、B-2(外注)と同時に判断する。

### C-5. 状態に応じた編集・削除の制限

**［事実］** 受付済・実施済・結果登録済のオーダーも、削除・明細の変更が止まらない
(`api/queries.ts:6433-6451`)。オーダーを削除しても進捗の `Task` は残る(部門横断の既知の課題。
`docs/injection-order-design.md` §8 D)。

**［提案］** 結果が紐付いたオーダーは明細の変更と削除を止める、受付以降は警告を出す、削除時に
`Task` と自所有の `Specimen` を片付ける。ラベル発行済みの `Specimen` は発行・到着の記録なので
残す(結果の削除で消さない現行の扱いと同じ)。

### C-6. 頻用項目

**［事実］** 検体検査に頻用(お気に入り)の仕組みが無い。頻用があるのは細菌検査(菌・抗菌薬)、
病理(臓器)、放射線(JJ1017)。

**［提案］** 検査伝票とオーダーセットがあるので優先度は低い。入れるなら「直近に自分が出した
オーダーからの選択」の方が、マスタを育てる手間が無い分だけ実用的。

### C-7. 会計連携

**［事実］** レセ電算コード(`receipt_code`)はオーダー項目マスタに持てるが、FHIR にも書いておらず
点数計算も無い。上流に `ChargeItem` / `Claim` / `Invoice` が未実装
(`docs/rad-result-design.md` §7)。

**［提案］** 種別をまたぐ課題なので、放射線・処置と合わせて扱う。検体検査に固有なのは、
包括算定(判断料・まるめ)の単位がオーダーではなく検査分野であること。
