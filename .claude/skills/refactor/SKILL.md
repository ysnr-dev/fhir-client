# リファクタリング

**振る舞いを変えずに**、読みやすく・重複なく・約束どおりの形に整える。画面の見え方、`/master` の JSON、
上流に書く FHIR リソースの形は前後で同じでなければならない。FHIR の出力が変わる変更はリファクタではなく
機能変更なので、見つけても混ぜずにユーザーに報告する(実装ガイド `../fhir-ig` に関わるため)。

スクリプトは fhir-client のリポジトリ直下から、下の表のとおりのパスで実行する。
どれも**候補を出すだけ**で、消す・まとめるの判断は 1 件ずつコードを読んで行う。

## 0. 始める前に

- `docs/refactoring-plan.md` を読む。過去の回(第 1〜3 回)の「次の候補(今回やらない)」が今回の種になり、
  「残すと判断したもの」「やらないこと(理由つき)」は蒸し返さない。同じ候補を再提案するときは、
  そこに書かれた理由が変わったことを示す。
- 始める前の状態が緑であることを確かめる(赤なら先にユーザーに報告する。リファクタで直したと誤認しないため)。

```bash
docker compose exec frontend npx tsc -b
docker compose exec frontend npm run lint
docker compose exec frontend node scripts/import-cycles.cjs src/api/queries src/api/masterClient src/api/masterQueries
```

  Docker が使えない状況(計画だけを頼まれた、コンテナが止まっている)では、未実施であることと
  着手時に回すコマンドを一覧に書く。

## 1. 範囲を決める

ユーザーが対象(機能・ディレクトリ・ファイル)や観点(コメントだけ、重複だけ)を指定していればそれに絞る。
部門名の前方一致は別部門を含みうる(`rad*` には `radiotherapy*` が当たる)ので、何を対象にしたかを一覧に明示する。

指定が無ければ、次の節のスクリプトで全体の候補を洗い、**効果が大きく危険が小さい順**に並べた一覧を
ユーザーに短く示してから着手する(確認待ちで止まらなくてよいが、何をやるかは先に見せる)。一覧の形:

| # | 候補 | 場所 | 規模(行・ファイル数) | 危険(低: 型で担保 / 中: 画面確認が要る / 高: FHIR 出力に触れる) | 順 |
|---|---|---|---|---|---|

テーマは「消す」「寄せる(名前だけ違うファイル)」「寄せる(マスタ画面)」「寄せる(FHIR の組み立て)」「約束からの外れ」
のように分類し、各テーマが diff を読んだ人に一言で言える単位になるようにする。

上流 `../fhir-server` も次のときは対象に含める。含めるときは、その旨を一覧に書く。

- fhir-client 側の手元フィルタや N+1 の read を消すために、上流の検索パラメータ・`_include` が要る
  (無ければ上流に足す。足せないなら `docs/server-improvement-backlog.md` に書いて手元は残す)
- 同じ定義(コード表・識別子の system・バリデーション)が両リポジトリに重複していて、片方に寄せられる
- 上流の `app/lib/fhir` や検索定義(`search_definitions`)に、同じ種類の経緯コメント・重複・未使用がある
- ユーザーが「上流も」と言った

上流に手を入れたら、rspec は上流のコンテナ(`docker compose exec web`)で回す。本番は fhir-server を
client より先にデプロイする前提なので、client がその変更に**依存する**なら報告にそう書く。

## 2. 候補を洗う

| コマンド(リポジトリ直下から) | 見つけるもの | 読むときの注意 |
|---|---|---|
| `.claude/skills/refactor/scripts/scan-comments.sh [path...]` | 経緯・比較・作業メモ・バグ言及・コメントアウトされたコード(3 リポジトリ) | 「変更前の担当医」「削除済みのプロブレム」のように業務の意味で使う語も混じる。文脈で判断 |
| `.claude/skills/refactor/scripts/scan-conventions.sh` | CLAUDE.md の約束から外れた箇所(日付・色・抑止コメント・ボタン・fullUrl・種別分岐) | `App.css` の色の直書きは件数が多いので、同じ色をまとめて変数化する単位で扱う。フォーム内の説明文は機械的に拾えないので目で見る |
| `node .claude/skills/refactor/scripts/dead-exports.cjs [--path <前方一致>]` | 未使用の export(「どこからも未使用」と「export だけ不要」、値と型に分けて) | 名前一致なので同名の別物は見逃す。消す前に grep |
| `.claude/skills/refactor/scripts/dead-ruby-methods.py backend ../fhir-server` | 名前がどこにも書かれていない Ruby メソッド | `send`・`public_send`・`respond_to?` で動的に呼ぶものは出てしまう |
| `.claude/skills/refactor/scripts/duplicate-blocks.py <dir...> [--by-file] [--min-lines N]` | 複数ファイルに同じ形で繰り返されている塊(長い順)。`--by-file` はファイルの組ごとの重複行数 | 名前だけ違う同形(`buildRadTaskUpdate` と `buildPhysioTaskUpdate`)は拾えない。次の行のスクリプトで測る |
| `.claude/skills/refactor/scripts/compare-departments.py --pairs <file...>` または `<fileA> <fileB> [--diff]` | 部門名を正規化してから diff し、「名前だけ違うファイル」の近さを行数で出す | 差 0〜数十行なら設定方式で 1 つにできる見込み。数百行なら別物 |

対象を絞るとき: `scan-comments.sh` は path 引数、`dead-exports.cjs` は `--path`、`duplicate-blocks.py` は
他部門との重複を見るために親ディレクトリ(`frontend/src/components` など)ごと掛けて出力を `grep` する。
`scan-conventions.sh` は全体実行して出力を `grep` で絞る。

スクリプトが拾わない候補は、対象の機能の `docs/features/*.md` と設計書を読んでから、コードを通しで読んで探す。
よくあるもの:

- 部門オーダー(放射線・生理・内視鏡・処置・病理・輸血…)で「同じ流れを種別ごとに書き写した」関数・画面
- 1 ファイルに画面・状態・FHIR の組み立てが同居している 1,500 行超のファイル
- 種別ごとの `if` / `switch` の連なり(レジストリ `fhir/orderKinds.ts` に 1 行足せば済む形にできないか)
- 読み込み直後の `.filter` / `.sort`、1 件ずつの `read`(上流の検索・`_include`・`_sort` に寄せる)
- hook を連続で呼んで読み直しを積み重ねている書き込み(transaction Bundle 1 回にまとめる)

## 3. 何を直し、何を残すか

判断の細目と例は `references/criteria.md` にある。迷ったらそこを読む。要点は次のとおり。

**コメント**は「現状の意図」だけを残す。消すのは、修正経緯・過去との比較(「以前は」「〜に変更」「〜していたが」)、
直した事実の記録(「バグ修正」「〜に対応」)、コードを日本語に訳しただけの行、作業メモ(TODO は `docs/*-backlog.md` へ)、
コメントアウトされたコード。残すのは、そうなっている理由(上流の制約、FHIR の作法、時差、競合)、
罠(`toISOString` の前日問題、`Modal` が非ポータルであること)、読み手が疑う分岐の根拠。経緯を含む文は
「今どうなっているか」の文に**書き換える**(消すだけで意図が失われるなら)。

**重複**は、同じ流れが 2 か所以上にあり、片方を直したらもう片方も直すべき関係にあるときだけまとめる。
差分は引数か対応表(レジストリ)で表し、「種別ごとの if を並べる」形にはしない。似ているが業務が違うもの
(検体検査の採血管グループと放射線の器材など)は無理に寄せない。共通化した結果が元より読みにくければ戻す。
既にある設定方式の例(`createTaskHelpers`、`makeUpdateTaskStatusHook`、`simpleMasterHooks`・`itemLayoutHooks` など)は
`references/criteria.md` の「まとめ方」にある。先にそれを探し、同じ形に揃える。

**未使用**は、grep で本当に参照が無いことを確かめてから消す。名前で動的に呼ばれるもの(Rails の
`send`、通知レジストリのキー、`.tlf` から参照するフィールド名、seed・マスタ CSV の列名)は grep の対象に入れる。
消す単位は関数・export・CSS クラス・ルート・マスタの列・ドキュメントの参照まで(片方だけ消して残骸を作らない)。

**約束からの外れ**(`scan-conventions.sh` の出力)は、CLAUDE.md の「実装上の約束」に合わせる。これは振る舞いを
変えない範囲で行う(たとえば `toISOString().slice(0, 10)` を `today()` に替えると JST 9 時前の結果が変わるが、
それは不具合の修正なので別立てで報告し、ユーザーが望めば直す)。

**分割**は、画面(React)・状態(hook)・FHIR の組み立て(`fhir/*Helpers.ts` の純粋関数)の境界で切る。
既存の分け方に従う: カルテのカードは種別ごとのファイル、`api/queries` はドメインごとのファイルと `index.ts` の再 export。
新しいファイルの名前は隣のファイルに倣う。

## 4. 進め方

1. **1 テーマずつ**。「コメントの掃除」「放射線と生理の実施 Bundle の共通化」のように、diff を読んだ人が
   一言で言える単位で進め、終わるたびに検証する。複数テーマを 1 つの差分に混ぜない。
2. **消す → 寄せる → 分ける** の順。先に未使用を消すと、共通化や分割で動かす量が減る。
3. 共通化は、まず共通関数を書いて 1 か所を置き換えて検証し、通ってから残りを置き換える。
4. 分岐をレジストリに寄せるときは、対応表の型を先に作って**型エラーを道標に**埋める
   (`orderKindRegistry.tsx` などの既存の対応表がその形)。
5. 整形だけの差分を出さない(コンテナの prettier は使わない。周囲の書き方に合わせる)。
   触っていない行を動かす変更(import の並べ替え、改行位置)や、部門名のままの CSS クラス(`rad-*` を生理でも使う)の
   改名は入れない。改名するなら別テーマにする。
6. 途中で不具合を見つけたら、直さずに控えておき、報告にまとめる(直すのは別の作業)。
   ただし明らかな誤りで、ユーザーが「ついでに直して」と言える程度なら、報告に「直した」と明記して直してよい。
7. `bash -c` の中に書く一時的な関数名・変数名に `rm` を含めない(`norm` など)。危険な操作と誤認されて止まる。

## 5. 検証

テーマごとに次を通す。

```bash
docker compose exec frontend npx tsc -b                                 # 型(必ず -b)
docker compose exec frontend npm run lint
docker compose exec frontend node scripts/import-cycles.cjs src/api/queries src/api/masterClient src/api/masterQueries
docker compose exec -e RAILS_ENV=test -e ADMIN_TOKEN= backend bundle exec rspec [spec/path]
cd ../fhir-server && docker compose exec web bash -c "RAILS_ENV=test bundle exec rspec [spec/path]"   # 上流を触ったとき
```

- frontend にユニットテストは無いので、**触った画面はブラウザで前後を見る**(一覧の表示・登録・編集・取消)。
  触った機能の検証データは `MEMORY.md` の `dev-seed-*` に場所がある。
- FHIR の組み立て関数を動かしたら、前後で出力が同じことを確かめる。やり方は 2 つ。
  - 開発環境で同じ入力を登録して `/fhir/<Type>/<id>` を前後で比べる(`git stash` で元の関数に戻して同じ入力の JSON を控える)。
  - 既存のリソースをフォーム値に戻す関数(`parse*` / `*FormValues`)があれば、開発環境のリソースをそれに通して
    組み立て関数に渡し、元の JSON と比べる round-trip のスクリプトを scratchpad に書く(`src/demo-seed` と同じく
    `npx vite build --config` で Node 用に束ねて実行する。手順は `docs/demo-seed.md`)。
  `meta`・`id`・日時以外に差分が出たら、それはリファクタではない。
- CSS の色を変数化したら、ライトとダーク(`data-theme="dark"`)の両方で見る。
- 未使用を消したあとは `tsc -b` と、消した名前での `grep -rn` が 0 件であることで確かめる。

## 6. ドキュメントと報告

- 振る舞いが変わらないので `docs/features/*.md` の更新は原則不要。ただしファイル名・関数名・ディレクトリを
  文書が参照していれば直す(`grep -rn "<旧名>" docs readme.md CLAUDE.md` で探す)。
- 実装ガイド(`../fhir-ig`)は出力が変わらない限り触らない。
- **`docs/refactoring-plan.md` に今回の回を足す。** 先頭(最新の回の上)に「第 N 回(日付)」の節を作り、
  既存の回と同じ見出し(正しさ / 上流に寄せた / コメント整理 / 機械的な重複統合 / 次の候補(今回やらない) /
  残すと判断したもの)で、やったこと・検証結果・見送った候補と理由を書く。計画だけで終えたときも
  「次の候補」として残す(次の回がここから始まる)。
- 見つけた不具合・設計上の課題・上流に欲しい機能は、それぞれ `docs/*-backlog.md` と
  `docs/server-improvement-backlog.md` に追記するか、報告だけにするかをユーザーに委ねる(勝手に書かない)。

報告には次を書く。

- テーマごとに、何を・どこで・どう整理したか(消した行数や共通化した関数名より、「放射線と生理の実施 Bundle を
  `buildPerformBundle` に寄せた」のように読んで分かる形で)
- 検証の結果(型・lint・循環・rspec・画面確認のそれぞれについて、通ったか、見ていないか)
- 見送った候補と理由(誤検出、業務が違う、危険が大きい)
- 見つけたが直していない不具合
- 上流を触った場合は、client がその変更に依存するか

**コミットはユーザーの指示があるまでしない。** 提案するメッセージは `refactor:` / `remove:` / `style:` の接頭辞で、
要点だけの 1 行(「refactor: 部門ごとに重複していた実施 Bundle の組み立てを共通化し、古いコメントを整理」)。
